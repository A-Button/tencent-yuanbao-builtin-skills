# 快递100 Connector寄件工作流

## 一、获取寄件人

```text
调用 get_default_sender
  ├─ 成功：展示脱敏姓名、手机号和地址，请用户确认
  ├─ 无数据：依次询问姓名和手机号、完整地址
  └─ 未认证：提示重新连接快递100服务
```

默认寄件人只作为自动填充来源，用户要求修改时以本轮明确提供的信息为准。

用户要求修改默认寄件人时：

1. 调用`search_address_book`，传`addressType=sender`和用户提供的姓名关键字。
2. 展示脱敏候选；无匹配或多条匹配时不得自行选择。
3. 用户明确确认某条候选后，调用`set_default_sender(addressId, confirmed=true)`。
4. Tool成功返回的地址即为写后校验通过的新默认寄件人；失败或超时不得自动重试。

## 二、获取收件人

用户用姓名指定收件人时，优先调用`search_address_book`并传`addressType=receiver`：

- 唯一匹配：展示脱敏姓名、手机号和地址，请用户确认。
- 同名多条：展示编号和脱敏地址，让用户明确选择。
- 无匹配：再依次收集并确认姓名、手机号、省市区及详细地址。

用户已经提供完整收件信息时无需重复查询地址簿，但仍需确认：

1. 姓名和手机号。
2. 省市区及详细地址。

地址为自由文本时调用`parse_address`。返回的省、市、区或详细地址不完整时，只追问缺失部分。

## 三、地址簿管理

### 新增地址

1. 先询问用户要新增“寄件地址”还是“收件地址”，不得根据姓名或上下文猜测分类。
2. 收集姓名、手机号、省、市、区和详细地址；缺少结构化行政区时先调用`parse_address`。
3. 展示地址分类和脱敏后的完整信息，取得明确确认。
4. 调用`add_address_book_entry`，分别以`sender`或`receiver`传递`addressType`。
5. 新增地址固定为非默认；如需设为默认寄件人，再单独执行`set_default_sender`流程。

### 修改地址

1. 先调用`search_address_book`定位目标；同名多条时让用户明确选择。
2. 只传用户要求修改的字段，未提及字段不传。
3. 展示脱敏后的修改前后差异并取得明确确认，再调用`update_address_book_entry`。
4. 普通修改不得改变地址分类或默认状态。

### 删除地址

1. 先调用`search_address_book`定位并展示脱敏目标，取得明确确认。
2. 当前默认寄件地址禁止删除；提示用户先将另一条寄件地址设为默认。
3. 调用`delete_address_book_entry`时只传`addressId`和`confirmed=true`，不得让用户提供`guid`或Token。
4. 超时、断网或结果未知时不自动重试，重新查询地址簿确认当前状态。

## 四、物品知识与重量

```text
用户提供物品名称
    ↓
query_item_weight
    ↓
按匹配来源展示已有重量、分类、寄递限制、运输规则和包装建议
    ↓
仅在继续查价或寄件时，让用户确认有效参考重量或提供实际重量
```

用户仅咨询能否寄、运输条件、包装或保价建议时，到回答知识结果为止，无需收集地址、订单和重量。

`matchSource`/`match_source=DEFAULT`表示未匹配，重量和可寄结论均未知；旧版返回的默认“1.0公斤、可寄递”也不能当作已核实结果。已匹配但没有重量时保留运输规则和包装信息；只有用户继续查价或寄件，才询问实际重量。

运输规则按运输方式和条件解释，空运禁运不等于全部禁运。信息未覆盖用户问题时可以按Skill规则补充网页搜索，不能将空规则解释为无限制。

## 五、查询并选择快递

调用`list_shipping_options`前必须具备：

- 寄件城市。
- 收件城市。
- 大于0的重量（公斤）。

Tool返回多家快递时：

1. 展示名称、预估价格、时效和服务类型。
2. 可以给出最便宜或最快的推荐，但不得自动选中。
3. 用户修改重量或寄收件城市后，必须重新查价。
4. 用户明确选择后，保留该结果中的公司编码、品牌标识、服务类型和价格字段用于预下单。

## 六、最终确认和预下单

调用`prepare_shipment_order`前，按以下顺序汇总：

```text
寄件人：姓名、脱敏手机号、完整地址
收件人：姓名、脱敏手机号、完整地址
物品：名称、重量
快递：公司、服务类型、预估价格
其他：备注、期望上门时间
```

只有用户明确回复同意后才能传递`confirmed=true`。未确认、表达犹豫或要求修改时，继续修改并重新展示汇总。

成功响应包含小程序链接 `url` 和二维码图片地址 `qrCode`。Agent必须：

- 优先读取 `structuredContent.url` 和 `structuredContent.qrCode`；字段位于 `structuredContent` 顶层，不再固定读取 `structuredContent.result`。仅有文本或旧服务字符串时按[链接与二维码](link-and-qrcode.md)处理。
- 在主对话中同时展示 `[去小程序确认并支付]({url})` 文字链接和 `![扫码进入小程序确认订单]({qrCode})` 内嵌图片，不默认附加“打开二维码”链接，也不调用工具新建网页、浏览器标签页或侧边预览。支付入口文字固定不变，禁止在正文或代码块输出裸链接；自定义协议无法点击时引导用户扫描主对话中的二维码，图片无法显示时如实说明并保留支付文字链接。
- 明确说明用户需要进入小程序确认最终订单、价格并完成支付。
- 使用本次Tool原样返回的两个地址，不自行拼接二维码、不重编码链接、不用示例值替代实际结果。
- 用户只要求展示或打开已有链接、图片加载失败时，复用本次结果，不重复预下单。只有用户明确要求重新创建预订单且寄件信息已确认时才再次调用；新结果替换旧链接和旧二维码，避免混用。

## 七、历史订单与物流查询

用户要求查看最近订单时调用`list_my_shipment_orders`。默认显式传`limit=200`获取当前接口允许范围内的最近订单，先汇总订单状态，再展示包含已取消在内的所有状态明细，不自动过滤取消订单。明细≤50条时全部展示，>50条时只展示前50条并说明剩余数量；50是展示上限，不是查询上限。用户明确指定状态、数量或查询范围时，按SKILL.md“历史订单”规则处理。统计覆盖本次已返回记录，不能将仅展示的50条当作全部统计。

历史订单列表不自动继续查物流。用户明确提供单号并要求物流轨迹时，调用
`aiserviceapiquery4agent_get`；若Tool提示需要手机号验证，再询问手机号或后四位。
不支持取消订单或售后能力。

物流查询有真实轨迹时，必须用Markdown表格输出，至少包含“时间”和“物流轨迹”两列。简短状态摘要可以放在表格前，但不能用段落、列表或原始Tool文本替代表格。时间、地点和状态均来自真实返回，缺失信息标为“未提供”，不推断或补造；未查询到轨迹时直接说明，无需生成空表或虚构记录。

## 八、失败降级

| 场景 | 处理 |
| --- | --- |
| 默认寄件人为空 | 手工收集寄件人 |
| 地址簿无匹配 | 手工收集收件人或提示用户换一个寄件地址关键字 |
| 地址簿同名多条 | 展示脱敏候选并等待用户选择 |
| 设置默认寄件人失败或超时 | 不自动重试；重新查询默认寄件人或提示稍后重试 |
| 地址新增、修改或删除失败/超时 | 不自动重试；重新查询地址簿确认状态 |
| 物流查询要求验证手机号 | 只询问手机号或后四位，再重新查询 |
| 物流查询无结果 | 如实说明未查询到，不编造轨迹 |
| 地址解析失败 | 要求用户补充或修正地址 |
| 重量未识别 | 要求用户提供实际重量 |
| 快递方案为空 | 提示当前路线暂无可用方案，不创建预订单 |
| 参数错误 | 只追问缺失或错误字段 |
| 未认证/Token过期 | 提示在当前平台重新认证或重新连接快递100 MCP；Skill不自行处理Token |
| 频率受限 | 告知稍后重试，不循环调用 |
| 预下单超时或失败 | 不自动重复提交，告知用户稍后重试 |
| 二维码缺失或加载失败 | 在主对话中保留“去小程序确认并支付”文字链接，说明图片未返回或未显示；禁止裸链接，不自动新开网页或侧边预览，不据此判定预订单失效，不重复下单 |
| 小程序链接无法点击 | 保留“去小程序确认并支付”文字链接并引导使用实际返回的二维码入口；禁止裸Scheme、原始URL代码块或伪造HTTPS链接 |
| 扫码提示失效 | 区分图片加载、扫码跳转和预订单可用性；有效期未知时不编造时长，同一链接重绘二维码不能刷新订单有效期 |

## 九、明确不做

- Python、CLI、Shell和本地缓存。
- 取消订单、退款及售后。
- 不在元宝对话或MCP Tool中直接扣款；展示小程序链接与跳转二维码，由用户在快递100小程序内确认并支付。
- 同名多条时自动替用户选择收件人，以及自动替用户选择快递公司。
