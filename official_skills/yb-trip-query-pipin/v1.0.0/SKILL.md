# 行程查询（携程公开数据）

通过四个携程 Connector 工具查询公开的交通、住宿、票务数据。工具在 Skill 加载后直接可用，
不要用 bash、curl 或任何自建客户端去替代它们，也不要假设存在第五个工具。

| 需求 | Connector | 工具 | 参数细则 |
|------|-----------|------|----------|
| 飞机票、航班时刻、航司舱位 | ctrip_flight | `query_flight` | [references/flight.md](references/flight.md) |
| 火车/高铁车次、席别余票 | ctrip_train | `query_train` | [references/train.md](references/train.md) |
| 酒店、房型与房价 | ctrip_hotel | `query_hotel` | [references/hotel.md](references/hotel.md) |
| 景点门票、票种与人群票价 | ctrip_ticket | `query_ticket` | [references/ticket.md](references/ticket.md) |

工具名就是上表的 `query_*`，属于四个携程 Connector，加载后可直接调用。查询前先读对应 references，
按里面的必填项与易错点组装参数，不要凭印象填参数名。

## 边界

- 只查询与比选：不代下单、支付、占座、改签、退票，也不要声称已经订好。
- 价格、余票、房态一律以工具回包为准，回包没有的字段不写、不用其他来源补齐、不估算。
- 查到的是查询时刻的参考价，会随库存和日期变动，呈现时说明这一点。
- 用户要下单时，只回包里返回的携程 H5 / APP 地址可以给出，除此之外不构造预订链接。

## 输入规范

- 城市用标准中文名，不带"市""省""自治区"等后缀：北京、上海、杭州、三亚。
- 日期 `yyyy-MM-dd`，时间 `HH:mm`。
- "明天""下周五""国庆"这类相对日期，用系统给出的当前日期换算后再传，不要用自己的记忆猜日期；
  跨年、跨月尤其要按换算结果写全。
- 缺参数时一次性问清，不要一轮只问一个。真正必问的只有"哪个城市"和"哪一天"：
  出发/到达城市不明确就必须问；日期缺失时，若上下文已有行程日期就直接用，没有才问。
  人数、舱位、预算这类筛选条件能推断就先按默认查，把筛选项在结果里说明，别拿来阻塞查询。

## 查询与放宽

- 默认只要最有用的那几条（机票等工具默认约 10 条）。用户明确说"全部""所有航班"再放开。
- 排序跟随用户意图："最便宜"用价格升序，"最早/最晚"用时间排序；用户没说就按工具默认，
  并在结论里点出最便宜和最快各一条。
- 结果为空或过少时，一次放宽一个条件并说明改了什么：先看是不是条件过窄
  （只直飞、时间窗太窄、预算过低、指定机场/站点），再考虑相邻日期或邻近机场/车站。
  放宽后仍无结果就如实说"这个条件没查到"，不要拿别的目的地或示例数据填空。
- 一个工具一次只解决一个品类。跨品类行程（交通+住宿+门票）分多次查询，最后汇总。

## 结果呈现

- 用紧凑的 Markdown 表格，一行一条，只放用户做决定要用的列：
  - 交通：班次号/航司、起降或到发时间、历时、中转情况、最低价。
  - 住宿：酒店名、星级或评分、位置或地标、入住日期区间的参考房价。
  - 门票：景点、票种、适用人群、价格。
- 顺带一句结论（推荐哪一条、为什么），不要写成长篇分析报告。
- 用户问"还有票吗/还有房吗"时，用回包里的余票、房态字段回答，不要说"可以订"。
- 不输出 Connector 内部 ID、三字码以外的调试字段、H5 参数或工具元信息。

## 异常

- 工具报错或超时：如实报告，最多换一种等价写法重试一次（中文城市名换三字码、加/去筛选条件），
  不要静默改用其他数据源。
- 传 `keyword` 的查询只返回检索页 H5 与 APP 地址，不是结构化结果。能用结构化参数时优先结构化
  参数，链接只作为补充。
