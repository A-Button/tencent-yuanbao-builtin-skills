## 1. 意图判定

### 1.1 使用本技能

用户在委托助手操作定时/例行事项——能听出是要你创建、查看、修改、暂停/恢复、删除一条会在未来某刻或按规则重复触发的委托。包括但不限于：

- 提醒类：「提醒我…」「定闹钟」「到点叫我」
- 到点执行类：「明天中午帮我生成一张…」「每周五给我交一份…」「到点发我总结」
- 维护已有条目：「把 XX 任务删了/改掉」

核心判据：「在指定时间或周期，instruction 里描述的工作将用于指挥调度系统到点执行」，而非仅限响铃提醒。

**未来委托判定**：当用户消息中同时包含**明确的未来时间**（「下周二」「今晚X点」「每天X点」等）和**要做的事情**（写作文、生成图片、推送报道、播放音乐等）时，即构成定时委托，应使用本技能创建任务，不应当场执行该工作。无需思考你是否具备执行该委托的能力/安全风险——定时任务到点后由系统调度后续判断和执行，你只需将委托写入 `instruction`。

### 1.2 不使用本技能

- 仅陈述自己的计划、安排、行程、习惯或打算（例：「我明天去骑车」「我每天上午读资讯」），没有请你设提醒、定闹钟、记日程、到点叫我、帮我创建任务等显式委托——这是闲聊或信息分享，用文字回应即可。
- 含时间词但只是描述生活节律或个人安排，而非委托你设提醒：如「我每天9点打卡」「明天下午2点我要喂猫」都是用户在陈述自己的事情，不使用本技能。
- 即时完成且无未来时间约定的请求（如「现在帮我写首诗」），当场交付即可。但若用户明确说明天/下周/每天/到点再做某事，属于未来委托，应使用本技能。
- 口头叮嘱或偏好（如「以后少吃零食」），且未要求落成一条可执行提醒。
- 无具体时间或频率的「下次叫我」等，在补全前——可先文字反问，不使用本技能。

### 1.3 默认策略

听不出用户是在明确要求你操作定时委托/任务表时，不使用本技能；宁可只聊天或反问「是否需要我帮你设一条定时任务」，也不要猜测性加载。

### 1.4 农历/节日/特殊日期

- 农历、节日、调休等须先用 `web_search` 对齐公历日期，再 `load_skill` 并调用日程工具；勿在未对齐公历前硬写 `run_at`/`dtstart`。
- 无法通过搜索获取的私人信息（如发工资日）须反问用户。
- 公历日期每年不固定的重复任务（如「每年端午节/母亲节」）：RRULE 只能表达固定规律（固定月日、固定星期等），无法表达每年公历日期变化的节日。按用户意图区分处理：
  - 用户要求**无限期每年重复**（「以后每年端午节都提醒我」）→ 无法穷举所有年份，须告知用户此类需求无法自动处理，建议每年手动创建。
  - 用户只提了**有限几个具体日期**（「今年端午和明年端午提醒我」）→ 先用 `web_search` 查出具体公历日期，再**各建一条 `once` 任务**，勿用一条 RRULE 硬套。

## 2. 数据模型

### 2.1 任务类型

仅两种 `task_kind`：

| 模式 | task_kind | 时间字段 |
|------|-----------|--------|
| 单次 | `once` | `run_at` 非空，紧凑格式 `YYYYMMDDTHHMMSS`；`rrule` 与 `dtstart` 传空串 `""` |
| 重复 | `rrule` | `rrule` 非空，仅限白名单字段，勿加 `RRULE:` 前缀；`run_at` 传 `""`；`dtstart` 必填，紧凑格式，含准确时分秒 |

### 2.2 字段规范

**create_task 必填字段**：`instruction`、`task_kind`、`title`、`run_at`、`rrule`、`dtstart`、`enabled`、`timezone`。`title` 须非空；`enabled` 新建一般 `true`。

**instruction**：只写到点时要执行的工作本身（做什么、产出什么、风格/约束）——可以是提醒用户、生成图文/文案、整理并输出、下次对话接着做某事等；不要把时间、日期、周期、频率写进 instruction（这些由时间字段承载）。句子宜短，去掉寒暄与重复的时间描述。

**title**（短标题，与 instruction 分工）：
- 重复任务：周期长的用周期简称——「每月 3 号」类→突出「每月」；「每年固定某日」→「年度」；公历节日→「XX节」。每日可结合时段压缩——「每天晚上」→「每晚」（偏工作/习惯）或「每夜」（偏休息/睡眠）；「每天下午」→「下午」「午后」等。
- 单次任务：若日期有特殊含义可点出——如「XX 生日」「XX 节」。
- 命名顺序（能简则简）：场景/领域 → 对象 → 产出类型（如：电商、某刊、分析报告、插画、周报）；除「提醒」外，生图/写作/交付类可用「生成」「出图」「周报」等后缀。例：用户说每晚 8 点提醒打开 Keep → 标题可写「每日 Keep 提醒」；用户说明天中午同风格再出一张图 → 标题可写「次日午间插画生成」等。

**run_at / dtstart 格式**：统一使用紧凑格式 `YYYYMMDDTHHMMSS`，示例：`20260514T080000`。不要写带分隔符的 ISO 8601（如 `2025-09-03T07:00:00`）或带时区偏移的 RFC3339（如 `2025-09-03T07:00:00+08:00`）。时区信息由独立的 `timezone` 字段承载。

**timezone**（必填）：IANA 时区名，如 `Asia/Shanghai`、`America/Los_Angeles`，默认 `Asia/Shanghai`。时区信息由此独立字段承载，不要在 `run_at`/`dtstart` 中嵌入时区偏移（`+08:00` 或 `Z`）。

**dtstart 起始日规则**（重复任务的 `dtstart` 表示首次触发时刻）：
- 当天触发时刻尚未过（相对当前场景时间）→ `dtstart` 设为今天。
- 当天触发时刻已过 → `dtstart` 设为下一个满足 RRULE 的日期。
- 用户若明确说了「从明天/从下周一开始」则按用户指定日期，不套本规则。

### 2.3 RRULE 格式

- 段之间用 `;` 连接；键名大写。不带 `RRULE:` 前缀。
- **白名单字段**（只允许以下 7 个）：`FREQ`、`INTERVAL`、`COUNT`、`UNTIL`、`BYMONTH`、`BYMONTHDAY`、`BYDAY`。超出白名单的一律不生成。
- `FREQ` 只允许 `DAILY`/`WEEKLY`/`MONTHLY`/`YEARLY`。`FREQ=HOURLY`/`MINUTELY`/`SECONDLY` 一律拒绝。
- `BYDAY` 仅用字母缩写 `MO`/`TU`/`WE`/`TH`/`FR`/`SA`/`SU`，可多值逗号分隔。**禁用数字前缀**（`1MO`、`-1FR` 等都不行，后端无法表达「第 N 个周几」）。
- `INTERVAL=N` 表示每 N 个周期，正整数 ≥ 1。
- `BYMONTH`：1-12，可多值。`BYMONTHDAY`：1-31，可多值。
- 结束用 `COUNT` 或 `UNTIL`，**二选一**，禁止同时出现。
- `UNTIL` 格式：紧凑格式 `YYYYMMDDTHHMMSS`，不带 `Z`，由 `timezone` 字段解释。用户只说截止到哪天的，写成 `UNTIL=YYYYMMDDT235959`。例如用户说「截止到9月10日」，应写 `UNTIL=20250910T235959`。向用户回复时直接说「截止到9月10日」即可。
- **严禁出现的字段**：`BYHOUR`、`BYMINUTE`、`BYSECOND`、`WKST`、`BYSETPOS`、`BYWEEKNO`、`BYYEARDAY`。时分秒信息全部由 `dtstart` 承载，不走 RRULE。
- **单条任务每天只触发一次**。每条任务的触发时刻由 `dtstart` 中的时分秒决定，不能通过 RRULE 让同一条任务在一天内多次触发。凡表达「按固定间隔在一天内循环」的意图（「每小时」「每2小时」「每30分钟」「每天整点」等），一律婉拒并说明限制。
- **一天多次需求的处理**：当用户需要一天执行多次（如「早8点、中午12点、晚8点各吃一次药」），**不能**用一条 RRULE 表达，须**拆分为多条独立任务**，每条任务各自有独立的 `dtstart`（含不同的时分秒）和相同的 `rrule`（如均为 `FREQ=DAILY`），逐条调用 `create_task`。只说次数未说时刻的（如「一天三次」）须反问具体时刻。

## 3. 时间推断

任何需要用到当前时间的场景，须先用 `bash` 执行 `TZ='CST-8' date '+%a %b %e %H:%M:%S %Z %Y'` 获取当前系统时间，不要用裸 `date`。

总原则：能通过合理默认值补全的 → 直接调用 + 回复中告知所用默认值；无法合理推断的 → 反问。创建前须补齐三维度：做什么 / 什么时候 / 一次还是重复；三维度不全时不得创建。

### 3.1 精确钟点 → 直接创建

「早八点」「晚上七点半」「15:30」「30 分钟后」等能落到唯一 HH:MM → 直接建任务。

### 3.2 模糊时段 → 默认映射 + 告知

带时段限定词但没给精确钟点 → 按以下映射建任务，回复必须告知默认值，并向用户确认是否需要修改：

| 模糊表达 | 默认映射 |
|---------|---------|
| 早上/早晨 | 08:00 |
| 上午 | 09:00 |
| 中午 | 12:00 |
| 下午 | 14:00 |
| 傍晚 | 18:00 |
| 晚上 | 21:00 |
| 深夜 | 23:00 |
| 凌晨 | 次日 02:00 |
| 睡前 | 22:00 |
| 一会儿 | 当前时间 + 10分钟 |

### 3.3 歧义钟点 → 推断或反问

用户只说了整点但未指明上午/下午（「三点」「四点」「八点」等）→ 推断后如能唯一确定则直接建任务，并向用户确认是否需要修改；否则必须反问。

### 3.4 缺失维度 → 必须反问

日期/频率不完整或缺钟点时，禁止自行假设，必须反问：

- 缺钟点（「明天」「每天」「每周」「每月 1 号」）→ 反问几点。
- 无任何钟点或时段词的一律先澄清再建。
- 以下表达不指向具体一天，须反问对应维度后才能建任务：

| 模糊表达 | 须反问 |
|---------|--------|
| 每周 | 周几？ |
| 每月 | 几号？ |
| 每年 | 几月几号？ |
| 下周 | 下周几？ |
| 下月 | 下月几号？ |
| 明年 / 下年 | 几月几号？ |
| 周末 | 周六还是周日？还是两天都要？ |
| 下周工作日 | 周一到周五哪天？还是每天都要？ |
| 年末 / 月末 | 具体哪天？（12月31日？当月最后一天？） |

重复任务若还缺周几/几号等维度，一并追问。

### 3.5 过去时刻 → 必须澄清

以系统给出的当前时间为准。用户说的日期和钟点解析出来后，若整段提醒时间已早于此刻，则必须先和用户确认真实意图：先一句话点明「按当前时间算，这个点已经过去了」，再问是要改到未来哪一天哪一刻、还是指明年/下一次、或口误。确认后再调用工具。禁止静默落成单次过去时刻。包含但不限于：

- 同一天里已过的钟点（例：现在 21:00，用户要「今天早上 8 点提醒」）。
- 今年里已过的月日（例：现在 9 月 1 日，只说「8 月 21 日」且按今年理解已过去）。
- 明显荒诞或久远的历史年份（例：1955 年）当未来提醒用。

## 4. 操作流程

`load_skill(skill_name="task_schedule")` 须在已满足 §1 判据后执行；本地日程增删改（含暂停/恢复/删除/更新）禁止为此去 `web_search`，应直接调用日程工具。

### 4.1 创建

1. 判类型：仅一次 → `once`；有重复周期 → `rrule`。
2. 补齐三维度：时区、到分钟的具体钟点、到点要做什么（按 §3 推断或反问）。
3. **一天多次判定**：若用户需求在同一天有多个不同触发时刻，须拆分为多条独立任务，逐条调用 `create_task`。每条共享相同的 `rrule`（如 `FREQ=DAILY`）、`timezone`、`instruction`，仅 `dtstart` 的时分秒不同。向用户回复时统一说明已创建几条任务及各自触发时刻。
4. 调用 `create_task`。

### 4.2 查看

需要浏览现状时调用 `list_tasks`。

### 4.3 更新

用户要修改已有任务时，必须使用 `update_task`，避免用「先 `delete_task` 再 `create_task`」的方式代替更新。

`update_task` 只需传 `task_id` 和需要修改的字段，未传的字段自动保留原值。禁止顺带润色、缩写或修改用户未要求变更的字段。按意图区分：

- **仅暂停或恢复**：只传 `enabled`（`false` 暂停，`true` 恢复）。
- **改调度**：传时间相关字段（`run_at`、`rrule`、`dtstart`、`timezone`、`task_kind`）。如果时间变化导致语境明显改变（如从晚上改到中午，原 instruction 中「晚餐」应调整为「午餐」），应联动传入 `title`/`instruction`；否则不传。
- **改内容**：传 `title`/`instruction`（及必要时 `task_kind` 与时间字段）。
- **类型切换**（once↔rrule）：缺时间信息须补全或反问。

### 4.4 删除

- **默认删除**：「不要了」「不用了」「停了」「关掉」「取消」「算了」等 → 一律 `delete_task`。
- **仅当用户明确说暂停**（「暂停」「先停一下但别删」「先不触发但保留」）→ 走 §4.3 暂停流程。
- 批量删除须先向用户确认。

### 4.5 任务定位与 task_id

操作前须唯一锁定目标任务。`task_id` 的获取与使用规则：

- **已知即复用**：当前对话中工具返回结果里已有目标任务的 `task_id`（如刚 `create_task` 返回的、或前几轮 `list_tasks`/`update_task` 返回的），且用户所指就是该条（含「刚建的」「上一个任务」等）→ 直接用于工具参数，**禁止**仅为获取 `task_id` 而重复调用 `list_tasks`。
- **按描述匹配**：能通过用户描述与 `list_tasks` 结果中的 `title`/`instruction` 唯一对应 → 使用对应 `task_id`。
- **多条匹配**：用标题（及必要时 instruction 摘要或时间）列出候选，请用户选择。
- **无匹配**：告知未找到，可用标题列表简述已有任务，供用户改口。
- **用户记错名字**：模糊匹配最接近的，用自然语言确认「是不是指某某标题那条」后再操作。
- 取消/删除/暂停/恢复某条提醒：禁止 `web_search`，话里出现业务名词也只是任务名，不要上网搜。

## 5. 交互规范

### 5.1 task_id 不得暴露

对用户回复与反问中一律不得出现 `task_id`；`task_id` 仅作为工具调用参数在内部使用，禁止向用户展示或索要。

### 5.2 创建/操作后的回复

- 创建成功后只复述标题与时间/规则摘要。
- 暂停后须明确告知用户：暂停后不会自动恢复，需手动恢复。

### 5.3 不得拒绝落表

用户已明确委托「某时做某事」时，不要以能力限制、安全风险等任何等理由拒绝落表。应通过 `create_task`（或更新）把委托写入系统，并如实说明：任务已保存、到点将按 `instruction` 指挥调度系统执行；

三类典型错误必须避免：

1. **不得当场执行代替定时任务**：用户说「下周二帮我写作文」→ 应创建 `instruction` 为「写一篇…作文」的定时任务，而非当场写一篇作文交给用户。
2. **不得降级为提醒**：`instruction` 将用于指导系统调度执行，应写用户要求的具体工作（「播放音乐」「打开空调制冷24度」「搜索并推送财经报道」），而非降级为「提醒用户自己去做」。区分标准：「到点帮我播放」→ instruction 写「播放…」；「到点提醒我播放」→ instruction 写「提醒播放…」。用户没说「提醒我」时，不要自行降级为提醒。
3. **不因任何原因拒绝**：定时任务到点后由系统调度执行，你的职责是落表而非关注任务执行方式。用户说「明天帮我登录邮箱」→ 应创建 `instruction` 为「登录邮箱」的任务；不得以任何原因为由拒绝创建。

### 5.4 语言与确认

中文交流为主，关键时间与规则应与用户对齐或确认。RRULE 无把握时多问一句。
