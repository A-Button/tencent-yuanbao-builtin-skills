# 规划住哪里

规划的产出是有事实支持的若干居住方案及其取舍，由用户选择后再缩小找房范围。后端没有第二个规划模型；你使用库存、地点和路线工具组织方案。

## 建立规划问题

确认城市、租赁方式、预算或预算弹性、居室、通勤目的地。多人目的地分别记录方式与上限。缺少影响选址的必要信息时优先问一个最关键问题；已经明确的条件保留。预算未知可以展示真实价位帮助确定，但不要默默填入预算。

按 [通勤](commute.md) 解析并确认各目的地。用户明确要求某个范围时保留为硬边界；“优先”“最好”作为偏好，不伪装为硬筛选。

## 取得候选片区

调用 `get_area_inventory`，传当前城市、租赁方式、预算和支持的居室。返回每片区库存和起止价格，以及有限的聚合覆盖范围；这是候选来源，不是自动生成的最优方案。

结合用户范围与返回库存挑选约 3–5 个差异化片区：价格有优势、选择较多、位置有潜力等。位置潜力只作为待测假设。必要时增加一批候选，而不是把首批没命中说成全城无解。

对于候选片区：用 `resolve_locations(purpose=area)` 取得可搜索范围；再用 `purpose=destination` 查片区内可明确定位的地铁站或地标作为代表点。地图候选歧义时请用户确认，或换成无歧义代表点。明确说出代表点及其代表范围；不能静默用第一个相似 POI 代表整个商圈。

## 比较方案

使用 `calculate_routes`，以代表点为 origins，对全部工作地点计算 routes。每个目的地使用自己的方式和上限。

给出一张紧凑比较表：片区/代表点、各人通勤、最长通勤、库存与起租价、预算/时长差异。库存和价格来自聚合；时长来自路线；缺失值显示未知。片区起租价不是每套房源价格，代表点通勤不代表整个片区。

在已测候选内推荐 2–3 个有不同取舍的方案。例如“最长通勤较短”“预算更宽裕”“可选房源更多”。用户没有指定权重时解释取舍，不暗设百分比权重，也不宣称唯一最优。所有方案都超限时明确列差异，询问愿意调整的维度，保留原约束。

## 从规划进入找房

用户选定片区后，按完整条件调用 `search_houses`。单目的地可同时传 commute；多人需求对实际返回房源再调用批量路线核验。只有具体房源的事实和路线都核对后，才给“这套满足”的结论。

交付完成标准：说明已比较哪些候选、每个方案的依据、未核验项，以及下一步要搜索的片区或需要用户决定的取舍。规划阶段不必强行出房源，也不能在用户只是咨询选址时偷偷改成另一个找房任务。
