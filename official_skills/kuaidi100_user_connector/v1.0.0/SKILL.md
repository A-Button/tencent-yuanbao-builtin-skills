# 快递100个人服务

## 运行边界

- 仅在当前 Agent 已发现下方快递100 MCP Tool时使用；Skill不负责注册MCP服务。
- 简单请求直接调用对应的单个Tool；查看全部地址簿时需查询寄件和收件两类并合并去重；完整寄件请求才执行多步寄件流程。
- 禁止执行 Python、CLI、Shell、本地脚本或本地缓存命令。
- OAuth、Token保存和请求头注入由宿主平台的MCP连接管理能力负责；不得在对话或Tool参数中索取、展示或传递 API Key、Token、`userId`、`openId`。
- 未发现所需Tool时，明确说明当前环境尚未接入快递100 MCP，并引导用户在当前平台完成服务连接；不得臆造调用结果。
- Tool返回未认证或凭证过期时，提示用户在当前平台重新认证或重新连接快递100 MCP；Skill不自行发起OAuth。
- 本Skill展示Tool返回的小程序预填订单页链接 `url` 和跳转二维码图片地址 `qrCode`。二维码承载同一个小程序链接；不直接向快递公司提交最终订单或完成支付。

## 输入要求

- 查询历史订单：50条是默认明细展示上限，不是接口查询上限。未限定查询范围时显式传`limit=200`，先统计状态，再展示订单明细；默认包含已取消订单，不按状态自动排除。结果≤50条时全部展示，>50条时只展示前50条。用户明确指定数量、范围或状态时遵循其要求。用户身份只能来自MCP认证上下文，不接受用户提供Token、`userId`或`openId`。
- 查询地址簿：`addressType`只能为`receiver`或`sender`；用户只给出联系人姓名时，将姓名作为`keyword`搜索。
- 修改默认寄件人：目标必须来自本轮寄件地址簿查询，且只有用户确认脱敏后的目标地址后才能传递`confirmed=true`。
- 新增地址：必须先询问新增寄件地址还是收件地址；`sender`和`receiver`不得由Agent猜测。
- 修改/删除地址：目标必须来自本轮地址簿查询；修改不改变地址分类和默认状态，删除当前默认寄件地址前必须先设置另一条默认地址。
- 查询运费：调用前必须具备寄件城市、收件城市和大于0的重量，重量单位为公斤。
- 完整寄件：必须取得并确认寄件人、收件人、物品、`weightKg`和快递公司信息；快递编码与品牌标识必须来自本轮`list_shipping_options`结果。
- 预下单：只有用户明确确认最终汇总后才能传递`confirmed=true`，不得根据历史对话或默认值推断确认。

## 调用路由

- 查看最近寄件订单：调用`list_my_shipment_orders`，默认显式传`limit=200`，按“历史订单”规则先汇总状态，再展示所有状态的订单明细（含已取消）；明细≤50条全部展示，>50条默认只展示前50条。用户明确要求指定状态、数量或范围时按其要求处理。
- 咨询物品寄递知识或参考重量：优先调用`query_item_weight`，包括“这个物品能不能寄”“能空运吗”“怎么包装”“是否建议保价”“寄快递大约多重”。提取具体物品名称作为`itemName`；缺少名称时只追问物品，不要求订单、单号、地址或先发起寄件。
- 解析地址：直接调用`parse_address`。
- 查询运费或比较快递：先补齐寄件城市、收件城市和重量，再调用`list_shipping_options`。
- 完整寄件或生成下单链接：执行下方寄件流程，并在预下单前取得用户明确确认。
- 获取默认寄件人只调用`get_default_sender`，不得让用户提供身份标识或Token。
- 查看全部地址簿时，按下方“地址簿合并展示与计数”规则查询两类地址，以`id`去重后展示；同一公共地址只展示和计数一次。
- 用户说“寄给某人”但没有提供完整收件信息时，先调用`search_address_book`查询收件地址；不要立即要求重新输入。
- 用户要求修改默认寄件人时，先查询`addressType=sender`的地址簿，完成候选选择和确认后再调用`set_default_sender`。
- 用户要求按单号查询物流时，直接调用`aiserviceapiquery4agent_get`；遇到需要手机号验证的快递再询问手机号或后四位。
- 用户要求新增、修改或删除地址时，按[寄件工作流](references/workflow.md)中的地址簿管理规则操作。

## 脱敏格式

手机号等需要打码的字段，星号必须写成转义形式，否则会被 Markdown 当成强调语法吃掉。

- **手机号固定写成前3位 + 4个转义星号 + 后4位**，即在正文里逐字输出 `188\*\*\*\*8888`，渲染后用户看到的才是 `188****8888`。
- **不要输出未转义的 `188****8888`**。未转义的连续星号会被解析成加粗或斜体标记，用户看到的是 `1888888`、半截粗体或残缺号码——既没达到脱敏效果，又把真实数字露了出来。
- 固定电话、身份证号、详细门牌等其他需要打码的字段，凡用到星号都按同一规则转义。
- 本规则只约束展示形态。传给 Tool 的参数一律用真实值，不得把带星号或带反斜杠的脱敏串当成参数传出去。

## 地址簿合并展示与计数

- 用户查看“我的地址簿有哪些地址”或“全部地址”时，分别调用`search_address_book`查询`addressType=sender`和`addressType=receiver`，两次使用相同的关键字（未指定则省略）和`limit=20`；只问寄件或收件地址时，仅查对应类型。
- 合并本轮两类成功结果时，以有效地址记录`id`去重。同一ID的数字和等值字符串形式视为同一记录，只展示、计数一次；不同ID即使姓名、手机号或地址文本相同，也不得合并，尤其不能根据脱敏文本判断重复。ID缺失时不得猜测合并或宣称精确去重总数。
- 默认展示一张去重后的地址表，使用连续编号并增加“用途”列。同一公共地址只列一行，标注“寄收通用”；保留服务端原始`tag`，不改写分类。如需分组，使用互不重叠的“寄件专用、收件专用、寄收通用”，不在寄件和收件两组重复列出同一ID。
- 数量按两类结果的有效ID并集计算，不能直接相加。例如寄件5条、收件5条，其中1条ID相同，则说“本次查询去重后共9条地址，其中1条寄收通用”；若分组，则为4条寄件专用、4条收件专用、1条寄收通用。可以分别说明“可用于寄件5条、收件5条”，但必须说明两者包含同一条通用地址，不能把它们加成10条。
- 数量默认表述为“本次查询去重后共N条”，不把受`limit`限制的结果当成整个地址簿的精确总数。任一查询达到上限时，说明可能还有未展示记录；一类查询失败时说明只展示成功查询的部分，不把失败当作空列表。同一ID返回的内容或分类冲突时，先重新查询核实，不拼接出未经确认的新记录。
- 用户按编号选中地址后，映射回原始`id`；同一公共地址的修改或删除只操作一次，不因它在两类结果中都出现而重复调用。继续遵守原有写操作确认及其他业务规则。

## 物品寄递知识

- `query_item_weight`提供物品库匹配信息，可独立咨询；按[字段映射](references/fields.md)读取运输规则、包装建议、重量及匹配来源。
- 默认先查本工具；工具不可用、返回未匹配或相关字段未覆盖问题时，可以用可用的web search补充，区分接口结果和网页信息。用户明确要求联网搜索时遵循用户要求；不要把无关的新闻、通用知识问题路由到本工具。
- `matchSource`/`match_source`为`DEFAULT`表示没有匹配到物品，不能据此认定可寄或推断重量。兼容旧服务：即使同时返回“1.0公斤、可寄递”，也不能把它们当成已核实的数据。
- 已匹配物品的重量可能为空；保留并回答已有规则和包装建议，不要求用户为单纯的知识咨询提供重量。只有继续查价或预下单时，才询问实际重量或请用户确认有效参考重量。
- 模糊匹配或品类聚合的结果只代表匹配物品或品类的参考信息；不匹配用户物品或规格时先澄清。匹配来源缺失不等于精确匹配，规则和建议为空也不等于没有限制。
- 按实际返回的运输方式、限制等级和条件说明回答；某一运输方式禁运不等于全部禁运，有条件收寄不等于无条件可寄。没有公司、地区或时效依据时，不承诺特定快递公司必定承运或规则实时有效。
- 仅根据返回的包装、保价建议回答，不扩展为保价金额、赔付规则或保险承诺。

## 寄件流程

1. 调用`get_default_sender`获取寄件人。成功时展示脱敏信息并让用户确认；失败或无数据时，分步询问姓名、手机号和完整地址。
2. 用户指定收件人姓名时，先调用`search_address_book`并传`addressType=receiver`。唯一匹配时展示脱敏信息并确认；同名多条时让用户选择；无匹配时再分步询问手机号和完整地址。
3. 需要结构化地址时调用`parse_address`。解析失败时请用户补充或修正地址。
4. 询问物品名称，调用`query_item_weight`获取物品信息并按上方规则判断匹配来源和寄递限制；重量缺失或为默认兜底时询问实际重量，否则让用户确认或修改参考重量。未知限制不得表述为可寄，明确禁寄物不得继续查价或预下单。
5. 调用`list_shipping_options`，按价格和时效清晰展示候选项。用户未表达选择时不得默认取第一项；用户明确说“最便宜”或“最快”时可按该条件选择。
6. 按[字段映射](references/fields.md)组装预下单参数，用表格形式逐项汇总寄件人、收件人、物品、重量、快递公司、预估价格、备注和上门时间。
7. 只有用户明确确认汇总信息后，才调用`prepare_shipment_order`并传递`confirmed=true`。
8. 成功后读取 `structuredContent.url` 和 `structuredContent.qrCode`，在主对话中展示“去小程序确认并支付”文字链接和内嵌二维码图片，禁止输出裸链接。不默认附加“打开二维码”入口，不主动新建网页、浏览器标签页或侧边预览。按[链接与二维码](references/link-and-qrcode.md)处理文本响应兼容、链接渲染和图片加载失败；不得自行编造或改写返回地址。用户仍需在小程序内确认最终订单、价格并支付。

仅在执行完整寄件或需要处理复杂分支时，读取[寄件工作流](references/workflow.md)；字段组装时读取[字段映射](references/fields.md)。

## 历史订单

- 用户要求查看最近寄件订单时直接调用`list_my_shipment_orders`，不必先执行完整寄件流程。默认显式传`limit=200`获取接口允许范围内的最近订单；默认明细展示上限N=50。查询条数与展示条数分开处理，不能为了只展示50条就只查询50条。用户明确限定查询最近N条原始订单时按该范围查询；只限定希望展示的条数时，仍在可查询范围内获取后按指定上限展示。参数范围1～200，超过接口能力的要求需说明限制，不臆造分页参数。
- 仅展示Tool返回的当前登录用户订单，不接受用户身份参数，也不尝试查询其他账号。
- 先检查JSON-RPC错误、`isError`和业务`success`；失败时说明查询失败，不把失败当作无订单。成功时优先读取`structuredContent.orders`、`count`、`total`；若宿主仅提供文本结果，解析同一次响应中的JSON，不混用历史结果。
- **先做状态汇总，再展示明细**：依据订单状态`statusCode/statusName`对本次查询的订单去重后分组统计，每笔订单只计入一个订单状态。默认明细包含所有状态，已取消订单与其他订单一样参与展示，不自动隐藏或跳过。物流状态和支付状态不能混入订单状态分组重复计数；未知或缺失订单状态如实标注，不据此删除记录。
- 仅当用户明确要求指定状态时才按其要求筛选，例如“只看已取消订单”或“排除已取消订单”；普通“查看订单/历史订单/全部订单”均保留已取消明细。这只是查询结果展示，不调用取消、删除等写操作。
- **明细展示上限**：基于本次成功响应，按有效`orderId`去重，默认不做状态过滤，保持服务端返回顺序；只有用户明确指定状态时才筛选。可展示记录数M≤N时全部展示，不额外缩减；M>N时只展示前N条，默认N=50，并说明“可展示M条，本次展示前50条，其余M−50条暂未展开”。状态统计在明细截取前计算，不能只统计已展示的前50条。用户要求继续展示时复用本次结果中的剩余记录。接口没有offset或cursor，不虚构分页，不反复调用相同查询试图获得更多订单。
- **订单状态必须展示**：主表固定保留“订单状态”列，优先展示`statusName`，`statusCode`也必须在该列括号内或逐单详情中展示。只有状态码时写“状态码：原值（暂无状态说明）”，不得猜测其含义；两者均缺失时写“未返回”。`statusCode/statusName`取自上游订单状态`tabId/tabIdName`（名称兼容`tabName`）；`logisticsStatusCode/logisticsStatusName`是独立的物流运输状态，`paymentStatus`是支付状态，两者均不能替代订单状态。订单为“已取消”但物流为`UNKNOWN/未知`时，订单状态列必须显示“已取消”，物流“未知”只放在物流状态详情中；已取消订单与其他状态一样按返回顺序和展示上限处理，不自动过滤。也不能仅凭运单号推断已揽收、运输中或已签收。
- 默认使用订单汇总表，列出“订单号、运单号、快递公司、订单状态、创建时间、寄件城市、收件城市、费用”；随后按订单号补充逐单字段详情。也可逐单用“字段—值”表展示，但不能为了表格简短而省略接口已返回的业务字段。
- 对按上述规则选入本次展示范围的每条订单，按下表逐项核对，已返回的字段必须展示；主表未容纳的字段放入对应订单详情。手机号继续脱敏；其他字段的`0`或`false`属于有效值，不得当作空值丢弃。缺失、null或空字符串显示“未返回”，不补造数据。

| `paymentStatus` | 支付状态；接口只返回编码且没有已确认映射时，展示原始编码，不猜测已付/未付 |
| `orderType` | 快递业务/渠道类型；不是订单状态，没有已确认映射时展示原始值 |

- 查询成功时按“查询概况 → 按订单状态统计 → 订单明细”组织回答。count是本次接口返回数，total是接口报告的总数（包括取消订单），不要与实际展示条数混淆；状态统计与时间跨度仅覆盖实际返回的数据。未取全时写“本次查询返回X条，接口报告总数Y条，以下统计基于本次返回结果”，不能宣称所有历史订单均已统计。示例：本次完整返回45条，其中待接单6条、待支付2条、已取消37条，则汇总这三个数量，45条未超过默认展示上限50，因此按返回顺序一次展示全部45条（含已取消记录）；不能只挑出8条非取消订单。若有65条订单，则默认展示前50条，说明其余15条暂未展开；若只有8条，则全部展示8条，不区分是否已取消。`orders=[]`时说明本次没有返回订单；全部为已取消时仍正常统计及展示，不能说没有可展示订单。
- 接口后续新增的用户可见业务字段也应在逐单详情中保留；继续遵守原有隐私规则，不展示Token、内部用户标识等敏感信息，不以“展示完全”为由输出原始鉴权信息。
- 历史订单列表流程只返回列表；用户另行提供单号并要求查物流时，才进入物流查询流程。取消订单和售后仍不支持。

## 物流查询

- 根据单号查询物流直接调用`aiserviceapiquery4agent_get`，`kuaidiNum`必填。
- `phone`和`comName`仅在用户已提供或查询结果明确要求时传递，不得猜测。
- 仅根据Tool真实结果回答；未查询到时不得编造轨迹、状态或预计送达时间。
- 物流轨迹必须整理成Markdown表格，至少包含“时间”和“物流轨迹”两列；即使Tool返回自然语言或Markdown，也按真实记录整理，不直接贴原始长文本。没有轨迹时如实说明，不编造表格行。

## 停止条件

遇到以下任一情况必须停止当前流程，不得继续调用`prepare_shipment_order`：

- 当前环境未发现所需MCP Tool，或MCP初始化、Tool发现失败。
- OAuth未认证、Token已过期，或当前授权权限不足。
- 用户拒绝提供必要寄收件信息，或地址在追问后仍不完整。
- 重量缺失、不是数字或小于等于0。
- 没有可用快递方案，或用户没有明确选择快递公司。
- 用户未明确确认最终寄件信息，或要求继续修改。
- 修改默认寄件人时没有先查询寄件地址簿、候选不唯一，或用户未明确确认目标地址。
- 新增地址时分类未确认，或者地址新增、修改、删除尚未获得用户明确确认。
- Tool返回`isError=true`、调用超时、网络中断或结果未知。
- 用户点名的快递公司不在本轮 `list_shipping_options` 结果里。此时必须停下来，如实说明当前寄收城市和重量下没有这家，列出实际返回的候选让用户重选；不得改用名称相近的一家，不得自行构造`companySign`，不得继续预下单。

预下单属于写操作。失败、超时或结果未知时不得自动重复调用，避免生成重复预订单。

## 最终输出要求

- 查询类Tool：仅根据Tool真实返回结果回答；无数据时如实说明，不补造订单、价格或寄件信息。
- 物流轨迹：必须用表格输出，至少包含“时间”和“物流轨迹”两列；简短状态摘要可以放在表格前，但不能用段落或列表替代表格。无数据或查询失败时只说明实际情况，不生成虚构轨迹。
- 查价Tool：展示快递名称、预估价格和时效，并等待用户明确选择。
- 预下单 Tool

优先读取成功结果中的：
- `structuredContent.url`
- `structuredContent.qrCode`
必须明确告知用户有以下两种确认并下单方式，任选其中一种即可：

1. 点击“点击去小程序确认并支付”，直接跳转至快递100小程序；
2. 使用微信扫描正文中展示的二维码，进入快递100小程序。电脑端优先推荐扫码下单。

#### 小程序支付入口

- 必须使用 [点击去小程序确认并支付]({url}) 渲染，禁止仅输出纯文本；支付入口的可见文字必须固定为“点击去小程序确认并支付”，真实地址必须且仅能放在链接目标中，旧版字符串结果也必须遵守。

#### 二维码图片

当 `structuredContent.qrCode` 为有效、非空的 HTTP(S) 图片地址时，必须原样使用该地址输出二维码图片：

<media_info>[{"type":"image","description":"快递100小程序确认下单二维码","url":"{qrCode}"}]</media_info>

二维码图片标签必须紧跟在扫码说明之后，不得集中放到回复末尾。

每个标签的 JSON 数组中只放当前二维码这一张图片。

`qrCode` 必须取自本次预下单 Tool 的真实返回结果，不得改写、截断、拼接或自行构造，不得使用搜索结果、历史结果或模型记忆补充。

不得同时把 `qrCode` 输出为裸链接、Markdown 图片或“点击打开二维码”链接。

仅有旧版字符串结果时：

- 能准确提取真实二维码地址，且地址为有效 HTTP(S) URL时，按上述 `<media_info>` 格式展示；
- 无法准确提取时，不生成二维码图片，不臆造缺失字段。

二维码地址为空、格式无效、无法展示或图片加载失败时，如实说明：

当前二维码暂时无法展示，请点击“点击去小程序确认并支付”进入快递100小程序完成操作。

同时保留“点击去小程序确认并支付”链接，不自动打开新页面，不调用浏览器、网页或侧边预览工具，不自动再次调用预下单 Tool，也不输出裸二维码地址。

二维码成功显示不代表微信已成功识别或跳转，更不代表订单已经提交或支付完成。
- 必须说明用户仍需进入快递100小程序确认最终订单、价格并完成支付；不得表述为已正式下单或已支付。
- 不展示完整Token、完整手机号、完整敏感地址或内部用户标识。

## 关键规则

- 收件人信息可以来自当前用户地址簿或由用户提供，但使用前都必须确认；同名多条时不得自动选择。
- `set_default_sender`属于写操作，超时或结果未知时不得自动重试。
- 地址新增、修改和删除都是写操作，超时或结果未知时不得自动重试。
- 快递公司必须由用户选择，或由用户明确给出“最便宜/最快”等选择条件。
- 物品类型和最终下单确认不可跳过。
- `prepare_shipment_order`失败时不得表述为成功，也不得自动重复提交。
- Tool返回401时提示重新认证；403时提示当前授权权限不足；400时补充或修正参数；404时说明目标数据不存在；429时提示稍后重试；超时或500时说明服务暂不可用。默认寄件人或地址为空时采用人工输入，订单列表为空时如实说明暂无订单。
- 不在日志、回答或Tool参数中回显手机号全号、完整Token及其他敏感凭证。
