# 产物渲染规则

本文件只决定“用什么形式呈现”。使用前应已有 `planning-core.md` 形成的标准计划数据，并叠加当前目标所需领域规则中的核心内容和本题适用的条件内容。

## 1. 选择顺序

1. 用户提到具体文件形态时，在当前能力支持范围内按他提到的交付。除了直接写格式名（HTML、PPTX、XLSX、DOCX、PDF、纯聊天），自然说法同样算数：「表格 / 计划表 / Excel」按XLSX，「PPT / 汇报 / 演示 / 家长会 / 给家人讲」按PPTX，「文档 / Word」按DOCX，「网页」按HTML。
2. 用户完全没提文件形态时，先判断是完整计划还是轻量安排：
  - **完整计划**：目标需要跨多个时间点执行，存在先后顺序、任务量、完成标准或后续检查，交付聊天计划卡、HTML阅读版和XLSX执行版。两份文件都要写出再回复，不要只交其中一份再问要不要另一份；
  - **轻量安排**：只解决当前或一次性的小安排，不需要后续跟踪，默认只生成聊天计划卡。
3. 用户明确要文件、完整计划或指定格式时，生成对应文件，不能按轻量安排只出聊天；确实无法生成时按 `SKILL.md`「完成条件」处理。
4. PDF不作为默认执行载体。用户明确要求PDF且当前能力支持时，生成或导出PDF；能力确实不可用时，说明限制并协商改用DOCX或HTML。
5. 不因格式变化删除计划的必要内容。
6. 用户只指定一种格式时，该格式就是全部文件产物；用户指定多种格式时按要求生成，不额外增加未要求的默认文件。指定了 PPT / 家长会 / 汇报时，展示版就是 PPTX，不要用 HTML 顶替，也不要把默认 HTML 一并交上。
7. 用户表达了打印、分享、汇报、演示或网页浏览等明确消费需求但未指定格式时，选择合适的DOCX、PPTX、HTML或PDF；只是判断“可能有帮助”时不自动增加文件，只在Answer中提供弱入口。

用户指定的格式明显不适合时，仍优先满足，并调整排版。例如用PPTX呈现长计划时，将完整任务放在附录页，不删除任务字段。

本轮所有文件必须来自同一份标准计划数据：执行版承担执行和自行记录，阅读版承担理解、打印、分享或汇报。内容可以重合，但不得分别规划。阶段切分只做一次，先写入执行主产物；切换格式时只改呈现，不重切阶段、不改日期。

## 2. 主产物必须保留的内容

完整计划以一个执行主产物为准：没有文件时主产物是聊天计划卡；有文件时执行版是主产物（默认XLSX），阅读版是补充；用户指定其他格式时，以指定文件为主。聊天只提供计划卡和使用入口。所有文件从同一份标准计划数据渲染。执行主产物至少覆盖：

- 目标、期限、完成标准、约束和假设；
- 可行性判断、关键差距和优先级；
- 适合任务复杂度的时间/进展结构、重点和通过标准；
- 可执行任务的做什么、做多少、耗时和完成标准；
- 执行缓冲、时间或状态不足时的最小方案；
- 可观察信号、检查时点、调整动作和重新制定条件；
- 命中领域文件规定的核心内容，以及本题触发的条件内容。

“快速启动”只在聊天计划卡中呈现，作为帮助用户低门槛开始行动的入口，不写入文件，也不创建“快速启动”工作表。

领域规则与本文件冲突时：

- **内容是否必须出现**：以领域规则为准；
- **内容如何排版和使用哪种文件**：以本文件和用户要求为准。



## 3. 聊天计划卡



### 3.1 固定内容

聊天计划卡始终让用户快速知道五件事：

1. 目标、期限和最重要的约束；
2. 目标是否可行，以及最关键的取舍；
3. 计划的时间/进展主线；
4. 下一个可用时段可以开始的第一步；
5. 有文件时，文件是什么以及如何使用。



### 3.2 条件内容

出现对应情况时再补充：

- 使用了未确认信息：列出关键假设；
- 任务容易被现实波动打断：说明缓冲和最小方案；
- 依赖实时事实或外部标准：给出关键来源和日期；
- 定时任务有明确增量价值：提供弱入口或待确认清单。

没有文件时，聊天计划卡同时承载完整计划；可使用以下结构：

```markdown
## 计划判断
- 目标与期限：
- 可行性：
- 关键差距：
- 关键约束/假设：

## 计划路线
| 日期/阶段 | 重点 | 通过标准 |

## 先执行这些
| 日期/周次 | 优先级 | 任务 | 数量或输出 | 耗时 | 完成标准 |

## 现实变化时
- 缓冲：
- 最小方案：

## 检查与调整
- 在【时间】检查【信号】；若【条件】，则【调整动作】：

## 现在怎么开始
- 下一个可用时段先做：
```

有主文件时，聊天只展示计划判断、路线总览、快速启动和文件说明，不重复粘贴全部任务。标题和措辞可以根据场景调整；评判重点是信息是否存在且清楚，不要求机械套用模板。

## 4. 文件渲染



### 4.1 XLSX

XLSX 是完整计划在用户未指定格式时的默认执行载体：方便执行、修改、筛选和自行记录。用静态值一次写成。不要 `load_skill` 读取 `xlsx` Skill，不要写公式，不要跑重算或公式检查，不要插图表，不要套财务模型。

#### 怎么出表

只写一份 JSON，用一次 `write` 写完，然后运行本 Skill 自带的脚本（与 SKILL.md 同级的 `scripts` 目录）：

`python3 scripts/render_xlsx.py <数据.json> <中文计划名>.xlsx`

计划数据只手写这一份 JSON。不要另写 Python 来生成 JSON 或 HTML（包括 `gen_plan.py`、`build_plan.py`、`build_json.py`、`ielts_plan.py`、`gen_testdata.py`、`build_html.py`），也不要读或改 `render_xlsx.py`。JSON 语法错了或渲染报错，只 `edit` 这一份 JSON 再跑。表太大就按已读颗粒度缩小（按周不按日）。

JSON 顶层是 `sheets`。每张表有 `name` 和 `blocks`。`block.type`：

| type | 字段 | 用在 |
| --- | --- | --- |
| heading | `text` | 区块标题 |
| kv | `rows`：`[标签, 内容]` | 概览判断 |
| table | `headers` + `rows` | 执行、对照、练习卡、记录 |
| note | `text` | 整行说明 |

执行表必须是 `table`，表头有日期或周次（或日期范围），并且有数据行。整张只有 heading / kv / note 共用规则，不算做成执行表。列头按领域写，不要为过报告改成「动作」「数量或输出」：

| 领域 | 做什么 | 做多少 |
| --- | --- | --- |
| 学习备考 | 学习内容，或科目/模块 | 题量或产出 |
| 健身减脂 | 动作，或训练内容 | 组次，或时长 |
| 求职面试 | 任务，或投递动作 | 数量或产出（如 5 个岗位） |

怎样算完一律用 `完成标准`。适用时再加耗时、优先级。填写列 `状态`、`实际结果`、`反馈/问题` 整本至少出现在一张 `table` 里，格子留空，脚本会浅底标出。不要预填「未开始」「进行中」「完成」或「跳过」——这些是用户自己勾的，写进去算预填。标明「示例」的示范行可以带字，不算预填。字体、表头深底浅字、列宽由脚本写入。渲染成功后回包打 5 行结构报告，结构项只看这 5 行。报告只认「有没有带日期或周次的数据行」和填写列是否空着，不认列头必须叫哪个词。

#### 按用途写表

工作簿按内容组织，不固定工作表名称、数量或列数。打开后按用途找得到即可。列数、是否上下叠表、记录是否单独成张，按内容决定，不为凑结构开空页签。

信息要覆盖：目标与阶段判断、详细执行、用户可自行填写的跟踪、本题的领域内容。同一信息只维护一处。跟踪可以写在执行表旁的空列，也可以是单独的记录模板，不能整本消失。

两列「字段名 + 整段说明」从顶拉到底，或把阶段、动作挤进一个单元格，都不算做成表。


| 用途   | 要达成的目标                           | 怎样算做成了                                                                | 不要                                        |
| ---- | -------------------------------- | --------------------------------------------------------------------- | ----------------------------------------- |
| 概览   | 打开第一张就能建立整体：目标、约束、阶段怎么切、值不值得按这个做 | 分块清楚，阶段和判断分开看。标签列只放短名，完整句子在内容列。阶段可叠在本页，也可单独一张                         | 一张两列从顶拉到底；标签列写整句或两列写同一段；把阶段主线或一串动作塞进一个单元格 |
| 对照   | 横着比较之后能排序、能取舍                    | 行是对象（科目、岗位、方案），列是可并排看的维度（差距、重要度、时间、结论）                                | 用「项目 + 一整段」代替比较                           |
| 阅读   | 查原则、事实、处方、资料、降级规则                | 打开能查到，不必翻执行表拼                                                         | 大段说明糊成一列；把整套处方写进执行表的一个格子                  |
| 执行   | 按日或周扫清做什么、做多少、怎样算完               | 日期或周次分列；做什么、做多少、完成标准分列，列头按领域（学习用学习内容 + 题量或产出，健身用动作 + 组次）。同一天多件事多行，日期列可重复或合并。适用时加耗时、优先级、依赖和最小方案 | 用箭头或顿号把一串事堆进同一格；整张只有共用规则、没有按日或按周的 table；学习表套用「动作 / 数量或输出」 |
| 练习卡  | 抽出一行就能练                          | 每行自洽：题目、结构、可用证据、追问等按字段分列。列可以多                                         | 压成两列长文，或把完整题包贴进阅读版                        |
| 记录模板 | 能勾进度、记结果，或按表头往后加行                | 流水类（投递、错题、周测）用户可往下加行；核对类（材料、检查项）行先写好，用户勾状态。填写列空着、浅底标出。示范格式单独一行并标明「示例」 | 整页只有规则、没有可填的空行；把状态预填成「未开始」                |


记录模板里的填写列常用：`状态`（该行是否开始或完成）、`实际结果`（实际做了什么）、`反馈/问题`（执行中遇到的情况）。领域需要时加体重、围度等测量列。

不得替用户预填完成状态、实际结果或反馈，也不得暗示系统会自动读取、同步或更新这些记录。「未开始」也是预填，不是空着。

#### 工作表怎么拆

通常从下面三张起，再按内容量合并或增减。名称可以随场景改。


| 参考工作表  | 主要用途                       | 组织原则           |
| ------ | -------------------------- | -------------- |
| `计划概览` | 概览：看懂目标判断、阶段路线、重点和约束       | 精炼，不放完整逐项任务    |
| `执行计划` | 执行：详细行动、时间、耗时、完成标准；旁侧可留填写列 | 详细排期只在这一处维护    |
| 领域工作表  | 对照、阅读、练习卡或记录模板             | 只有内容足以独立使用时才增加 |


阶段路线可以放在`计划概览`里，也可以单独一张；无论放哪，都是一块能分开看的阶段表，不是塞进判断区的某一格。领域工作表已经带日期和详细行动时，直接当执行表，不再复制一张通用执行表。健身计划里，`训练安排`作执行表；力量日处方、动作要点放到阅读表。内容少时，执行表上方可写几行共用规则，不要把整套动作清单塞进组次格。共用规则不能替代排期：没有按日、按训练日或按周的 table，不算做成执行表。

只生成一个 XLSX。不增加第二套排期、`方案`列或只为凑结构的工作表。目标诊断只用来确定最终目标，不另建建议页签；用户坚持原目标时，问题和建议写在概览或判断区域。危险动作即使用户坚持也不进入详细执行安排。

相同详细信息只维护一处，其他位置最多摘要或引用。内容少就合并；用途不同、需要独立筛选或记录时再拆。合并的是说明，不是整本拿掉跟踪。

#### 叠表

叠表：同一张工作表里上下放多块表。叠不叠按内容，不要求叠。列宽属于整列。一旦叠了：短字段对短列、长说明对长列；上面内容列要够读，不要细成一条，也不要把两列拉满把下面多列表挤坏；右边为下面表留的列可以空着，前提是上面自己够读；不要把处方清单和日历叠在一起抢同一套列宽。字段对的是宽窄，不是第几列。


| 可以                         | 不要                       |
| -------------------------- | ------------------------ |
| 概览上叠判断和阶段，或阶段单独一张          | 上面挤成细条，下面多列，右边空着         |
| 执行表按周分段、每段重复表头（前面拆到日、后面按周） | 上面一块把某列拉得很宽，下面把短字段仍塞进这一列 |
| 测试安排下方叠填写空行                | 把整段文章倒进 A 列、旁边空列拉得很宽     |
| 执行表上方几行共用规则（如热身、主观用力程度）    | 把整套每日动作处方和日历叠在同一套列宽里     |


默认不冻结窗格。只有整张工作表就是一张多列明细任务表时，才冻首行并打开筛选。上下叠了多块表时不要冻，以免滚到下面仍顶着第一块的表头。

#### 样式

用途是最终要求。样式分硬要求和参考：硬要求是打开不能出现的问题；参考是第一次写入时的做法，字号、大约列宽、浅底、合并怎么并，不必严丝合缝。字体、表头和列宽由 `render_xlsx.py` 写入。不要用 `pandas.to_excel`（pandas 导出 Excel 的函数，会变成默认西文字体），也不要把 HTML 转成 xlsx，不要自写 openpyxl。写出后不为换色号、对列宽数字或空格默认西文字体再开一轮；硬要求按下面交付检查做。

##### 硬要求

打开不能出现这些。数字对不上、浅底没用、没合并，只要没有下表这些问题，仍算过。


| 不能出现               | 判定                                                                                                            |
| ------------------ | ------------------------------------------------------------------------------------------------------------- |
| 有字格子的字体名不是微软雅黑，或只给表头设了 | 格子里有文字的，字体名写成「微软雅黑」，包括表头、示例行、填写列表头。不要写成生成环境里探测到的其他中文字体名。没写字的格子、合并区里除左上以外空着的格子出现默认西文 Calibri 不算这项没过。不要为消灭这些默认字体改合并或改列数。不设时有字的中文会按宋体显示 |
| 深底深字、浅底白字；表头只涂色没有字 | 表头深底浅字、加粗，格子里要有文字。深底盖到的格子都设浅色字，包括合并区右侧和同一行内容格，不要只设左上。区块标题不是表头：浅底深字或深底白字。不规定色号，但每块表头要能辨认，不能整表白底黑字只靠括号标题分块      |
| 字号错乱               | 整表过小、标题和正文分不清、同一块里忽大忽小                                                                                        |
| 列宽过窄或过宽            | 挤成竖字或折十几行；字很少却撑出大片空列；字少的列明显宽过字多的列。用到的列都要设宽度。不要插空白列把字段推开                                                       |
| 行高空白               | 一行被撑得很高，格子里大片空着。常见于标签列换行、一格塞清单、列过窄连折多行。标签列、日期、优先级不换行；只给说明、标准、改法这类长列换行，不要整表统一换行。换行后不要写死行高。执行表一格一件事，清单先拆行或拆到阅读表 |
| 底端对齐               | 正文左对齐、顶端对齐。表头可以水平居中，仍要顶端对齐。不设时 Excel 默认底对齐，行一高字就沉底                                                            |
| 标签列写整句，或两列写同一段     | 标签列只放能一眼看完的名称。完整句子、日期预估、数字拆解放内容列                                                                              |
| 填写列预填，或整本没有空填写格    | 留空列浅底标出，格子保持空。预填「未开始」也算这项没过                                                                                      |
| 用户看得见的文字全是代号       | 周次写「第1周」，阶段写中文名，优先级写「高 / 中 / 低」或「必保」。不要单独写 `W1`、`P0`、`A`/`B`/`C`                                              |




##### 参考做法

验收只看两件事：各用途表的目标做成了，硬要求里的问题没有出现。下表是可选手段，用了容易一次写对；不用也可以，只要打开仍满足用途和硬要求。不要为了对齐这些数字或手法再改一轮。


| 参考                                                            | 为了守住              |
| ------------------------------------------------------------- | ----------------- |
| 区块标题约 14pt 加粗；表头和正文约 11pt                                     | 字号不错乱             |
| 按这一列一行大约要放下几个汉字估宽（紧接着的估宽表）。短标签宽度只给短列，说明列不要收成短标签宽度             | 列宽不过窄也不过宽         |
| `阶段`、`科目`、`模块`、`优先级` 这类短标签列可用浅底深字。块与块之间空一行。不给所有格子加重边框，也不做斑马纹  | 分块能看见             |
| 长说明同一行右边空着，可以向右并；区块标题色块可以并到下面表最右。拿不准就不并                       | 列不太窄、右边不太空、色条不短一截 |
| 开屏第一块内容列大约 28–42，不要细成一条，也不要拉满把下面多列表挤坏                         | 叠表时上面够读、下面不被挤     |
| 状态列可加下拉（未开始 / 进行中 / 完成 / 跳过）。需要时用很淡的条件格式标「完成」，不要整行划线，不要数据条或色阶 | 填写列能用             |
| 按需要设置日期或时长格式、隐藏网格线                                            | 能读                |


11pt 微软雅黑下，按「这一列一行大约放下几个汉字」估宽：


| 这一列一行大约要放下 | 大约字数     | 列宽大约  |
| ---------- | -------- | ----- |
| 阶段、星期、优先级  | 4–8 个字   | 10–16 |
| 日期、科目、时间范围 | 8–14 个字  | 16–22 |
| 一句说明、动作    | 16–24 个字 | 28–36 |
| 完成标准、两句说明  | 24–32 个字 | 40–48 |


不要把大段说明写进任务明细的每一行。练习卡和阅读表的说明列可以多行。

#### 不要做

- 不要 `load_skill` 读取 `xlsx` Skill，不写公式，不跑重算或公式检查
- 不插图表，不套财务模型，不为装饰加斑马纹或加重边框
- 只写一份 JSON，用一次 `write` 写完再跑 `scripts/render_xlsx.py`；语法错误只用 `edit` 改这一份 JSON。不要自写 openpyxl 生成脚本，不要先写一份再整份换掉
- JSON 太大写不全时，按已读颗粒度缩小表（按周不按日），不要拆成很多次写入
- 不要发现一项改一项，不要为换色号、对列宽数字、空格默认西文字体循环改 JSON 或改渲染脚本
- 不要另写只用来扫样式、修表、造 JSON 或拼 HTML 的脚本（如 `check.py`、`check2.py`、`check_style.py`、`check_plan.py`、`fix_plan.py`、`peek.py`、`gen_plan.py`、`build_json.py`、`ielts_plan.py`、`gen_testdata.py`、`build_html.py`），也不要把这类脚本当作用户产物
- 不要读或改 `render_xlsx.py` 来迁就报告。不要把自写核查脚本接到渲染后面，不要用 `head` / `tail` 截断回包，不要扫 `font.name`。渲染回包里的 5 行就是结构检查，不必再跑一条命令
- 不规定必须用某种函数或字段元组来组织 JSON 内容



#### 交付检查

检查一次、修复一次。渲染成功的标准是打得开且不是空表。空表：打得开，但看不到阶段或具体安排（只有表头，或整本空白）。结构项只看渲染回包那 5 行（写出路径、表名、执行表、填写列、预填）；字体和表头色由脚本写入，不必再问、不必扫。用途和内容在脑子里过一遍，不要另写脚本。

```
写一份 JSON → 跑 scripts/render_xlsx.py
        │
        ├─ 没写出 / 打不开 / 空表 → 报错一次看完，只改这一份 JSON，再跑到打得开且不是空表
        │                           （还没进入检查；不要改写 openpyxl 自己出表）
        └─ 打得开且不是空表 → 看回包 5 行 + 脑子里过用途/内容
                                ├─ 结构项没有 FAIL，用途也做成了 → 停
                                └─ 有 FAIL 或用途没做成 → 只改 JSON 再跑一次 → 停（不要打开 render_xlsx.py）
```

| --- | --- |
| 写 JSON / 跑渲染 | 自写 gen_plan / build_json / ielts_plan / gen_testdata / openpyxl；同一文件多次 `write`；另写 fix / check / peek 脚本；读或改 `render_xlsx.py` |

| 修复一次 | 为字体、空格默认西文字体、列宽数字、换色号、丰富度或把列头改成「动作」再开一轮。阅读版或聊天的阶段、日期不一致时，改阅读版和聊天，不重做执行版 |


| 必问 | 怎样算过 | 不要当成过 |
| --- | --- | --- |

| 用途和内容（脑子里过） | 概览分块能建立整体；执行表一格一事；跟已读领域规则一致 | 为此写核查脚本；只看字体和表头色 |

| --- | --------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 能用  | 打得开且不是空表；目标、阶段、具体安排和填写位置找得到 | 打不开、空表、明显截断、空区块、列表或字典直接打出来 |

### 4.2 DOCX

适合连续阅读、打印和手册。用户指定DOCX，或明确需要XLSX之外的阅读版本时，推荐顺序：

1. 结论与目标；
2. 现状、证据和关键差距；
3. 时间/进展路线；
4. 执行安排；
5. 适用的领域模块；
6. 缓冲、最小方案、执行校准和风险边界；
7. 来源、假设及待确认信息。

标题层级清楚；长表格必要时横向排版，不用大段重复聊天内容。

### 4.3 PPTX

适合汇报和讲解，不是默认执行载体。用户明确需要展示版本时，推荐结构：

1. 目标与判断；
2. 现状和差距；
3. 进展路线；
4. 近期行动；
5. 关键领域模块；
6. 风险、缓冲、最小方案和下一步；
7. 详细任务附录。

一页只表达一个主要结论。完整任务字段放在附录表格中，避免为了视觉简洁丢失执行信息。阶段名和起止日期从执行主产物抄，不在做 PPT 时重切；阶段路线只写一次，后面页不另写一套日期。不配图也能交；需要配图时，生成失败就跳过该页配图，不重试、不改用另一套生图流程。

一次生成完整 PPT（或一份脚本只跑一次）。不要按页改文案、不要为单页溢出逐页打转。检查一次、修复一次：能打开、有实质页、没有空页、阶段只出现一套、和执行版日期一致。记下的问题在同一次生成里改完，最多再跑一次，然后停。单页是否溢出不作为必须反复核对的项。

工作区里一旦有可打开的完整稿（常见文件名 `final.pptx`：演示文稿流水线产出的成品），立刻复制成中文计划名的 `.pptx`。用户产物列表里出现这份中文文件，才算交付；留在工作区子目录里不算。指定了 PPT / 汇报 / 演示 / 家长会时，展示版就是这份 PPTX，不要用 HTML 顶替。片子已在工作区后，不要回头重做执行表，也不要再写 HTML。步数将满时有片子就交片子。


| 做 | 不要 |
| --- | --- |
| 成品复制成中文计划名后再回复 | 片子只在工作区子目录，用户产物列表里没有 `.pptx` |
| 指定 PPT 时交 PPTX（外加需要的 XLSX） | 用 HTML 顶阅读版；片子已在工作区还去写 HTML |
| 片子已在工作区就停 | 回头重写执行表或再开一轮生图 |

### 4.4 HTML

HTML是完整计划的**阅读、理解与导航版本**，适合网页浏览、分享和打印。在默认的HTML＋XLSX双产物中，HTML帮人第一次读就看清全貌、里程碑，以及具体要做什么；XLSX负责按日或按周执行、填写和改状态。HTML 内容可以全，细度不必跟执行表一样。

页面长度不设机械限制。**首屏让人立刻抓住目标、关键数字、判断和主路线**；复杂计划可以继续展开重点方法、领域地图、资源路线、风险和取舍。页面较长不是问题，但应通过清楚的导航、视觉层级和渐进展开，让第一次阅读仍然清晰。

#### 信息内容

根据计划复杂度和领域需要组织，通常包括：

- **首屏摘要**：标题、目标、周期、投入、阶段数等关键信息，以及是否可行的判断。数字用短块呈现；判断可以放在首屏。不要用大段连续文字把标题后面堵死。
- **整体路线**：阶段顺序、时间关系、阶段重点、关键里程碑和通过标准；
- **判断与取舍**：关键差距、优先级、主要取舍，以及为什么这样安排；
- **领域重点**：只呈现帮助理解计划的领域结构，例如学习路线与资源路径、健身阶段与周结构、职业差距与证据路线；
- **现实边界**：关键风险、最小方案、调整信号、重要假设与必要来源；
- **执行入口**：默认双产物时，用一两句话说明详细日期、完成标准和记录字段在表格文件中查看和填写。页面里不要出现任何下载按钮或下载链接：包括指向本地文件、`href="#"`、「见下方附件」、`download` 属性、blob。也不要把 HTML 再转换、另存或导出成 xlsx。用户只要HTML时不写指向XLSX的入口。阅读版文件名用中文计划名，不要 `plan_reader.html` 这类英文占位名。

“快速启动”仍只放在聊天计划卡中，不复制到HTML或XLSX。HTML 不要求和聊天同一套版式、也不限制条数。

#### 视觉表达

视觉设计服务于第一次就能读懂，而不是装饰。内容用网页自己的形态表达全貌，不必做成一行一行的任务表。按内容选用，例如：

- 用指标卡突出期限、投入、阶段数、关键目标等少量核心数字；
- 用时间线、路线图或阶段日历表达阶段、依赖、里程碑和先后关系；
- 用学习地图、训练地图或分层结构表达方法、资源和能力之间的关系；
- 用卡片、条形图、矩阵或对比区表达差距、优先级和关键取舍；
- 用典型一天 / 典型一周 / 典型一训说明节奏和接下来要做什么；
- 用醒目的提示区表达重要判断、风险、安全边界和最低可行方案；
- 内容较长时提供页内导航，次要说明可按需折叠，但核心内容在不执行脚本时仍应可读。

不要求机械套用以上全部组件，也不为了好看生成无意义图表。首页应有明确视觉焦点，标题层级、留白、配色和信息密度应协调；避免大段连续文字、整页同质卡片、装饰性堆砌，以及把XLSX表格直接粘贴成网页。

#### 与XLSX去重

HTML 与 XLSX 的差别是细度和形态，不是内容多少。默认双产物时，网页要把同一份计划讲全、讲清，不得另行规划；也不要把执行表原样搬进页面。


| 计划有多长   | HTML 怎么写                                                                                      |
| ------- | --------------------------------------------------------------------------------------------- |
| 约 1—7 天 | 可以按天写每天做什么                                                                                    |
| 更长      | 用路线图、阶段日历、学习/训练地图、典型一周等把全貌、里程碑和要做的事写清楚。不要做成执行表那种一行一天、格子里塞满动作/数量/耗时的明细，也不要带状态 / 实际结果 / 反馈这些填写列 |


以下内容留在 XLSX，不在 HTML 中按任务逐项重复：

- 每项任务的完整字段（动作、数量、日期、耗时、完成标准、状态、实际结果和反馈）；
- 用于频繁修改、筛选或填写的详细清单和记录表。

只有当用户明确只要HTML、且没有XLSX执行版时，HTML才按需承载更细的任务安排。

#### 技术与交付检查

- HTML必须自包含，用一次 `write` 直接写完整页面。不要写 `build_html.py` 或任何 Python 来拼 CSS / HTML，不要用 f-string 拼，也不要分段反复改；写完报错只改这一份 HTML。兼顾桌面端、移动端和打印阅读；避免横向溢出，不只依赖颜色表达含义；
- 核心结构应使用清楚、可访问的语义层级；页面较长时仍能快速定位重点；
- 不在HTML中实现状态维护、打卡、自动更新或文件下载；
- HTML与XLSX中的目标、日期、阶段、优先级、合理性判断和安全边界应一致；HTML能打开且核心内容可读后，不为版式、组件或丰富度再改。



### 4.5 PDF

PDF适合固定版式阅读、打印和分享，不是默认的可编辑执行载体：

- 内容来自同一份标准计划数据，不因导出PDF删减必要计划内容；
- 同时存在XLSX时，XLSX负责执行和填写，PDF作为阅读或分享版本；
- 用户只要求PDF时，可以将PDF作为主产物；
- 生成时兼顾字体、分页、表格、链接和页面可读性。



## 5. 文件质量

- 文件名、标题默认中文，并写清计划日期和版本。
- 脚本、临时JSON、CSV及其他中间文件不是用户产物；除非用户明确要求相应格式，否则不在Answer中列出或交付。
- 用户没要求压缩包时，不要把最终产物再打成zip。
- 重要内容不能只依赖颜色、批注或动画表达。
- 写出后执行版按「4.1」交付检查收手：结构项看渲染回包 5 行，用途和内容在脑子里过。JSON 一次 `write` 写完，只跑 `scripts/render_xlsx.py`，不要另写核查脚本或造数脚本。指定 PPT 时，工作区成品复制成中文交付文件名再回复。阅读版用一次 `write` 写出即可，不为此再跑外部校验脚本，不要写 `build_html.py`。
- 不写“系统后续自动更新”“已同步到文件库”等当前不存在的能力。
- 用户明确要求其他支持格式时，沿用同一计划数据、领域核心内容和本题适用的条件内容进行渲染。
- 同时生成多个文件时，目标、日期、阶段、任务量、优先级、合理性判断和安全边界不得冲突；信息可以因消费方式不同而详略不同。
