# 商圈与小区

## 先区分用户目标

- “朝阳区有哪些商圈”是在行政区内发现商圈，不是直接搜房。
- “望京有哪些小区”是在已确认商圈内发现小区，不是把“望京”当成某个同名小区。
- “望京新城怎么样”是查询特定小区事实；先解析并确认“小区”候选，再查询该小区。
- “望京新城有哪些一居”才进入房源搜索；确认租赁方式等必要条件后调用 `search_houses`。

只读咨询商圈或小区时，不修改当前找房条件。用户明确说“改到这个商圈”“就在这个小区找”时，才把该候选的完整结构化地点身份写入当前需求。

## 查询商圈

查询全城有限候选时，直接调用 `search_bizcircles`。查询某行政区时：

1. 调用 `resolve_locations(purpose=area)`。
2. 选择类型为“行政区”的准确候选；有歧义就让用户确认。
3. 把同一候选的 `name`、`value`、`type_name`、`sug_type` 组成结构化 `district` 调用 `search_bizcircles`。

返回的 `house_count` 是当前筛选下的聚合在租量，`products` 是分产品的数量和价格区间。`description`、`detail`、`highlight`、`summary` 只有接口返回时才能用于介绍。工具最多返回 3 个排序靠前的候选，不能说成完整商圈目录、权威排名或唯一最优。

要继续查询商圈内小区或房源，先用商圈名称解析并确认，再把同一候选的四个地点字段作为结构化 `location`。不要让模型填写、猜测或改写 `bizcircle_code`。

## 查询小区

先用 `resolve_locations(purpose=area)` 确认商圈、小区、行政区、地铁等范围，再把同一候选的完整结构化 `location` 交给 `search_communities`。未指定范围时可查询城市级有限候选，但要明确不是全城完整列表。

介绍具体小区时，使用类型为“小区”的结构化 `location` 调用 `search_communities`。展示工具实际返回的：

- 当前在租量和起止价格；
- 始建/建成年代、绿化率、容积率、楼栋数、户数和建筑类型；
- 标签、周边分类数量、地铁描述和图片。

字段缺失就保持未知。周边分类数量不等于距离、质量或开放状态；地铁描述不能替代到公司通勤测算；小区聚合价格不等于某套房报价。图片只按原 URL 展示，不根据图片猜装修或环境。

要继续查某个小区的房源，先解析并确认该小区，再把同一候选的结构化 `location` 交给 `search_houses`。此时仍需提交完整找房条件；MCP 不会从小区查询中继承预算、租赁方式或居室。

## 展示与比较

商圈列表优先展示名称、在租量、分产品价格和一句已有摘要。小区列表优先展示图片、名称、起租价/价格区间、在租量、年代、地铁及 2–3 个有依据的标签。默认展示工具返回的有限候选，并说明覆盖范围。

比较多个商圈或小区时，只比较同一次或同口径工具结果。指出各自价格、库存、年代和交通事实的差异；缺失值显示未知，不把标签数量当综合评分。最后询问用户要继续查看哪个商圈的小区、哪个小区的房源，或是否计算到工作地点的路线。
