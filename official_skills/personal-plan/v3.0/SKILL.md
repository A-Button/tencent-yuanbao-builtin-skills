# 个人计划

将一个主目标转化为现实、可执行、可检查的一次性计划。吸收规划复杂度，不要求用户理解模型、工具或工作流。

## 执行流程

1. **确定主目标**
   - 从请求中识别目标、期限、完成标准和所属领域。
   - 一次只制定一个主目标计划；把其他目标转成时间、健康或资源约束。
   - 若请求属于旅行、理财、写作创作、工作项目排期或普通提醒，停止本流程并交给对应能力。

2. **读取适用规则**
   - 始终读取 [planning-core.md](references/planning-core.md)。
   - 学习备考：再读取 [study-prep.md](references/study-prep.md)。
   - 健身减脂：再读取 [fitness-fat-loss.md](references/fitness-fat-loss.md)。
   - 职业定位、求职、面试、Offer或入职准备：读取 [job-search-interview.md](references/job-search-interview.md)。
   - 只有需要生成针对性面试题包时，再读取 [interview-question-design.md](references/interview-question-design.md)。
   - 其他个人目标：只使用通用规则，不虚构领域专业方法。

3. **补齐最小信息**
   - 先复用对话、附件和用户已提供的信息。
   - 检查主目标、完成标准、期限、当前状态、可投入时间和安全/成败约束；这些是形成可靠计划需要理解的信息，不代表任一字段缺失都必须打断用户。
   - 只有同时满足以下条件时，才调用 `ask_user_question`：
     1. 缺失信息会使主目标/领域无法确定，或显著改变负荷、优先级、方法、安全性；
     2. 无法从当前对话、附件或可靠公开信息中取得；
     3. 不适合用清楚、保守且不危险的假设继续。
   - 以下情况通常必须追问：
     - 无法确定本次只规划哪个主目标；
     - 目标仍是“提升一下”等无法拆解的愿望，且无法提出可验证标准；
     - 缺少期限或容量，导致无法判断任务量；
     - 缺少会造成安全风险的信息；
     - 面试等强时点任务缺少关键日期，且用户没有表示只要粗略初稿。
   - 以下情况可以不追问：
     - 用户明确只要基于假设的初稿；
     - 当前基础可通过首阶段诊断获得；
     - 完成标准可以先提出建议并清楚标注；
     - 缺失项只影响配色、表格样式等低价值体验。
   - 多目标请求中若无法判断主次，也必须追问“这次优先保证哪个目标？”
   - 领域最低输入：
     - **学习备考**：学习/考试目标与完成标准、日期/周期、当前进度或薄弱项、可用时间；考试范围或资料只有在其会改变任务安排时才追问。
     - **健身减脂**：目标与周期、当前身体和运动基础、可训练时间与器械、伤病/疾病/孕期/医嘱限制。
     - **职业与求职计划**：当前阶段、目标岗位或方向、期限、现有经历与材料状态、每周可投入时间及城市等硬约束。
     - **面试备战**：公司或岗位/JD、面试日期与轮次、简历或可用真实经历、可准备时间。
   - 每轮最多调用一次，合并提出 1—4 个最关键的问题，不重复询问已知信息。
   - 不为输出格式、配色、表格样式等低影响偏好单独追问，采用默认产物。
   - 若用户明确只要初稿或不知道某项信息，使用保守假设继续，不反复追问。
   - 若用户已同时请求定时推送，把缺失的任务内容、具体日期和时间、重复方式合并到同一次询问中。
   - 用户跳过后继续生成“基于假设的初稿”，并显式列出假设。

4. **读取材料与核验事实**
   - 使用现有 `read`、`pdf`、`docx`、`xlsx` 和图片理解能力读取考纲、成绩、简历、岗位描述等材料。
   - 出现以下任一情况时使用 `web_search` 或 `web_fetch`：
     1. 计划依赖会变化的事实，如考试日期、报名资格、考纲、招聘批次、岗位要求、公司近期业务或专业安全指南；
     2. 需要选择会改变计划路径的外部资源，如官方教材、课程、题库、训练方法或求职渠道；
     3. 用户材料缺失、过期或相互冲突，需要核验后才能确定范围、顺序或负荷；
     4. 领域规则不足以支撑方法选择，需要查找权威指南、研究或成熟实践。
   - 不搜索只有用户本人知道的个人事实，也不为稳定常识或装饰性引用联网。
   - 搜索内容分为“硬事实与限制、可靠方法、可用资源、常见风险与验收标准”四类，避免用一条宽泛查询代替判断。
   - 来源优先级为：官方/原始来源 > 专业机构或研究 > 可信行业资料 > 社区经验。社区内容只作为线索，不作为唯一依据。
   - 将查证结果转化为计划决定：说明查到了什么、来源与日期、它改变了哪个阶段/任务/负荷，以及仍有哪些不确定性。

5. **诊断并生成**
   - 先判断目标是否现实、安全，识别范围、能力和时间差距。
   - 目标激进但仍安全时，解释成功概率和代价，给出推荐方案与可选挑战方案；用户理解后仍选择挑战方案，应在安全范围内尊重其选择。
   - 目标在期限内难以完整实现但仍安全时，不承诺结果，给出期限内阶段目标和后续路径。
   - 目标不安全时，即使用户坚持也不执行危险部分，改给安全替代或建议专业评估。
   - 必要时在“缩小范围、降低标准、延长期限、增加投入”中给出明确取舍。
   - 先按 [planning-core.md](references/planning-core.md) 形成与文件格式无关的标准计划数据，再加入领域文件规定的核心内容，以及本题实际触发的条件内容。
   - 核心任务必须写明动作、对象、数量或输出、预计耗时、完成标准和优先级；只有确有前置关系时才填写依赖。
   - 计划必须包含执行缓冲、时间或状态不足时的最小方案、可观察的调整信号，以及下一个可用时段能开始的低门槛第一步。

6. **交付产物**
   - 读取 [output-contracts.md](references/output-contracts.md)。
   - 始终先给聊天计划卡。完整计划默认生成XLSX；只解决当前或一次性小安排、无需后续跟踪时，可以只用聊天。
   - 用户明确指定HTML、PPTX、XLSX、DOCX或纯聊天时，在当前能力支持范围内优先采用其格式，不强制附带XLSX。
   - 用户明确需要执行和阅读/汇报等多个用途时，可以基于同一份计划数据生成多个文件；只是判断其他格式“可能有帮助”时，不自动增加文件。
   - DOCX、PPTX和HTML是同一计划的阅读或展示方式，必须保留通用计划数据和适用的领域内容，不能因格式变化而删掉目标、进度结构、任务、完成标准、缓冲、最小方案和调整规则。
   - 面试题包较大时，先按 [interview-question-design.md](references/interview-question-design.md) 的字段形成JSON中间结果，并从本Skill目录运行 `python3 scripts/validate_interview_question_pack.py <题包.json>` 检查字段、重复题和题型覆盖，再渲染进用户指定或默认选择的主产物。
   - XLSX中的`目标总览`、`阶段计划`和`执行任务`职责不得重复；`执行任务`保留空白的`状态`、`实际结果`和`反馈/问题`供用户自行填写。领域工作表按命中的Reference推荐组织，不机械创建空表。
   - 快速启动只在聊天Answer中呈现，不创建独立工作表，也不在文件中复制一套启动清单。
   - 不把文件写成系统后续会自动管理或更新的对象。

7. **判断是否提供内容型推送**
   - 默认不推荐定时任务。用户主动提出，或计划中存在“错过会造成明显损失、到点能产生新内容、需要提前准备”的高价值节点时，才进入推荐。
   - 首次最多建议3条任务，优先选择截止日期、测试/复测、面试前检查或按固定条件查询最新信息等关键节点；不得把每天的学习、训练或投递动作全部转成任务。
   - 同一计划默认最多1条重复任务，频率不高于每周。每天重复仅在用户明确要求、且固定指令每次独立执行仍有价值时使用。
   - 内容随日期不同的有限计划使用少量一次性任务；不要为了覆盖整份计划批量创建大量任务。
   - 若本轮未调用 `ask_user_question`，可在交付计划后用一次结构化问题展示拟创建任务并收集缺失的时间或重复方式。
   - 若本轮已调用过 `ask_user_question`，只在结尾提供弱入口，例如“需要的话，可以为模考或面试前检查创建关键节点任务”；不得再次结构化追问。
   - 用户确认后通过读取 [schedule-prompts.md](references/schedule-prompts.md) 了解定时任务生成规范，并通过load skill读取`task_schedule`这个skill调用定时任务工具。

## 工具规则

- `ask_user_question`：按“主目标、完成标准、期限、当前状态与容量、安全/成败约束”检查最低输入，不重复询问已知内容。
- `web_search` / `web_fetch`：查证硬事实、可靠方法、资源和风险；必须说明搜索结果如何改变计划，不用搜索替代规划判断。
- `xlsx` / `docx` / `pptx` / `write`：按产物契约渲染XLSX、DOCX、PPTX或HTML，并检查文件。
- `task_schedule`：创建时写死每条任务的名称、时间、重复方式和指令；默认最多3条、最多1条重复任务，不得假设任务会读取原计划、自动选择当日任务、修改后续任务或按执行进度调整。
- `picture_search` / `video_search`：只在健身动作说明等确有帮助时补充可信参考。

外部来源、许可证和未引入脚本的审计记录保存在 [source-attribution.md](references/source-attribution.md)，仅在维护Skill时读取，执行用户计划时不要加载。

## 运行约束

- 只生成当前会话的一次性计划和文件。
- 不读取未来执行状态，不维护个人档案、计划进度、打卡记录或多目标看板。
- 不承诺跨会话记忆、自动复盘或自动修改原产物。
- 定时任务只能使用创建时写入的固定指令和必要摘要，不得读取原计划文件、自动获取用户执行状态或虚构完成进度。
- 不编造用户经历、学习成绩、身体状态、公司事实或官方规则。
- 医疗、心理、劳动法律等高影响内容只做信息整理、一般性计划和风险提示，不替代专业意见。

## 质量检查

- 是否只保留一个主目标？
- 是否写清目标、期限、完成标准、现状、约束和假设？
- 是否完成了合理性、安全性和时间容量判断？
- 存在真实取舍时，是否按证据和优先级分配任务，而不是平均铺开？
- 核心任务是否包含动作、对象、数量或输出、耗时和完成标准？
- 是否包含执行缓冲、最小方案、检查信号、调整动作和低门槛第一步？
- 是否只在一个位置定义了通用计划字段，并保留了命中领域的核心内容和本题适用的条件内容？
- 完整计划未指定格式时是否生成XLSX，且三张核心工作表职责清楚、记录列留空、所有工作表没有重复维护同一信息？
- 快速启动是否只出现在聊天Answer，没有被扩写为文件中的独立清单？
- 多文件是否来自同一计划数据并保持关键内容一致，且没有暗示文件会被系统持续管理？
- 定时任务是否确有增量价值、数量是否不超过默认上限，且每条任务的时间、重复方式和固定指令均获得明确确认？
