# 关联分支、无关干扰与多问题

## 先确认范围

每次新剧本分别确认关联分支和无关干扰是否启用；已明确的意愿直接复用，不重复问。确认各自事件数、题材或作者自由度、占用Session和长度，以及分支附加问题数量。总Session数必须说清是否包含主线、分支、干扰、后续状态桥接和留出问题，不能把“加两条事件”自动膨胀成两段长Session。

这两种是独立选项：只有主线、仅加分支、仅加干扰或两者都有都可以。没有用户选择或授权作者决定时，不擅自增加。用户无需先写完整支线，作者可以在范围确认后提出设计。

## 按任务依赖区分，不按题材区分

|类型|判断标准|问题与评分|
|---|---|---|
|主线|用户最初要完成的核心目标及其方案|主留出问题与对应rubrics|
|关联分支|有独立小目标或状态，与主线存在人物、资源、时间或行动依赖，或需要后续独立续接|每条分支映射到主问题或附加问题的rubrics；按确认数量设计附加复杂需求，可一题覆盖多个分支|
|无关干扰|同一用户在另一段对话里处理其他事情，不影响目标任务所需的约束或状态|默认不出题、不加对应rubric，问题/rubric映射为空|

例如，旅行之外已约好的就诊或朋友会面，会受到换目的地的影响，是分支；同一用户另开Session讨论与旅行无关的股票知识，可以是干扰。若股票亏损实际改变了旅行预算，就已产生任务依赖，不能继续标为纯干扰。不要把旅行、医疗或股票固化为某一种类型。

事件可占一到多个Session，同一Session也可能包含多条事件。事件数不是Session数，更不预先规定MU数量。单用户样本不因为“另开聊天界面”就换uid；使用不同Session ID和独立主题即可。

## 关联分支怎么写

- 有自己的目标、讨论、决定及执行状态，不只是主线里插一句人物背景。
- 在主线计划中体现实际影响：已被占用的时段、还需履行的承诺、预算归属、变更需要征求谁同意。不能只扩写篇幅而不修改主线日历。
- 区分提出、接受、预约、办理、完成、取消、待确认。主线改变不意味着分支目标消失，更不意味着相关事务已取消。
- 附加问题是新的行动需求，例如重新安排、换地点处理或合并两件事；允许顺带问历史，但不能退化成只问“当时是谁”。附加问题不必重复主问题，也不必每条分支各生一题。
- Skill定义不足的业务不虚构调用或权限；可以由用户报告外部完成，或助手只拟稿、解释和整理待办。

## 无关干扰怎么写

- 是完整、合理的独立对话，有自己的提问和交付，不是随机词、占位文本、提示注入或重复刷长度。
- 不为最后问题埋隐形答案，不把干扰里的金额、地点或他人偏好偷偷变成主线条件，也不在主线回复中主动汇总干扰。
- 对话中不写“这是干扰”“这段不用记”等提示；分类仅在作者侧报告或台账中。自然出现的误发纠正可以保留，但不能用它给所有干扰打标签。
- 干扰默认没有附加问题，也不为它新设“记住某股票名称”等rubric。若用户要专门测试错误混入干扰的行为，应另行确认并登记评估目标；否则不事后增加扣分点。
- 内容仍遵守相应安全和真实性边界，不能因不计分就允许编造真实交易、诊断或已执行操作。
- 在问题允许的历史截止内，干扰应与其他历史一起进入记忆构建候选输入。不能作者先滤掉干扰，又称测试了抗干扰召回。

## 作者侧映射

### 近邻混淆型历史

用户授权提高难度时，可用同城另一趟出行、同名不同人、代他人咨询、同品牌另一订单、过去的单次例外等自然完整对话。它们的主体、日期、任务与状态必须有足够证据区分，不能靠隐藏设定或提示注入误导。不要只堆无关长文，也不要在模型可见消息标“干扰样本”。

新增历史不得无意改掉主线条件。近邻如果真的影响主线资源或决策，应按关联分支或混合消息范围记录。纯近邻干扰不要求正向复述；只有用户授权考查错误混入时，才登记归属/作用域错误的评价规则。其核查上下文不应被当成必须召回的正向证据。

在大纲与报告中记录：`event_id / 类型(main, branch, distractor) / 主题 / 所在Session与消息范围 / 与主线依赖 / 当前状态 / question_ids / rubric_ids`。

原始消息格式保持不变，不附加给模型看的事件类型标签。若一个Session同时包含不同类型，引用具体消息范围；同一事实不能一边作为必须召回的证据，一边被称为纯无关干扰。用户改变考查范围时，更新设计版本及映射，不静默改名。

## 多个留出问题与时间隔离

1. 每题单独指定允许的历史Session集合、截止日期、问题文件及其评分材料；不能仅靠“全集里靠后的一条消息”隐式控制输入。
2. 多题可以共享同一历史，独立运行时互不读取对方问题、答案或Judge结果。
3. 若后续问题需要知道主线变更后来怎样落实，新增有明确日期的固定状态对话，记录用户确认的结果和仍未完成部分。它不是前题Agent真实表现，更不能倒流进前题的历史。
4. 若用户明确要真实纵向评估，使用实际产生的执行轨迹另行绑定历史身份，不把固定合成状态和实际模型结果混在一起。
5. 新任务调用旧信息时要考虑时效：以前的朋友档期、预约、报价不直接成为今天可用的安排；过去推测不升级为确定事实。

先确定这些关系再写详细消息，评分证据则须等最终正文冻结后定位。
