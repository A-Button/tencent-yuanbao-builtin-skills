# 判断口径

根据以下标准判断通勤、出差、接送、跨城、多日旅行和临时出门等场景。不要默认用户正在规划多日旅行。

## 提炼 Todo

判断用户是否需要单独完成、改期、暂停或取消该事项；需要时拆为独立 Todo。

不要将步骤、渠道、重复次数或授权动作拆为独立 Todo。将订票到确认下单保留为一条 Todo；
将连续多日的同类事项设置为一条 Todo 加 rrule，不要按天拆分。

根据出行跨度确定条数，不设固定清单。单次出门通常创建 1–3 条，多日行程最多创建 5 条。
保留用户明确提出的事项；对未提出的事项保持克制。

每条 Todo 都要有完整 `schedule_info`。时间型 `kind=TIME`，监测型 `kind=MONITOR`。不设提醒也不能省略安排。

## 选 Trigger

已上线的 `make-things v1.2` 用顶层 `prompt` 写执行指令：定时执行用 `type=schedule` 和
`schedule.start_at`，需要取数判断时再加 `judge.tool_call` / `judge.condition`。
行政区到达用 `type=event`、`event.source_id=yb_geo_location`，Judge 取数工具是
`geo-location/get_last_known_location`，见 [location-trigger-demos.md](location-trigger-demos.md) 的示例。
确定行程目的地后的城市介绍、景区游览推荐也用同一个 Event + Judge，
创建与发卡参数见 [destination-arrival-demos.md](destination-arrival-demos.md)。
其他定时条件判断可按场景使用 `check_weather`、`check_route_eta` 或 `find_nearby`。

能够使用 Timer 时不要添加 judge，尤其是当天的一次性事项。

已确定属于用户本人的航班或高铁，且可核实日期、上车站/出发机场和该站出发时刻时，
创建行前信息 Todo 与一次性 Timer：航班默认提前 2 小时，高铁默认提前 1 小时。
到点后才查询、组装 `show_widget`；不是对票务接口做 `judge` 轮询。
仅在查票、比价或候选阶段不自动建提醒。详见 [trigger-instruction.md](trigger-instruction.md)「已知航班或高铁的行前信息」。

顶层 `prompt` 必须写：重读 Todo、把本次结果覆盖进展行、判断是否发卡，终态后停用规则。用户委托的到点提醒、到达后通知或重要变化，须明确用 `show_widget` 发到「此刻」；session 回复或 `show_panel` 不能代替这项交付。
Judge 未命中时不投递 `prompt`，不能假定会有执行轮更新检查时间。

**顶层 `prompt` 要写清要不要发卡**，以及结束条件与监测有效期——写法、出行的触发时机
谱系、`judge.condition` 的阈值写法都在 [trigger-instruction.md](trigger-instruction.md)。
漏写发卡意图不报错，但那条规则永远不会发卡。

结论性的数值（出门时刻、预留时间、是否适合出门）**要在触发时现算**，不要在创建时算好写死进指令：
创建那一刻的路况和天气到点早已过期。

## 选卡型

**先过闸：这一轮该发卡吗？** 普通创建轮不发（见 SKILL.md「卡片发在哪一轮」），
安排和候选写进回复正文即可。本节仅在**触发轮**、本轮缓存定位可靠确认已抵达目的地，
或用户明确要求发卡时才往下读。

确认要发之后，仅从四种固定组件中选择，不要使用 `stock`、兜底卡型或自定义 HTML。按以下问题依次判断。

**第零步：卡上放什么，点击后回哪里。**

卡片是信息流里的一瞥，不是详情页。一张卡只允许出现这些：

| 卡上可以有 | 卡上不可以有 |
| --- | --- |
| 标题、一行 `summary` | 天气块、信息格、时间轴 |
| 每行一句 `desc` + 缩略图 | 门票、开放时间、交通方式的明细 |
| 最多 2 个按钮 | 多段说明文字 |

行程卡要把当下需要知道的结论写在卡上，点击回原会话继续交流；不生成自建详情页。
到达快览只保留一条卡上能读完的建议，点击也回原会话。
天气作为行程辅助信息时，只有在**改变了安排**才进卡，写成 `summary` 里的一句话（「有雨，改室内」），
不单独占一块。**用户明确要求到点或到达后通知天气是例外**：天气本身就是交付结果，确认命中后用 `show_widget` 发简短天气卡，即使无需改行程也要发。

判断标准很直接：**这张卡用户扫一眼能不能懂？** 要停下来读第二遍，就是堆多了。

**第一步：看用户此刻在什么状态，不是看你手上有多少数据。**

| 用户此刻 | 他要什么 | 卡型 | 典型错法 |
| --- | --- | --- | --- |
| **被打断**（提醒触发，可能在睡、在赶路） | 一句话 + 一个动作 | `image_text` | 摆四条清单让他读 |
| **在挑** | 能比较的 3–5 条 | `recommend_list` | 只有 2 条还硬凑第 3 条 |
| **要表态**（你需要他定夺才能继续） | 明确选项 + 确认按钮 | `todo_choice` | 在信息流里问开放式问题 |
| **在核对**（出发前清点） | 一串能逐条对照的事 | `todo_remind` | 拿它当提醒用 |

已知班次的行前信息属于出发前打断用户的**一句话核对**，优先用 `image_text`：
标题放航班号/车次，`summary` 放出发站、时刻和实际核实的登机/检票信息。
个人车厢座位只从用户票据取；同程显示的可售座别不是个人座位。
不能获得口号或座次时仍可提醒，但必须明确告知用户查看票据或现场屏幕，不填推测值。

**最容易错的是第一行和第四行。** `todo_remind` 读起来像「提醒」，
但它**自身不创建任何 Trigger**，只是展示——真正到点的是规则。
被叫醒的人不想读清单，那一刻该用 `image_text` 配一句狠话。

**第二步：检查必需槽位。** 无法满足卡型要求时逐级降级：

- `recommend_list` 不足 3 条真实条目 → 需要用户选择时改用 `todo_choice`，选项写类别而非具体名称；普通查询仍不可用时在会话中说明。
- 只有 1–2 条真实结果 → 普通查询直接在会话中说明，不编造第三条。
- Trigger 承诺的关键通知有可信内容，但不够组成列表 → 改用无图 `image_text` 概述真实结果，不能只在会话中回复。若取数失败，按 [data-sources.md](data-sources.md) 如实发无法核实提示；发布失败不能声称通知已完成。

目的地**到达快览**是例外：城市、美食、景点各选一个真实对象，
每个对象单独发一张 `image_text`，摘要不超过 40 个汉字；
不将几个对象装进 `recommend_list` 或 `todo_choice`。
每张都配整卡 `tap={"type":1,"agent_chat":{}}`，点击回到原会话且不自动发消息；
卡片本身仍把该对象的建议说完整。默认同一趟旅行
每天主动到达快览最多 3 张，其中景点最多 1 张；只选用户点名或行程核心景点，
不对所有景点逐个建 Event。每个对象只发一次，并分别记录 `now_id`。

将配图视为可选项。按 [card-media.md](card-media.md) 获取真实图片或生成图；无法获取时发布无图卡片。
不要因缺少图片而放弃 `image_text`，也不要添加无关图片。

让每张卡只承载一个主题。将「已经排好」和「还需要你告诉我 X」拆为两张卡，或先询问再安排。

**第二步半：多日行程按「一天一张总览卡」发。**

多日行程的**每日总览**同一 Thing 一天一张，不为每程各发一张总览。
目的地到达的不同对象快览按上面的一物一卡规则发；用户明确要求的不同对象
不是同一进展的重复通知。不创建额外 Thing 来发这些卡，
同一个美食或景点在同一次旅行中已经发过就不再发。

| 当天程数 | 卡型 | 怎么配落地 |
| --- | --- | --- |
| 3–5 程 | `recommend_list` | 每行一程，`items[].tap={"type":1,"agent_chat":{}}` 回原会话；**不配整卡 tap** |
| 1–2 程 | `image_text` | 大图配主图，整卡 `tap={"type":1,"agent_chat":{}}` 回原会话 |
| 要用户定夺 | `todo_choice` | 选项是具体的几程，确认按钮回会话 |

每行写名字和一句对当下有用的话；卡片本身要能读懂，不把必须知道的信息留给点击之后。
更多行程细节由用户回到原会话继续询问。

每日行程总览的 `recommend_list` 每行回原会话，仍不配整卡 tap。
地点等推荐列表每行和整卡都回原会话时可同时配置，目标必须一致；
`prepare_card` 只对不一致的点击目标给出 warning。
不要将已完成内容放入 `summary`，同时在卡片主体中提出另一问题。

**第三步：确定点击区域及其目的。**

- 地点、美食、景点等推荐列表的每一项都给 `items[].tap={"type":1,"agent_chat":{}}`，点击回原会话；列表卡整卡也用相同的 `tap`，使留白区域可点，且点击目标一致。
- 底部主按钮执行下一步：给 `actions[].tap`；需要写 Todo 或继续确认时必须回 `agent_chat`。
- 推荐卡和行程总览都只在有清晰点击目的时配置 `agent_chat`；卡片自身写清关键结果。

需要跳转合作方小程序或地图时读 [landing-pages.md](landing-pages.md)，用 `prepare_landing` 生成，不手拼。
回原会话直接配置 `{"type":1,"agent_chat":{}}`。

## 赶时间的时候别走完整流程

用户说「马上」「现在就走」「来不及了」，或算出来距出发不到 30 分钟时，走**紧急路径**：

1. 先把 Todo 和规则建出来（建规则时注意 `run_at` 要留 5 分钟余量）
2. 回复里一句话说清最要紧的事：几点出门、走哪条路
3. **跳过**配图和周边推荐——这些都可以等他上车之后再补

理由很直接：这个场景每一秒都是真实的焦虑。用户说完需求还要盯着屏幕等十几轮工具调用，
等来的却是一张配了图的漂亮卡片，这是帮倒忙。

判据是**这件事现在不做会不会来不及**，不是内容完不完整。

## 用户要取消或改期

「算了不去了」「改到明天」「别提醒了」——这几句必须当成明确指令处理，不要只回一句「好的」。

| 用户说 | 要做什么 |
| --- | --- |
| 不去了 / 取消 | 停用该 Thing 下**全部**规则，Todo 标取消 |
| 改到 X | 重算时间，更新 Todo 的 `schedule_info`，**并更新对应规则的 `run_at`** |
| 别提醒了 / 太吵 | 停用规则但保留 Todo，告诉他事情还在、只是不再打扰 |
| 这条不用了 | 只停用那一条规则，其余不动 |

**只改 Todo 不动规则等于没改**：规则会照常触发、卡会照常发，用户会更生气。
按 `rule_ids` 查出全部关联规则，逐条处理。

改完要在回复里说清楚「现在还剩哪些提醒」，别让用户猜。

## 先问还是先排

先起草 Todo 的 `instruction`。如果必须留空或写入「地点待定」，**在会话里直接问**，
不要为了提问把 `todo_choice` 发到 NOW；收到回复后再创建 Todo 并启用 Trigger。

不要在必要信息缺失时先锁定时间或启用 Trigger，以免用户修改需求后需要回收规则。

输入齐全才走 `make-things` 的标准顺序：建停用 Trigger → 回填 `rule_ids` → `write_todos` → 启用。

建完之后**不发卡**，把安排写进回复正文就结束这一轮。卡片由规则到点那一次发出，
口径见 SKILL.md「卡片发在哪一轮」；唯一的目的地例外是本轮已用缓存定位可靠确认抵达，
可以直接交付一次性到达推荐，见 [destination-arrival-demos.md](destination-arrival-demos.md)。

## 参考示例

将以下内容作为示例而非固定清单；未列出的场景继续按上述标准判断。

**多日旅游，`get_trip_context` 有行程。** 证件行李（Timer once，出发前一天，`todo_remind` + `badge.tone=2` 标必带）→ 每日陪伴（Timer rrule 讲解，Agent 日频天气备选）→ 归程总结。行程规划中的景点卡仍由 `travel_plan` 出；本包仅在确认抵达核心景点后给一条当下有用的新建议，若当天卡片已讲过同一内容则不重复。

**明早赶飞机。** 创建一条「几点出门」Todo，使用 Agent 和 `check_route_eta`，规则定在出发前
60–90 分钟。出门时刻由**触发那一次**按当时路况算出并发一张 `image_text`，给预留区间而非单点时刻；
创建轮只把安排说清楚，不发卡。`judge.condition` 要拿本次 `reserveMin` 跟进展行里的上次值比，
给出具体阈值。

**已知本人航班/高铁号。** 另建「核对登机/检票信息」Todo 和一次性 Timer；
航班起飞前 2 小时、高铁从用户上车站发车前 1 小时核对并发 `image_text`。
与「几点出门」规则共存时避免重复投递同一内容：优先保留行前班次提醒的 NOW 展示，
路况无明显变化只回写进展；独立到点的用户提醒仍须发 `show_widget`。改签或改站须同时更新 Todo 时刻和规则 `run_at`。

**今晚就近放松。** 城市未知时先在会话里问。创建 1–2 条 Todo，使用 Timer 到点提醒，不配置 Agent。
候选地点写进回复正文，**创建轮不发 `recommend_list`**；到点那一次再按当时情况决定发不发。

## 选择回传之后

`ui_snapshot.selectedIds` 只是卡片选项，不是业务 Todo。重读 Thing，按真实执行 `write_todos`，需要时再发一张完成态快照。不要把 `option_id` 写进 `rule_ids`。

问「想做什么」的选择卡还没有对应 Todo，`thingId` / `todoId` 整段省略。
