# 工作指令怎么写

投递是把这段原文送进**一次全新的执行**。那一次看不到创建时的对话，这段文字就是它拿到的全部指令。

创建参数以实际加载的 `make-things v1.2` 工具 Schema 为准：`type=schedule` 填 `schedule`，
`type=event` 填 `event`；执行指令统一放顶层 `prompt`，`judge` 只填 `tool_call` 与 `condition`。
旧版本的 `instruction`、`trigger_kind`、`run_at` 不是 v1.2 入参，**不要照搬**。
本文补出行场景的取舍。

## 卡片这一项决定用户看不看得见

**每一条规则都必须就发卡表态，发或不发，二选一，没有第三种。** 用户委托的提醒、到达后通知、到点查询结果，以及需要及时关注的重要变化，都要在命中后的回调中用 `show_widget` 发到「此刻」。只在 session 中回复或调用 `show_panel`，不算完成这项通知。无变化、核验未通过或仅维护规则时可以不发卡；其他会话说明不必全部做成 NOW 卡。

不表态的后果是单向的：**沉默等于不发，而且不会报错**。规则照常触发、照常取数、照常回写 Todo，
只是用户什么都看不到——进展只留在待办的进展行里，没人会去翻。

建完一批规则，逐条回读一遍指令，确认每条里都能找到「发…卡」或「不发卡」。
漏掉的那条不会有任何提示，只会在用户某天问「怎么没提醒我」时才暴露。

出行的判断是：**有仍然有效的到点提醒，或这次触发算出了需要告知用户的新结果吗？**

| 触发结果 | 发不发 | 指令里怎么写 |
| --- | --- | --- |
| 出门时间因路况变了 | **发** | 「…若出门时间较上次有变化，发一张图文卡，标题写新的出门时间，摘要写路况与预留区间」 |
| 天气转坏、原计划要改 | **发** | 「…发一张图文卡说明天气与替代安排」 |
| 用户要求到乌鲁木齐后通知当地天气 | **发** | 「…确认抵达后重新查询乌鲁木齐天气，用 `show_widget` 发天气摘要卡」 |
| 到了要挑一个地方 | **发** | 「…把候选整理成 3 到 5 条发一张推荐列表卡，每条配地点落地」 |
| 需要用户定夺才能继续 | **发** | 「…发一张选择卡，选项是 <具体选项>，确认按钮回会话」 |
| 纯提醒，没有新信息 | **发** | 「…用 `show_widget` 发一张简短 `image_text`，提醒带证件、带伞或该出门了」 |
| 查完没有变化，也没有到点提醒 | **不发** | 只更新进展行，保持静默 |

写了也不是每次都发：执行时仍要核对内容是否可信、提醒是否仍有效、同一对象是否已发；无须告知用户时保持静默。
`make-things v1.2` 没有对所有 Thing 统一的「一天一张」限制；每日总览的一天一张只是本场景的规则。
**指令是许可，不是强制。**

## 七要素骨架：照着填，不要从零写

出行场景的顶层 `prompt` 按下面七个要素写全：

```
【定位】先读 Thing「<标题>」下 Todo「<标题>」的最新 description 与状态；
        已完成、已暂停或用户已自己办完，就不执行并停用本规则。
【业务】<用什么工具、取什么数、算出什么>。结论性数值在这一刻现算，不要用创建时算好的。
【无结果】<无变化时只更新进展行；关键提醒取数失败时用 show_widget 发简短失败提示，非关键失败只记录原因>。
【维护】把 <本次算出的值> 覆盖进展行。
【结束】本次结束后停用本规则。／ 继续，UNTIL <日期>。
【边界】只读不下单；<需要确认的动作> 停下等用户确认。
【卡片】承诺的提醒／通知或重要变化用 show_widget 发一张 <卡型>：标题写 <什么>，摘要写 <什么>。／ 本轮无值得通知的结果，不发卡。
```

**最容易漏的是【定位】和【维护】**，漏了的后果很具体：

- 没有【定位】→ 用户已经自己办完值机了，回调照样发一张「该去值机了」
- 没有【维护】→ 提醒发了，Todo 永远停在原状态，下次触发还以为没做过
- 没有【结束】→ 一次性提醒发完规则还留着，明天同一时刻再来一遍

**指令里的「现在」是创建时的现在，不是执行时的。** 写「提醒他去值机」没问题，
写「距离起飞还有 2 小时」就错了——那是创建时算的，执行时早就不是了。

**2048 字节硬上限**，超了服务端整条拒绝。要压缩时的省略顺序：
【边界】在纯只读场景可省 → 【无结果】可并进【卡片】 → 其余五项不能省。

## 出行的完整指令样例

### 条件型：出门时间（Agent + judge）

v1.2 的执行指令放顶层 `prompt`，`judge` 只放取数与条件；概念写法如下：

```
tool_call  check_route_eta，from=南山科苑站，to=深圳宝安国际机场，mode=driving
condition  reserveMin 比 description 进展行里记录的上次预留时间多 10 分钟以上时命中；
           取数失败或超时不算未命中，按错误处理
prompt     先读 Thing「明早赶飞机」下 Todo「几点出门」的最新 description 与状态。
           用 check_route_eta 重算当前路况下的预留时间，换算出门时刻。
           把本次 reserveMin 与出门时刻覆盖进展行。
           发一张图文卡：标题写新的出门时刻，摘要写路况与比上次提前了多少。
           本次结束后停用本规则。只读不下单。
```

要点：`condition` 必须给**阈值和比较基准**（跟进展行里的上次值比），不能写「路况变差时」。
没有基准，下次要么次次命中、要么永不命中。

### 时间型：出发前一天的证件行李（Timer）

```
prompt  先读 Thing「成都三日游」下 Todo「证件行李」的最新状态；已完成或已暂停就不执行并停用本规则。
        调用 show_widget 发一张无图 image_text 到「此刻」，标题写「出发前核对证件行李」，
        摘要提醒核对身份证、充电宝、雨具。拿到真实 now_id 后记录已提醒，停用本规则；
        提醒不等于用户已核对完成，不自动标记 Todo 完成。发布结果不明时先核查，不重发。
```

要点：纯提醒也是用户需要感知的消息，必须明确写 `show_widget` 的卡型和内容；已完成或暂停时才静默结束。

## 已知航班或高铁的行前信息

用户明确说自己要坐某班航班或高铁时，建立「核对〈航班号/车次〉登机/检票信息」Todo，
即使没有单独说「提醒我」。**仅查票、比较候选或拿到一个搜索结果，不代表用户已经选定那班。**
建规则前确认乘坐日期、从哪座机场或车站出发，以及该站的计划出发时刻；同一车次可能在多个站停靠，
不能拿始发站时刻替用户上车站时刻。把班次、日期、出发站、计划出发时刻、用户票据中已有的
车厢/座位或值机信息及各字段来源存进 Todo；票据没有的字段留空，不填「待定座次」当作事实。

- **触发**：`type=schedule`、只填 `schedule.start_at` 的一次性 Timer，不带 `judge`。航班默认起飞前 **2 小时**，高铁默认从用户上车站发车前 **1 小时**；用户指定 1–2 小时内的时刻时以用户要求为准。`schedule_info.kind=TIME` 记录出发时刻，Trigger 的 `schedule.start_at` 记录提醒时刻，两者按出发地当地时区换算。跨日也按真实日期回退；按 [一次性规则要留足余量](#一次性规则要留足余量) 建规则。若预定提醒时刻已过，直接告知当前能核实的行前信息，不创建过期 Trigger。
- **触发轮取数**：重读 Todo，核对没有取消、改签或改站；运行本包 `check_ticket`，按 **班次 + 日期 + 出发城市/到达城市** 复查计划时刻和出发机场/车站，火车必须传用户上车站 `depStation`。若另有实际可用的可信实时航班/车站接口，再核对检票口、站台、登机口及其采集时间。用户提供的电子客票可作为其本人车厢、座位信息来源。当前同程接口只提供班次静态信息与**可售座别**，不提供用户座位、检票口、站台或登机口；不要用搜索、常识或前一班的口号补齐。
- **发卡**：发一张无图 `image_text` NOW 卡，标题写「〈班次〉出发前核对」，`summary` 用一行放真实的出发站/机场、计划时刻，以及**已核实**的检票口/登机口、车厢座位。没有座次或口号时，写「座位见车票」「检票口请看车站屏幕」等明确提示，不暗示已经查到。动态字段如有来源，也提示以车站或机场现场信息为准。`source.label` 按真实来源写，不混淆用户票据与同程班次；用真实 `thingId`/`todoId` 关联。
- **收尾**：记录本次复查时间、已发卡的 `now_id` 与可用字段来源，停用本规则；**提醒已发不等于旅程已完成**。重复回调先读进展行，已有成功或结果未明的发布就不重发。关键取数失败时仍发简短 `image_text` 告知「班次信息暂未核实，请查看官方行程/车站或机场屏幕」，不编造具体口号；卡片发布失败按 [失败不要静默](#失败不要静默) 处理。

这是按已知计划时刻执行的**一次性行前提醒**，不是延误或登机口变化监控。

顶层 `prompt` 样例（`<…>` 在创建时替换成真实 Thing、Todo、班次及日期，控制整条规则在 2048 字节内）：

```text
先读 Thing「<标题>」下 Todo「<标题>」最新状态和行前进展；已取消、改签或暂停则停用本规则，不发卡。
加载 travel_assistant，按 Todo 中的班次、日期、线路及出发站调用 check_ticket 复查计划时刻；座位只用用户票据，
检票口、站台、登机口只用能标明查询时间的可信实时来源，缺失就明确提示用户查看票据或现场屏幕。
发一张 image_text：标题「<班次> 出发前核对」，摘要写出发站与计划时刻，并仅写已核实的口号和座次；
取数失败则发无图卡告知用户自行核实。只读不订票。记录查询时间、来源和 now_id；
已有成功或未决发布不重发，本次结束后停用规则，不把乘车 Todo 标完成。
```

示例：用户 **2026-09-28 10:30** 从深圳宝安机场乘 CA1234，`schedule.start_at=2026-09-28T08:30:00`；
用户 **2026-09-28 18:00** 从深圳北站乘 G1234，`schedule.start_at=2026-09-28T17:00:00`。
这两个时刻仅演示计算，不能当作实际班次资料。

## 行政区到达：Event + judge

用户说「到了北京推荐吃的」「到了赛里木湖讲人文」「到了深圳南山区提醒吃肠粉」时，
按 `make-things v1.2` 创建 `type=event` 的 Trigger，事件源是 `yb_geo_location`。
区级到达不能用城市中心点加半径代替，更不能把深圳宝安区判作南山区。

这类 Event 的 `judge.tool_call` 使用**已绑定的地理位置 Connector 完整工具名**
`geo-location/get_last_known_location`，参数 `{}`。该工具返回最近一次采集的**缓存**位置，
含 `is_cached` 与 `collected_at_ms`；Event payload 不会自动注入 `tool_arguments`。
Judge 只把有效且位置描述明确指向目标区的结果作为**候选**，不在 `condition` 中检查缓存采集时间；
缓存防抖由下游处理。最后是否发卡由顶层 `prompt` 再读一次缓存位置核验；只有「深圳市」而没有区级证据、
坐标或精度不足时保持静默。

以下是「进入深圳南山区后提醒吃肠粉」的 Trigger 模板；真实 ID 和监测有效期要在创建时填入
Todo。`prompt` 是顶层字段，`judge` 只包含 `tool_call` 和 `condition`：

```json
{
  "thing_id": "<真实 Thing ID>",
  "todo_id": "<真实 Todo ID>",
  "title": "进入深圳南山区后提醒吃肠粉",
  "type": "event",
  "event": {"source_id": "yb_geo_location"},
  "judge": {
    "tool_call": {
      "tool_name": "geo-location/get_last_known_location",
      "tool_arguments": {}
    },
    "condition": "定位结果有有效坐标，位置描述明确指向深圳市南山区时才作为候选；宝安区或区名不明不命中；取数失败属于错误，不能当作到达。"
  },
  "prompt": "重读对应 Thing、Todo 和本规则；已提醒、暂停、取消或超出有效期就停用并结束。调用 geo-location/get_last_known_location 读取缓存位置，不调用实时定位；只有能可靠核验深圳市南山区且能排除区界误判时，才用 show_widget 发无图 image_text 提醒吃肠粉。宝安、区界不明或取数失败不发卡。仅收到真实 now_id 才记录已提醒并停用本规则；结果未知不重发。提醒不代表 Todo 已完成。"
}
```

`get_last_known_location` 的公开描述保证坐标、位置描述、城市编码、缓存标记和采集时间，
**未保证有结构化区名、定位精度或区界距离**。若缓存回包不足以排除区界误判，
这条规则会安全地不发卡，不能宣称已能准确检测整个南山区。要提高覆盖率，需接入可信的行政区
归属与精度核验能力，再按实际字段收紧 `condition`。正式创建时还须按 `make-things v1.2`
顺序：先建停用 Event Trigger → 回填真实 `trigger_id` 到 Todo.`rule_ids` → 启用；
Event 不使用仅支持时间规则的 `bind_and_enable=true`。同一 Todo、同一目标已有有效规则时
更新它，不叠加新规则。

到北京推荐吃的、到赛里木湖讲人文、进入南山区提醒吃肠粉的完整 Event 参数与触发轮步骤见
[location-trigger-demos.md](location-trigger-demos.md)。

### 到乌鲁木齐后通知当地天气

用户说「等到乌鲁木齐了给我推送下当地的天气」时，天气就是这条 Trigger 承诺交付的通知，不要求它先改变行程。按本节创建乌鲁木齐市的 Event + Judge，创建时确定监测有效期；Judge 只判断到达候选，不能把创建时的天气写死在规则中。顶层 `prompt` 写清以下回调动作：

```text
重读 Todo；已取消、已通知或超过有效期就停用规则，不发卡。
用 geo-location/get_last_known_location 复核仍在乌鲁木齐市，无法确认到达则不发卡。
确认抵达后调用本 Skill 的 check_weather，city=乌鲁木齐、type=now，读取此刻的天气和温度。
调用 show_widget 发一张无图 image_text 到「此刻」：标题「乌鲁木齐天气」，摘要只写已查到的实况、温度及查询时间；关联真实 thingId/todoId，不调用 show_panel。
天气取数失败时，仍用 show_widget 发简短 image_text 告知暂时无法核实当地天气，不编造天气。
只在 show_widget 返回真实 now_id 后记录卡片已发布并停用 Event；发布结果未决先核查，不盲目重发。会话回复不能代替这张通知卡。
```

## 地理围栏触发：具体地点按距离

出行里最自然的触发是「快到了」，不是「到点了」。时刻会因为堵车、改签全部作废，
**距离不会**。

### 什么话该建围栏

用户不会说「盯着我的位置」，他说的是**一件到了某地才做得了的事**：

- 「等我快到酒店的时候，提醒我先去取快递再上去」
- 「到了机场提醒我先值机」
- 「明天路过公司楼下的时候提醒我把伞还了」
- 「快到武侯祠了跟我讲讲这儿有什么看点」

共同的形状是「**到 / 快到 <地点>，提醒我 <这件事>**」。听到这个形状就建围栏规则，
不要因为用户没说「帮我盯着」就漏掉。反过来，用户只是提了个地点、没说到了要干什么，
不要自作主张挂一条位置规则。已确认的行程**主目的地**是例外：可按
[destination-arrival-demos.md](destination-arrival-demos.md) 建一次到达快览；普通途经景点不逐个建规则。

**提醒内容用用户自己说的那件事。** 他说的是取快递，到点就提醒取快递，
不要换成「欢迎来到 XX 酒店」或者自作主张讲一段酒店介绍——他要的是那件事，不是导览。

围栏有两类用途，别混：

| 用途 | 目标从哪来 | 提醒内容 |
| --- | --- | --- |
| **到某地办一件事**（取快递、值机、还伞） | 用户说的那个地点，显式传 `targets` | 用户交代的那件事 |
| **到站讲这一程**（景点、门票、开放时间） | 不传 `targets`，自动读行程站点 | 这一程最要紧的一件事 |

「到站讲这一程」只用于用户明确要求**快到各站**时讲解的距离提醒；
目的地确认抵达后的快览使用 Event + Judge。两者涉及同一景点时只保留用户要求的时机，
不要同时建两条讲同一内容的规则。

地点坐标用 `prepare_landing kind=map` 拿：回包 `lookup.lat` / `lookup.lng` 就是那个 POI 的坐标，
顺带还能拿到 `tap`，提醒卡可以直接点进地图导航。用户说「我酒店」这种指代，
先从行程或上文确认是哪一家，确认不了就问，不要拿同名的另一家建围栏。

形态是 **Agent + judge 轮询**：后台按周期调 `geo-location/get_last_known_location` 读缓存位置，拿坐标去比 `condition`；不向设备请求实时坐标，
**没进围栏就什么都不发生**——不投递 prompt、不唤起执行、会话里看不到任何东西。
只有进了围栏那一次才投递 prompt。

不要用 Timer 做位置轮询：Timer 每次到点都把指令投进会话，每分钟一次就是一小时 60 条 prompt，
绝大多数只是「还没到」。

judge 只能调一次取数，判断方也不该心算球面距离，所以条件不写「距离小于 3 公里」，
而是用 `plan_geofence` 把围栏换算成经纬度区间，judge 只做数字比较：

```bash
run_tool plan_geofence '{"radius_km":3,"targets":[
  {"name":"成都天府国际机场","lat":30.3125,"lng":104.4415,"radius_km":5},
  {"name":"武侯祠","lat":30.6469,"lng":104.0435}]}'
```

回包里的 `condition` 原样填进 `judge.condition`。不传 `targets` 就自动读行程站点；
一条规则最多放 5 个未提醒的站点，行程长就只放接下来要去的几站。
整条规则 2048 字节，`conditionBytes` 加上 prompt 要装得下，prompt 照下面的样例写短句。

**定位失败在 judge 这层按错误处理，不能当作到达来投递提醒**——否则手机离线时每一轮都会投递一次，又回到刷屏。
代价是定位一直失败时用户不会知道，所以**关键提醒不能只靠围栏**：赶飞机赶火车要同时有一条出门前重算路况的时间规则兜底，围栏只负责「快到了」这句锦上添花。

### 半径怎么选

| 场景 | 半径 | 到了要干什么 |
| --- | --- | --- |
| 赶飞机赶火车 | **5 公里** | 提醒值机截止、航站楼、行李检查 |
| 下一程景点 | **3 公里** | 讲这一程的看点、门票、开放时间 |
| 回酒店、到家前要顺手办的事 | **1.5 公里** | 提醒取快递、买东西、拿寄存 |
| 吃饭、商圈 | **1 公里** | 推附近几个去处 |
| 酒店入住 | **2 公里** | 提醒办入住、寄存行李 |

**要顺手办的事半径别给大。** 提醒取快递，5 公里外就弹出来，到家时早忘了；
1.5 公里大约是下车前那几分钟，正好来得及拐一趟。

半径可以逐个目标给，不必全局统一：

```bash
run_tool check_proximity '{"lat":30.657,"lng":104.066,"targets":[
  {"name":"成都天府国际机场","lat":30.3125,"lng":104.4415,"radius_km":5},
  {"name":"武侯祠","lat":30.6469,"lng":104.0435,"radius_km":3}]}'
```

不传 `targets` 就自动读 `travel_plan` 行程里带坐标的站点，`radius_km` 作为统一半径。

回包给 `hit`、`within`（进了围栏的，按距离排序）、`nearest`、以及每个目标的
`distanceKm` 和 `bearing`（方位，用来写「在你东北方 2.1 公里」这种人话）。

### 完整规则样例

**到某地办一件事**（用户：等我快到酒店的时候，提醒我先去取快递再上去）：

```
type          schedule，schedule.rrule 的 UNTIL=离店那天
tool_call     geo-location/get_last_known_location，tool_arguments={}
condition     plan_geofence 回包里的 condition，原样填（targets 只放这家酒店，radius_km=1.5）
prompt        先读 Thing「成都出差」下 Todo「到酒店取快递」的状态；已完成或已取消，停用本规则并结束。
              调 geo-location/get_last_known_location 读取缓存位置，用 check_proximity 复核是否在围栏内；
              不在就不发卡、不改规则，直接结束。取位置失败记「连续失败 N 次，原因 X」，
              连续 3 次停用本规则并发卡说明。
              在围栏内：发一张 image_text，标题「快到酒店了，先去前台取快递」，
              摘要写还有多远、快递放在哪（读 Todo 里记的），整卡 tap 落到酒店的地图页。
              把 Todo 标记完成，并停用本规则——这件事只提醒一次。只读不下单。
```

要点：提醒的是**用户交代的那件事**，不是酒店本身。事情办完规则就结束，不留着。

**到站讲这一程**（多日行程，每到一个景点讲一次）：

仅在用户明确要求逐站讲解时使用本例；不要因行程里列出多个景点就自动启用。

```
type          schedule，schedule.rrule 的 UNTIL=返程日
tool_call     geo-location/get_last_known_location，tool_arguments={}
condition     plan_geofence 回包里的 condition，原样填
prompt        先读 Thing「成都三日游」的维护 Todo 进展行；Thing 已结束或用户已取消，停用本规则并结束。
              调 geo-location/get_last_known_location 读取缓存位置，用 check_proximity 复核是否在围栏内
              （区间是方框，角上会多出一点）；没在围栏内就不发卡、不改规则，直接结束。
              取位置或复核失败：进展行记「连续失败 N 次，原因 X」，不要只写「本次失败」；
              连续失败 3 次停用本规则，发一张图文卡说明哪个能力不可用。
              在围栏内：发一张 image_text，标题写「快到<站点名>了」，摘要写距离方位和这一程
              最要紧的一件事，整卡 tap={"type":1,"agent_chat":{}} 回原会话。把「已提醒<站点名>」和本地时间覆盖进展行。
              再调 plan_geofence，exclude 放所有已提醒过的站点，用回包的 condition 调 update_trigger
              替换本规则的 judge（tool_call 和 prompt 不变）；回包 fences 为空就停用本规则。只读不下单。
```

### 三条必须守的

**同一程只提醒一次：命中后要把自己改掉。** 平台不保证持续命中只通知一次——用户在围栏里待多久，judge 就命中多久。
所以命中那一次的 prompt 必须用 `exclude` 重新生成条件、替换 judge，把刚提醒过的站点从条件里拿掉。
漏了这一步，用户在景区里逛两小时就会被同一条提醒刷两小时。

**命中不等于发卡。** prompt 里仍要用 `check_proximity` 复核，并检查该景点是否已介绍过；方框角上的误命中不发卡。

**必须有监测截止。** 没有 `UNTIL` 的位置轮询会一直跑下去。
办一件事的规则跟到那天结束，多日行程的跟到返程日；**不建无限期的**。

### 成本

未命中的轮询只读一次 `get_last_known_location` 缓存，不向设备请求实时定位，也不唤起执行。
这种逐站距离提醒**只在用户交代了「快到某地要做什么」时才建**；
已确认的核心目的地到达快览按 Event 规则，普通途经景点不默认挂上。
用户没说间隔时默认 **15 分钟**；用户指定了就按他的，不要自行降级。

## 出行的触发时机谱系

不要只会「到点提醒一次」。按出行阶段选：

| 时机 | 典型规则 | 类型 |
| --- | --- | --- |
| 出发前一天 | 证件行李核对 | Timer once |
| 出发前一晚 | 次日天气与是否要改安排 | Agent once |
| 当天出门前 60–90 分钟 | 按当时路况重算出门时刻 | Agent once |
| 多日行程每天早上 | 当日总览卡（每行一程） | Timer / Agent rrule |
| 快到下一程（5/3/1 公里） | 按距离提醒，见上一节 | Agent judge 轮询位置，命中才投递 |
| 返程当天 | 行程总结 | Timer once |

单次出门通常 1–2 条就够；多日行程按天用一条 rrule，不要按天拆成多条 once。

### 多日行程的每日规则怎么写发卡意图

一天一张总览卡，卡上每行一程，点击回原会话：

```
prompt       先读 Thing「成都三日游」下今天的 Todo 与最新进展行。
             取当天剩余的行程点，核实需要的门票、开放时间、路线和提示。
             发一张推荐列表卡：每行一程，写名字和一句最有用的信息；
             各行 tap={"type":1,"agent_chat":{}} 回原会话，不配整卡 tap。
             卡上不要放天气块、信息格或时间轴；关键变化在摘要里说清。
             天气只有在改变了安排时才写进 summary 一句话。
             把当天已发覆盖进展行。今天已发过就不再发。
```

**一天一张是上限，不是配额**：当天没有值得看的变化就不发，只更新进展行。

## 一次性规则要留足余量

**一次性规则的 `schedule.start_at` 至少比当前钟晚 5 分钟。** 够不上就别建这条规则，
改成在回复里直接把事情说清楚。

实测过一次翻车：23:23:34 建出规则、`next_fire_at` 排在 23:25:00，只隔 86 秒，没触发。
调度按分钟粒度扫，刚启用就要在下一分钟触发，很容易漏一轮。

**取钟必须在建规则那一轮。** 同一条轨迹里，模型 23:20:44 取的钟、23:23:34 才建完规则，
中间做了十几轮工具调用。它拿 23:20 那根钟判断「还有 5 分钟来得及」，落库时只剩 86 秒。
**取钟和用钟之间会漂，漂多少取决于你中间做了多少事。**

赶时间的场景（用户说「马上」「来不及了」）先建规则再补细节，别让配图把余量吃掉。

## 结束条件

跟进期限由规则承载，写进 `rrule` 的 `UNTIL` 或 `COUNT`，**不要在指令里让模型自己数轮次**。

- 多日行程的每日规则，`UNTIL` 对齐**返程当天**，行程结束后不留空跑的规则。
- 日频天气规则的 `UNTIL` **不得超过第 3 天**——`check_weather` 只覆盖当天加未来 3 天，
  再往后规则会照常触发却永远取不到数（见 [data-sources.md](data-sources.md)）。
- 一次性规则在指令的【结束】里写明「本次结束后停用本规则」。

## 多条规则之间要能看见彼此

凌晨叫醒那种场景会建好几条规则，它们各自独立触发、互相不知道对方做过什么。
用户 01:00 已经回复「醒着呢」，02:00 那条还是会照发。

**约定**：同一个 Thing 下的规则共用**维护 Todo 的进展行**作为黑板。
每条规则触发后都往上面写一行「<时间> <规则做了什么> <用户有没有反应>」，
触发时先读它再决定要不要发。

## 失败不要静默

取数失败、卡没发出去、位置拿不到——用户完全不知道，他只会觉得「说好提醒我的，怎么没动静」。

| 这条规则的重要程度 | 失败了怎么办 |
| --- | --- |
| 关键提醒（赶飞机、赶火车、值机截止） | **必须让用户知道**。发一张 `image_text` 说明哪一步没做成、他现在该自己确认什么 |
| 锦上添花（周边推荐、景点讲解） | 静默，只在进展行记一笔 |

判据是**漏掉会不会造成实际损失**。误机会，少一条美食推荐不会。

### 连续失败就停用自己

同一个原因连续失败 **3 次**，说明这条路不通，不是偶发抖动。这时候：

1. 停用本规则，别再空跑
2. 发一张 `image_text` 告诉用户哪个能力不可用、他现在能做什么替代

**指令里必须写这一条**，否则规则会一直跑到 `UNTIL`。分钟级轮询尤其要命：
一条取不到数的规则能在一小时里白烧 60 次完整执行，每次还可能卡满超时时长。

进展行要记**失败次数和原因**，只记「本次失败」下一轮无从判断是第几次：

```
【维护】把本次结果覆盖进展行；失败时记「连续失败 N 次，原因 X」。
【结束】同一原因连续失败 3 次就停用本规则，并发一张图文卡说明哪个能力不可用。
```

## 两条不要建的规则

- **航班动态变化**（延误、取消、登机口）。`tongchengtravel` 只有静态信息，
  动态一律取不到（见 [data-sources.md](data-sources.md)）。
  建了只能空转，还会让用户以为有人在盯延误。改成出门前重算路况，或按距离提醒。
- **第 4 天及以后的天气判断**。超出 `check_weather` 的预报射程。

## 长度

整条规则序列化后不超过 **2048 字节**，超了服务端直接整条拒绝并报 `context exceeds limit 2048`。
工作指令控制在 500 字以内，七个要素写短句就够。景点名和城市写全，但不要把整份行程抄进去。
