# 确定目的地后的主动到达推荐

用户明确说这次行程**确定要去**某个城市或核心景区，或已有行程的当天主目的地已确认时，准备到达快览。仅问「某地怎么样」、比较备选目的地、查询票价、转机途经城市，不创建主动到达推荐。对话 XCard 不承载这项内容；交付通道是 `make-things v1.2` 的 `show_widget`。

先 `load_skill(skill_name="make-things")`，读取当前 Thing 与 Todo，避免同一趟旅行同一目的地重复创建或重复发卡。用行程结束、离开该目的地等已有时刻作为监测截止；没有可信截止时刻时问用户，不启用无限期规则。按目的地**类型**确定识别边界：

**一物一卡**：到新城市时，城市介绍、一个有来源的当地美食对象、一个有来源的景点对象
各用一张独立、点击回原会话的 `image_text`。默认同一趟旅行每天主动到达快览最多 3 张，
其中景点最多 1 张；内容不足就少发。用户只指定某类内容时按其要求收窄。
景点只选用户点名、已有门票或行程中明确的核心目的地；不能识别核心景点就省略景点卡，
不能把普通途经景点逐个建成 Event。多城市同日到达时只围绕真正停留的主目的地发快览，
不把转车、转机经过的地方当作新的推荐对象。
若已规划当天实地进入某景区，城市级 Event 可先发城市和美食卡，景区卡留给该景区自己的
到达 Event；同一景点已在城市快览或当天行程卡中介绍过，就不要到景区再发重复卡。
美食也检查创建轮对话正文：若同一餐厅或食物、同一建议已经展示，抵达时没有新的位置价值，
就不再投一张重复 NOW 卡；能根据抵达位置选出另一家真实餐厅时才发新卡。
如果当天景点卡已经用完，也不为下一个普通景点补建或排队发卡。用户明确提出的
单独景区提醒按用户要求处理，仍须去重。
`make-things v1.2` 不对所有 Thing 统一限制一天一张；同一次交付不能重复发同一内容。
继续复用旅行 Thing，按「城市 / 美食名称 / 景点名称」分别记录真实 `now_id`，
不要为了发多张卡另建空 Thing。已有同一目的地的显式到达推荐时，合并进这一条 Todo/Event，
按用户明确指定的内容与时机投递，不另建同地规则。

- **城市**：用完整城市名，以及可核实的城市编码或位置描述判断；到附近城市、机场仅以机场所属城市为准，不能因为机票目的地写了城市就算抵达。
- **景区**：创建前核实景区的边界或足够保守的可用围栏，在 Judge 的 `condition` 中写入实际边界/中心与半径；Todo 记录来源。仅落在归属城市或地市，不算到景区。边界不明、精度不能排除外围误判时暂不启用景区到达规则。
- 位置 Event 只表示位置发生变化；`judge.tool_call` 固定调用 `geo-location/get_last_known_location`，`tool_arguments={}`。Judge 条件做地点判断，不写缓存采集时间或防抖；该工作由下游承担。回调再用同一缓存工具复核，不请求 `get_geo_location` 实时定位。

**如果用户在创建轮已经抵达**：先调用缓存位置工具，按同一目标边界确认。可靠确认后创建或复用记录用 Todo，按不同对象分别调用 `show_widget`；
每张成功后立即把对象名称及真实 `now_id` 记入 Todo，**不建待触发 Event**。
缓存定位不可用或归属不明时按未抵达处理；不能拿用户说的目的地顶替位置。

**如果尚未确认抵达**：按下面 Demo 创建或复用 Thing/Todo，只创建一条停用的 Event + Judge，把它的真实 `trigger_id` 写入 Todo.`rule_ids`、回读后才启用。若目的地已取消或期限已到，停用规则且保持静默。
回调逐个核对对象是否已经发过；每张 `show_widget` 返回真实 `now_id` 后立即回写该对象的收据，
下一个对象才发。返回不确定时先核查，不能盲目重发；本轮处理完已发和无资料对象后停用 Event。
推荐投递不代表用户已完成旅程。

内容在启用前备好：城市介绍为一条可核实的地理/文化背景；美食对象可以是一种当地食物，
也可以是 `find_nearby kind=dining` 实际返回的一家餐厅，不能编店名、评分或人均；
景点对象从已确认的行程、景区官方介绍或可信地点资料选一个真实名称。
Web Search 可以查当地饮食、景区故事、游览建议和近期注意事项，并保存来源 URL 与查询时间；
每个对象只取一条已核实内容压成能独立读完的一句话。如运行环境没有 Web Search，
只用已核实的稳定资料，**省略当日开放、预约、交通管制等动态结论**。
Web Search 不参与 Judge，也不能补天气、门票价格、评分、人均等结构化字段。
无可核实内容时不编造卡片，先补资料。

每个城市、美食、景点对象分别发**一张 `image_text`**。标题不超过 18 个汉字，
`summary` 不超过 40 个汉字，可配一张真实 HTTPS 封面；整卡配置
`tap={"type":1,"agent_chat":{}}`，点击只回原会话，不自动发消息。
不用“点开看详情”或省略号吊起后文；用户只看卡片就应拿到完整建议。
即使 Web Search 找到多篇文章，也只选每个对象最适合此刻的一条，不变成 `recommend_list`。

## Demo A：确认去北京，到北京市后分卡快览

例句：「我 10 月 1 日去北京，10 月 4 日回程。到了北京，分别给我看看这座城市、一个当地美食和一个景点。」先创建或复用这趟旅行的 Thing；下面展示没有现成 Thing 时的 `create_thing` 参数。示例中的时间在实际调用前按本次行程年份与北京时间换成绝对时刻。已有 Thing 只新增 Todo。若用户只要一张城市介绍卡，就只发城市卡，不擅自补发美食或景点卡。

```json
{
  "title": "北京行程",
  "goal": "抵达北京市后分别快览城市、一个当地美食和一个景点；每个对象只发一张，10 月 4 日离开时停止监测。",
  "todos": [{
    "title": "抵达北京市后分卡快览",
    "schedule_info": {"kind": "MONITOR"},
    "description": "目标：北京市，城市级；截止：<本次行程10月4日的北京时间绝对时刻>；交付：城市介绍、一个北京美食对象、一个已核实的北京景点对象分别用 show_widget 发点击回原会话的 image_text，整卡 tap={\"type\":1,\"agent_chat\":{}}，内容不足就少发；若景区另有到达 Event，该景点卡可延后至实际抵达。Judge 使用 geo-location/get_last_known_location 确认北京市；回调仍用缓存位置复核。按对象名称分别记录真实 now_id，不重复发卡；进展：待触发。"
  }]
}
```

`trigger/create_trigger` 的完整 Event 参数；把占位 ID 换成前一步的真实回包：

```json
{
  "thing_id": "<真实 Thing ID>",
  "todo_id": "<真实 Todo ID>",
  "title": "到北京市后分卡快览",
  "type": "event",
  "event": {"source_id": "yb_geo_location"},
  "judge": {
    "tool_call": {"tool_name": "geo-location/get_last_known_location", "tool_arguments": {}},
    "condition": "缓存定位有有效坐标，城市编码或位置描述明确指向北京市时才命中；廊坊、天津、城市归属不明或取数失败均不命中。"
  },
  "prompt": "重读 Thing、Todo 与规则；已取消或到期则停用。调用 geo-location/get_last_known_location 复核缓存位置，确认仍在北京市；不调用实时定位。核对本次旅行当天已发快览：每天最多三张、景点最多一张；只选行程核心景点，已在行程卡或对话正文讲过同一对象与建议的跳过。按用户要求准备城市、一个有来源的美食、一个核心景点的独立 image_text，每张整卡 tap={\"type\":1,\"agent_chat\":{}}，点击回原会话且不自动发消息；景点有单独的景区 Event 就留到实际进入景区时发。美食可用已核实当地食物或 find_nearby kind=dining 的真实餐厅，景点从行程或可信资料取名；无资料不发。每张标题不超过18字、摘要不超过40字，卡上说完整。每发一张拿到真实 now_id 就用最新 Thing 版本按对象回写 Todo；下一个对象先重读收据，已发跳过。结果未决先核查、不重发。本轮处理完停用 Event，推荐不等于完成旅程。"
}
```

抵达后 `show_widget` 的**三张独立卡**参数形状如下。每张只讲一个对象；
示例文案只说明布局，实际内容须与本次核实的资料一致，缺资料就省略对应卡。
三张都配置整卡 `tap` 回原会话，不另配详情按钮：

```json
{
  "card_type": "image_text",
  "title": "到北京了，认识一下这座城市",
  "summary": "从中轴线到胡同，北京的历史街区适合慢慢走、慢慢看。",
  "source": {"label": "北京行程"},
  "thingId": "<真实 Thing ID>",
  "todoId": "<真实 Todo ID>",
  "data": {},
  "tap": {"type": 1, "agent_chat": {}}
}
```

```json
{
  "card_type": "image_text",
  "title": "北京美食｜烤鸭",
  "summary": "想尝北京烤鸭，可按当前位置找一家真实餐厅。",
  "source": {"label": "北京行程"},
  "thingId": "<真实 Thing ID>",
  "todoId": "<真实 Todo ID>",
  "data": {},
  "tap": {"type": 1, "agent_chat": {}}
}
```

```json
{
  "card_type": "image_text",
  "title": "北京景点｜故宫博物院",
  "summary": "可把故宫列入参观计划，出发前核对官方开放信息。",
  "source": {"label": "北京行程"},
  "thingId": "<真实 Thing ID>",
  "todoId": "<真实 Todo ID>",
  "data": {},
  "tap": {"type": 1, "agent_chat": {}}
}
```

若故宫就是本次行程中已规划的**景区级到达目标**，这张景点卡不在北京市到达时抢先发，
而是在景区 Event 真正命中后作为该景点的一张卡发出；同一对象不重复。

## Demo B：确认去赛里木湖，到景区后发相关推荐

例句：「10 月 7 日去赛里木湖，10 月 8 日离开。到了景区给我推荐怎么看，有需要注意的也告诉我。」先核实**赛里木湖景区范围**、至少一条可用的景区游览建议和来源。下面的边界占位符必须在**创建 Judge 前换成实际核实的数值或范围**；不能把占位符、Todo 引用或「到博乐市」写进已启用 Judge。

`create_thing`：

```json
{
  "title": "赛里木湖行程",
  "goal": "确认抵达赛里木湖景区后发一次有来源的游览推荐；离开景区的行程结束时停止监测。",
  "todos": [{
    "title": "抵达赛里木湖景区后推荐游览",
    "schedule_info": {"kind": "MONITOR"},
    "description": "目标：赛里木湖景区，景区级；景区边界或保守围栏：<已核实数值与来源>；截止：<本次行程10月8日的北京时间绝对时刻>；内容：<已核实的一条景区游览建议及来源URL、查询时间>。Judge 和回调均使用 geo-location/get_last_known_location 缓存位置，不调用实时定位；只有确认进入景区才发一张点击回原会话的 image_text NOW 卡，整卡 tap={\"type\":1,\"agent_chat\":{}}，标题不超过18字、摘要不超过40字，记录真实 now_id。Web Search 的动态事项要在发卡时重新核实，取不到就省略。进展：待触发。"
  }]
}
```

`trigger/create_trigger`：

```json
{
  "thing_id": "<真实 Thing ID>",
  "todo_id": "<真实 Todo ID>",
  "title": "到赛里木湖景区后推荐游览",
  "type": "event",
  "event": {"source_id": "yb_geo_location"},
  "judge": {
    "tool_call": {"tool_name": "geo-location/get_last_known_location", "tool_arguments": {}},
    "condition": "缓存定位有有效坐标，且同时位于<创建前已核实的赛里木湖景区边界或保守围栏数值>、位置描述能确认属于赛里木湖景区时才命中；只在博乐市或博州、景区外围、边界或精度不明、取数失败均不命中。"
  },
  "prompt": "重读 Thing、Todo、景区边界及来源；该景点已发、取消或过期则停用。核对本次旅行当天已发快览：主动推荐满三张或景点已发一张时不发；用户明确点名本景区提醒则按要求处理且去重。调用 geo-location/get_last_known_location 复核缓存位置，确认仍在赛里木湖景区，不调用实时定位。优先用 Todo 中有来源的内容；如可用 Web Search，可核实近期官方注意事项并记录来源与时间，查不到就不写动态。只选一条可核实且此刻有用的建议，用 show_widget 发一张 image_text：标题不超过18字、摘要不超过40字，卡上说完整，整卡 tap={\"type\":1,\"agent_chat\":{}} 回原会话，不加详情按钮；有真实封面才加图。无可信内容不发卡。只有拿到真实 now_id 才记该景点已发并停用 Event；结果未决先核查，不重发。"
}
```

景区到达快速推荐的 `show_widget` 形状。此处文案仅演示长度和展示方式，实际投递时须用
当次已核实的建议替换，并按真实来源填写 `source.label`：

```json
{
  "card_type": "image_text",
  "title": "到赛里木湖了",
  "summary": "先确认景区当天开放的游览区域，再选路线。",
  "source": {"label": "<本次核实的来源简称>"},
  "thingId": "<真实 Thing ID>",
  "todoId": "<真实 Todo ID>",
  "data": {},
  "tap": {"type": 1, "agent_chat": {}}
}
```

配置回原会话的整卡 `tap`，不加详情按钮；不把 Web Search 结果拆成列表，也不把开放状态、
预约要求或路线变化当作静态事实。真实封面可作为 `data.cover.url` 加入；
没有图片仍照常发这张无图卡。

## 两个 Demo 共用的启用步骤

Event 先保持停用。调用 `write_todos` 保留该 Todo 的完整 `description` 与
`schedule_info={"kind":"MONITOR"}`，把 Event 的真实 `trigger_id` 写入 `rule_ids`；回读核对后调用
`trigger/update_trigger(enabled=true)`。若创建时已经确认到达，直接发卡并记录收据，**不创建** Event。
截止时刻留在 Todo，Event 命中后的回调先检查是否过期；当前 Event 没有原生截止字段，
若始终没有地点命中，规则不会仅因到期而自动停用，不能承诺自动清理。

## 连续体验 Prompt

1. 「这趟我 10 月 1 日到北京，10 月 4 日回。到了北京，分别用小卡片给我看看这座城市、一种当地美食和一个景点，每张只讲一个。」
2. 「这趟之后还会在 10 月 7 日去赛里木湖，8 日离开。到了景区后，推荐怎么玩，顺便看看有没有需要注意的。」
3. 在测试环境分别提供**北京城市内**与**赛里木湖景区内**的 `yb_geo_location` 事件和缓存定位。北京应按城市、美食、景点分别发最多三张短卡，赛里木湖只发该景区的一张；内容不足就少发。廊坊或博乐市的定位不应触发。
4. 重复投递同地事件，观察 Todo 对每个对象记录了 `now_id` 后是否跳过该对象；取消行程时停用，过期后若 Event 命中则静默停用。

测试环境若没有真实定位事件、可信景区边界或已绑定的 `get_last_known_location`，单靠聊天中说「我到了」不足以证明命中；不能伪造成功卡片。
