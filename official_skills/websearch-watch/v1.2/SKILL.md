# websearch-watch 1.2

使用网页搜索持续关注用户指定的对象和条件。天气、股价、新品发布都使用同一套流程，不需要划分类型。

本 Skill 只负责明确监控对象、命中条件、网页搜索参数和命中后的内容。Thing / Todo / Trigger 的创建、更新、状态与卡片交付统一遵循 `make-things`，不要在这里另维护创建流程。

新建监控先完成下方信息检查，信息齐全后再加载当前 Agent 配置的 `make-things`；修改已有监控时先加载它并读取原对象，不在指令中写死旧版本；本方案依赖已部署的 v1.2 创建与卡片契约，创建和 Trigger 执行 Agent 的配置都须对齐。取数只用实际已加载的 `web_search`，参数以其工具 Schema 为准，不通过公网搜索内部工具定义。

## 先确认再创建

先检查对象、条件和检查时刻。只有“提前一晚／晚上”等模糊时段时，先问具体几点；未补齐前不加载 make-things、不读 reference、不取钟、不创建。用户补齐后直接进入创建流程，不重复确认已有答案。

1. **对象**：用户要关注的地点、公司或股票代码、产品或话题。
2. **条件**：按用户原话写清关注内容、阈值和时间范围，例如「上班时下雨」「股价大于 450」「公布正式售价和上市时间」。
3. **检查时间**：沿用用户指定的时间、频率和范围。缺少必要的检查时刻时先问，不擅定每天 08:00、19:00 或 21:00。一次性“明天”按请求时的日期和时区固定；周期监控的“今天／明天”按每次执行日及约定时区计算，不能固定成创建当天算出的日期。未指定结束时间，不自行增加截止日期。

## 创建与规则内容

每个监控任务对应一条 Todo 和一条带 judge 的时间 Trigger。Todo.schedule_info 使用 MONITOR 表示持续监控；具体检查时刻独立写入 Trigger.schedule。

加载 make-things 后，按其要求读取创建 reference，再选择创建路径。明确新建、一个 Thing / Todo / 时间 Trigger 且依赖已就绪时，使用其快捷创建；补充尚未创建请求的信息仍属新建。其余情况按 make-things 处理，不额外前置搜索或复制一套创建顺序。

- `judge.tool_call.tool_name` 使用实际加载的 `web_search`；`tool_arguments` 遵循当前工具 Schema，搜索词含对象、关注内容及目标日期范围。滚动查次日天气可用“北京明天天气预报”，condition 和 prompt 均按本次执行日的次日解释，不在搜索词中写死某一天。
- `judge.condition` 按用户条件写清命中口径，不自行增加降水概率等阈值。查询失败、超时、异常或证据不足按查询失败处理，既不当作命中，也不当作未命中，不发送条件命中提醒；不能写成“查询失败按有雨处理”。
- 顶层 `prompt` 写命中后的执行与交付，不使用旧 `judge.prompt`、`instruction`、`trigger_kind`、`dtstart` 等字段。

## 命中后的交付

以下要求写入规则 prompt，供未来执行使用；创建时不读取 show-widget reference、不提前发送命中卡。

规则 prompt 必须明确：加载执行 Agent 配置的 make-things，重读绑定的 Thing / Todo 核对状态和用户要求；按本次证据给出简短结果，并遵循其 show-widget reference 发布一张无图摘要 Now 卡。普通网页监控不需要专门天气卡型、搜图或创建 App。

卡片使用真实 Thing / Todo ID 关联，source.label 使用 Todo 名称，提供“看详情”回到本会话；具体字段只在 make-things 中维护。会话详情写清对象、目标日期、命中事实及来源，卡片摘要自含结论。拿到真实 now_id 才算卡片发布成功。无命中不发卡，查询失败不伪装命中；创建成功本身不提前发送命中卡。

judge 命中后，执行 Agent 仍须调用 `web_search` 获取本次交付所需的最新详情和来源，例如降雨时段、雨量和预报日期。judge 负责判断是否进入执行，执行侧搜索负责取得交付内容；不能仅凭 judge=true 编造详情。搜索结果仍支持用户条件时，给出简短说明并调用 `show_widget` 发布 Now 卡；条件已不成立、查询失败或证据不足时，不发送命中提醒。

提醒发出不代表持续监控任务完成；状态、进展回写和失败处理沿用 make-things。

## 示例：选择创建或更新路径

以下假设北京时间已明确、web_search 已可用；工具参数与字段格式遵循 make-things，不照抄占位 ID。

### 1. 信息齐全：带 judge 也能快捷创建

用户：「每天晚上 19 点查北京明天的天气，有雨就提醒我带伞，带上雨量。」

执行：加载 make-things 并读取创建 reference；不先 get_thing、不预查今天的天气。调用 create_thing 携带一个 MONITOR Todo，再用真实回包 ID 调用 trigger/create_trigger，设置 bind_and_enable=true。schedule 为每天 19:00，起点按可信当前时间确定；judge 用 web_search 判断北京次日预报是否有雨，不另加概率阈值。

规则 prompt 示例：「加载 make-things，重读绑定任务确认仍需执行。用 web_search 查询北京时间次日的北京天气，获取降雨时段、雨量和来源。证据仍支持有雨时，提醒明天带伞并说明雨量；查不到雨量就注明未提供，不编造。按 make-things 的卡片规范调用 show_widget，发布关联本任务的无图摘要 Now 卡，并在会话给出来源。无雨或查询失败不发送命中提醒。回写检查进展，保持持续监控。」

两步创建成功后：「已设置每天 19:00 检查北京次日天气，有雨时提醒你带伞并附上查到的雨量。」创建时不提前发命中卡。

### 2. 补充时间：仍是新建，不搜索旧事项

用户：「帮我盯北京天气，第二天有雨就提前一晚提醒带伞。」
助手：「每天晚上几点检查并提醒你？」（此时不加载 make-things、不读 reference、不取钟、不创建。）
用户：「19 点，带上雨量。」

执行：信息已齐，按例 1 快捷创建。不再确认“是不是只在下雨时提醒”，不因这是后续回复而查询同名 Thing。

### 3. 修改已有监控：更新原对象

用户：「把刚才那个北京天气监控改成每天 20 点。」

执行：用上下文中的真实 ID 读取原 Thing 和 Trigger，按 make-things 更新原规则时间，保留原对象、条件及 web_search＋show_widget 交付要求。不是新建，不调用 create_thing；没有可信 ID 时才查询定位。

## 修改与停止

改条件、对象或检查时间：先重读 Thing 和 Trigger，用 `write_todos` / `trigger/update_trigger` 改现有规则，不删除重建。用户叫停：先停用或删除 Trigger，再按 `make-things` 更新 Todo 状态；暂停或取消不标为完成。提醒发出、规则命中不等于 Todo 完成。持续命中是否去重尚未确认，不要承诺只通知一次。
