# 字段怎么写

创建或更新对象前读这份，本轮已读则复用。字段格式对快捷创建和普通创建同样适用，执行步骤按所选路径使用。

字段类型、枚举和格式见对应工具 Schema，本文不重复定义；这里只写填写原则和示例。

---

## 1. 事项 Thing

`goal` 是后续每次执行时重读的唯一依据，写不全会导致规则跑起来时缺上下文；它每轮投递都会进上下文，按三类写：**硬约束与行动基线**（材料清单、预算、红线日期）留全量；**调研事实**只留结论；**执行时会重新查证的资料**（电话、地址、链接）留一句索引，不抄全文。滚动的进展只记在 Todo 说明的进展行（覆盖式），goal 只在事实变更时更新。

除了 Schema 说的目标、范围、硬约束，还要记**查证过的事实修正**——用户说"港澳居住证我办好了"属于事实变更，写进 `goal`，不写任务说明。具体执行明细留在原方案里，不入库。

---

## 2. 任务 Todo

### `title` 里不写时间

时间由四个位置承载（见「时间写在哪个字段」），塞进标题会造成多处重复，改期时容易只改一处。

| | 写法 |
| --- | --- |
| 差 | 每日 20:30 打卡：推进当天 RAG 学习任务 |
| 好 | `title`：推进当天 RAG 学习 + `schedule_info.time.time_of_day`：20:30 |

时间、频率、周期一律不进 `title`——「每周推送」「每天监控」这类频率词由 `schedule_info` 和规则承载，标题里重复会让界面同一信息出现两次。

| 差 | 好 |
| --- | --- |
| 每周推送AI生图新玩法简报 | AI生图新玩法简报 |
| 每天 08:30 三餐打卡 | 三餐打卡 |

### `schedule_info` 每条任务都要填

字段格式参考 `write_todos` 工具的 `todos[].schedule_info` Schema，`create_thing` 使用相同格式。若该工具 Schema 尚未加载，先加载其定义，无需执行 `write_todos`。

每月使用 `time.cycle="MONTHLY"` 与 `time.month_days`，例如 `[1,15,31]`，同时填写 `time_of_day`。日期数组取值 1–31、升序去重；当月不存在的日期跳过。`time.date` 仅用于 ONCE，不再用锚点日期表示每月几号。更新完整 Todo 快照时保留未修改的 month_days。

Schema 的 `required` 里没有它，**但服务端实际必填**——省略或传空对象会被拒。工具的外层 required 是否声明不改变服务端的业务校验。

| 情况 | 怎么填 |
| --- | --- |
| 有日期或钟点、有周期 | `kind=TIME`，`time` 必填 `cycle` 和 `time_of_day`；单次再加 `date` |
| **相对期限**（行前 / 出发前 / 提前 / 截止） | 也算安排，同样写 `kind=TIME`。**先拿到锚点日期**（用户给出的，或用户明确接受的假设），再换算成绝对 `date` |
| 条件监测 | `kind=MONITOR`，不填 `time`，监测目标写进 `description` |

三条不能做的事：

- **锚点日期未知时先问，不要创建缺安排的任务**。「出发前三天提醒」而用户没说哪天出发，就先补齐出发日期。
- **不得用 `MONITOR` 代替时间未定的普通待办**。`MONITOR` 是条件监测，不是「还没定时间」的占位。
- **「不用提醒我」只表示不建 Trigger，不表示任务本身没有安排**。这种情况照样填 `schedule_info`，只是不配规则。

事项本身有日期、钟点、周期或相对期限的业务安排时，`schedule_info` 写 TIME；纯事件监测写 MONITOR。事件发生时间、检查时间和进展记录中的日期不是定时安排，不因此改成 TIME。

`expected_version` 沿用最新查询回包里的版本**字符串**（如 `"1"`），不要转成数字。

### `status` 的三条补充

- **没有"跳过"这个状态**。用户说"这条不做了"走删除，不是标完成。
- `PENDING_CONFIRMING` 同时承载两种等待：等用户授权、等用户回报结果。
- 暂停或取消**不能**标成 `DONE`。

### 快捷创建的输入和展示字段

`create_thing.todos` 可选；传入时长度必须恰好为 1。只含 `title`、可选简短 `description`、`schedule_info`，不填 todo_id、status、rule_ids。工具生成稳定 ID、PENDING 和空规则引用，并按既有消费契约补说明格式；下一步 `create_trigger(bind_and_enable=true)` 绑定并启用。没有启用回执不能说提醒已生效。

`schedule_info` 的格式复用 `write_todos.todos[].schedule_info`，服务端仍须在写入前校验。展示与触发时间的区别见本文件第 4 节。不新增 write_todos Schema 中不存在的字段；展示文案依据 Todo 自身安排生成，不取 Trigger 的提醒时间代填。

### `description` 普通流程固定六行

Schema 只说它是"供用户查看的事项说明"。实际要按固定六行写，缺项省略。**标签用词不能自造**——界面从这里取文案展示给用户。

```
内容：完整说清这次要做什么、对什么做、输出什么
由谁做：元宝 / 你 / 元宝和你
完成标准：做到什么算完成
时间：业务上哪天前要做完
结果确认：要不要问结果、什么时候问
进展：当前状态 + 累计量 + 最近一次时间
```

七条硬要求：

| 要求 | 说明 |
| --- | --- |
| **不用第一人称代词** | "由谁做"写"元宝""你"，不写"我"——用户视角和 Agent 视角的"我"指代冲突 |
| **"时间"只写业务截止** | 事项时刻在 `schedule_info`、时间重复规则的跟进期限在 `schedule.rrule` 的 `UNTIL`，都不写进这里。持续监控类没有业务截止就省略这行 |
| **"进展"覆盖不追加** | 只留当前状态、累计量、最近一次时间。历史数据（体重逐条、投递记录逐条）不堆进来 |
| **有约定就有落点** | 写了"会问你结果"必须有对应的规则安排；写了业务截止要检查规则时间是否配套 |
| **短句，人能读懂** | 不写字段名、不写枚举值、不写内部标识——用户会在卡片和详情页看到原文 |
| **「内容」行不写时间和频率** | 时刻、周期、频率由 `schedule_info` 和规则承载，「内容」行只写做什么的语义。写了时间会和界面显示的 schedule 信息重复 |
| **六行合计 80 字以内** | 用户在移动端详情页读，字越多越看不了。「内容」行一两句话，细节由触发规则的工作指令承载 |


### 四类完成约定

"完成标准"这行决定执行后怎么回写：

| 类型 | 完成标准怎么写 | 执行后 |
| --- | --- | --- |
| 仅提醒 | 提醒发出即本次结束 | 一次性的置完成；循环的保持进行中 |
| 元宝代办 | 出票成功才算完成，仅选好航班不算 | 交付成功置完成；执行到需授权处转待确认 |
| 跟进用户办事 | 你报数即算本周完成 | 转待确认等反馈；超时回进行中并记一次未反馈，**不重复追问** |
| 重复任务 | 本周完成三次即算 | 更新进展行；本轮完成不结束整条 |

"由谁做"的对应关系：只提醒 → 你；元宝代办 → 元宝；需要用户确认或回报 → 元宝和你。

### 一次建几条

判据：**这部分单独完成、改期、暂停或取消时，用户需不需要单独管理它**？需要就独立一条，不需要就并进上一条。

四类不拆：

| 不拆什么 | 用户说的 | 合成一条 |
| --- | --- | --- |
| 步骤 | 深蹲 3 组、臀桥 3 组、平板支撑 3 组 | 每周三次力量训练 |
| 渠道 | 小红书发一遍、抖音也发一遍 | 每周发一条内容 |
| 重复次数 | 连续 30 天打卡 | 每日打卡（次数由规则的 `schedule.rrule` 承载） |
| 授权动作 | 选航班、报给我看、我确认后下单 | 盯机票，确认后下单 |

**自动提炼控制在 5 条以内**。这个上限约束的是从长方案里主动提炼的首批任务；用户明确点名 7 条就建 7 条，不能静默漏掉点名的事项。

场景 Skill 给出长方案时，先剔除做不了的，再按近期需要、用户明确点名、是否值得单独管理来选。用户明确要更多时，先列清单确认再分批建。

## 3. 触发规则 Trigger

### 先选 type，再选是否需要判断

`trigger/create_trigger` 必填 thing_id、todo_id、type、prompt；type=schedule 时只填 schedule，type=event 时只填 event。工具默认只建停用规则、不绑定。`bind_and_enable=true` 时建好、追加到 Todo.rule_ids 并启用，只支持 type=schedule 且 Todo 已存在。Todo 还没写入时先停用建好，一次 write_todos 写齐本批任务及关联，再逐条 `update_trigger(enabled=true)` 启用。用户要求暂不执行、依赖未就绪，或可能在任务写入前立即触发时保持停用。

| 来源 | 模型填写 | 适合的场景 |
| --- | --- | --- |
| 时间 | schedule.start_at；重复再加 schedule.rrule，时区可省略 | 明早提醒、每周检索 |
| 真实事件 | event.source_id 固定可选 yb_geo_location | 已接入的位置事件（本期仅此一种） |

执行指令始终放在顶层 `prompt`。`judge` 仅含 `tool_call` / `condition`：触发后还需要额外取数判断时才加；本期 Filter 固定在 Tool Proxy，模型不填写。时间规则也能有 judge，事件规则也能有 judge；是否由用户执行与是否有 judge 无关。

- 事件源 ID、数据字段和授权范围必须来自实际契约，不能猜。没有事件来源就说明缺口；轮询仍写 schedule + judge，不宣称实时订阅。
- 本期仅支持 yb_geo_location；不向模型暴露 filter。Tool Proxy 固定 `$.data.uid != null && $.data.uid != ""`。不检查 location、不推断位置结构。
- 本次事件数据与 prompt 分开。收到事件不代表到家、离家或移动；信息不足时不编造位置和状态。
- 不承诺冷却、只报一次或暂停期间事件补发；重复上报与业务去重按已验证能力处理。EVENT 没有 UNTIL，需自动到期时另行落实关闭机制。

### `judge.tool_call` 选取

- **参数要在执行时仍然有效**，不写死会过期的临时 ID。
- **区分固定日期与滚动日期**：一次性“明天”按请求时的日期和时区确定目标日期；每天查“明天”则按每次执行日取次日，查询参数、condition 和 prompt 保持同一口径，不能写死创建当天算出的日期。工具支持相对日期时使用其支持的写法；只接受绝对日期时改用到点执行，在执行时计算日期后查询，不编造日期变量。
- **只承载一次取数调用**。要多次取数说明条件过复杂，该拆成多条规则或改用到点执行。

### `judge.condition` 四类写法

Schema 只说"写清对象、阈值及必要口径"，这覆盖不了后三类。

**查询失败不等于命中，也不等于未命中。** 超时、报错或缺少判定证据时按查询失败处理，不发条件命中提醒；不能把“查不到天气”写成“按有雨处理”。

**数值阈值**——必须有：对象、比较字段、比较符、数值、单位、是否含税。

| 差 | 好 |
| --- | --- |
| 价格便宜一点 | XX 酒店 2026-11-20 入住、大床房、含税总价 ≤ 800 元 |
| 降价了 | 当前价格低于 description 进展行里记录的上次价格 |

**有无新增**——必须有：比对基准（跟上次检查比还是跟某清单比）、什么算"新"、什么算"匹配"。

| 差 | 好 |
| --- | --- |
| 有合适的岗位 | 检索结果中存在发布时间晚于上次检查、地区含广州或深圳、职能为产品的岗位 |
| 有新消息 | 该公众号发布时间晚于 description 进展行记录的上次检查时间的新文章 |

**状态变化**——必须有：关注哪几个状态、从什么变到什么算命中、只报首次跃迁还是每次都报、到终态后停不停。

| 差 | 好 |
| --- | --- |
| 航班有异常 | 航班状态由正常或计划变为延误或取消时命中，只报首次变化；状态变为已落地后停用本规则 |
| 快递到了没 | 物流状态变为已签收时命中；变为派送中时也报一次；已签收属终态，报完停用本规则 |

已签收、已落地等终态若已完成委托，应停用无用途的规则。时间型否则可能继续轮询到 UNTIL；事件型没有 UNTIL，不承诺自动到期。

**语义判断**——必须有：判断对象、判定要点、模糊时宁可报还是宁可不报。

| 差 | 好 |
| --- | --- |
| 有重要邮件 | 邮件正文出现面试安排、面试时间或面试官联系方式之一即命中；仅提到"已收到简历"不算；判不准时按命中处理并在告知时说明不确定 |
| 是不是好机会 | 岗位描述中要求的年限 ≤ 3 年且不含"需要 985 硕士"这类硬门槛即命中 |

**有无新增与状态变化需要可靠的比较基准。** 命中后的 prompt 可以回写进展，但 judge 未命中不会执行 prompt，不能靠其中一句话保证每轮都更新检查时间。需要每轮更新时采用按时直接执行，或使用已经实现的取数/判断状态存储；不要承诺尚不存在的状态维护。

### 更新连带：改哪样就连带更新什么

先按 Thing 与 `rule_ids` 重读关联 Trigger，判断本次改动影响哪些规则。**写完任务还要继续更新受影响的规则——只保存任务不算调完。**

| 改什么 | 连带要做什么 |
| --- | --- |
| **改标题或说明** | 检查规则的名称、投递内容、判断条件、取数参数是否仍符合；只改措辞不影响规则含义时保留原配置。**投递内容里的发卡意图也要一起看**——事项性质改变时同步卡片内容；提醒与结果交付都默认发卡，只有明确静默、纯记录或无结果等情况才不发 |
| **改安排** | 按原有提醒要求更新规则时间，如保留"提前半小时"；不把所有规则时间直接改成任务时刻；与本次改期无关的规则保持原样 |
| **暂停** | 停用继续推进该事项的规则。只关某一条提醒时改那条规则的开关，任务状态不变 |
| **恢复** | 重新检查时间和依赖，只启用本次需要恢复的，不启用全部停用规则 |
| **完成** | 停用已无用途的提醒或监测；用户明确要求的后续动作保留 |
| **用户回报进展** | 更新说明里的进展行（**覆盖不追加**），并判断是否要改后续规则 |

同类修改使用 `trigger/update_trigger`。未传顶层字段保持；schedule、judge 传入时整体替换。schedule 省略 rrule 变单次、省略 timezone 恢复北京时间；改期前先查询并保留其他子字段。judge=null 清除判断但保留 prompt。本期 event 没有可更新配置，仍可修改 prompt、judge、title、enabled。更换类型须暂停旧规则、创建新规则（不传 bind_and_enable，保持停用）、迁移绑定、启用新规则、取消旧规则并移除旧引用；不是原子切换，不承诺事件补发。


### 工作指令怎么写

顶层 `prompt` 写给未来那一次执行的 Agent，添加或清除 judge 都不搬运这段指令。Schema 已说要写清目标与上下文、不依赖历史指代、依赖 Skill 时写明先加载。除此之外七件事都要有，实际写作时不必带标签：

> **为什么这段文字这么重要**：投递是把这段原文送进会话、唤起一次全新的执行。那一次 Agent 看不到创建时的对话，**这段文字就是它拿到的全部指令**。写漏什么，执行时就一定缺什么，而且事后很难查——现场已经过去了。

```
【定位】先读取 Thing「<真实标题>」下 Todo「<真实标题>」的最新 description 与状态。
【业务】<做什么>。使用 <实际 Skill / 工具名称>，数据范围 <范围>，产出 <形态>。
【无结果】<没有符合条件的结果时：静默记录不通知 / 报一句本次没有>。
【维护】完成后 <更新什么>；进展行 <怎么覆盖>；<哪条规则该停 / 该留>。
【结束】<本次结束 / 继续下一轮>，<命中后停用还是保持启用>，<到什么时候停>。
【边界】只在已授权范围内操作；<需要确认的动作> 停下等用户确认。
【卡片】投递时 Now 里发什么卡：卡型 + 标题要点。会话里的详情不用写在这里，它就是业务部分的执行结果。纯记录类投递写「不发」。
```

工作指令写短句，通常 500 字以内，七个要素各一两句就够。红线：`prompt` 单字段 2048 字节封顶；`judge.condition` 与 prompt 共享整条规则的 context 预算，**条件越长，指令越要短**，合计超限整条被拒（由适配器按环境实际配置校验）。别把条件写成第二篇指令，Schema 的字符数不能替代 UTF-8 字节预算。

五条要求：

- **指令里不含凭据**。账号、密码、token 一律不写。
- **维护不等于扩大授权**。用户授权查岗位，不代表授权投递；授权看日程，不代表授权支付。
- **不因创建时加载过 Skill、带 `judge` 或话题涉及邮件就自动要求加载**，也不发明斜杠语法或占位假名称。后台确实需要该能力时才显式写加载。
- **本技能自己不用写加载。** 投递后唤起的那次执行会自带长程任务技能（要重读和回写对象，本来就需要它），`show_widget` 也在同一个包里。**只有垂类能力**（岗位检索、机票查询、菜谱等）才要写「先加载【实际 Skill 名称】」。
- **引用 goal，不整段复述**。告知要点、偏好、材料基线这类 goal 里已记的要求，指令写「按 Thing goal 记录的 X」——重读 Thing 时本来就会拿到 goal，复述会在改 goal 时漏改指令。

**关于【卡片】这一项**

投递靠两条通道同时触达：**Now 里一张缩略卡**（`show_widget`，标题加关键信息）＋**会话里的详细内容**（分析、方案或产物，由指令的业务部分决定）。Trigger 投递后默认必须调用 `show_widget`，会话文字不能代替 Now 卡；只有明确静默、没有用户交付或同次交付已成功发卡才免发。上层场景有卡片方案时执行该方案，不额外补默认卡；仅有发卡安排不算已发布。结束前按 `references/show-widget.md` 自查。

| 这条规则投递什么 | 指令里怎么写 |
| --- | --- |
| 到点提醒、定期询问 | 「…发一张提醒卡，标题写提醒事项」 |
| 条件命中（降价、新岗位、异动） | 「…命中后发一张图文卡，标题写结论，摘要写关键数值」 |
| 定期产出（周报、清单） | 「…发一张图文卡放标题与要点，详细报告写在会话回复里」 |
| 纯记录、无需打扰 | 明确写「不发卡」；监测无新增、条件不成立时也静默 |

具体判断见 `references/show-widget.md`。到点提醒和定期询问本身就是本次交付，即使文案相同，不同约定时刻也应分别提醒；监测没有新结果则不发。同一次交付已成功发布，不再补发；结果不确定不自动重试。默认无图 `image_text`：source.label 填本次真实任务名称，actions 带「看详情」按钮，按钮和整卡均回到会话；不为发卡额外找图片。

哪些动作要在执行时停下等确认：

| 动作 | 是否需要确认 |
| --- | --- |
| 查询、检索、整理、告知 | 不需要 |
| 拟写草稿 | 不需要，但不发送 |
| 下单、支付、发送、提交、删除 | **需要**，停下等确认 |

日程授权不等于支付授权。不要写"直接帮我买""自动发出去"，除非用户明确要求且授权链完整。

七条反例：

| 反例 | 问题 | 改法 |
| --- | --- | --- |
| 「按之前说的做」 | 执行时读不到"之前" | 写全业务内容 |
| 「提醒用户带伞」（无维护） | 提醒发了，Todo 永远停在原状态 | 补"提醒后本次结束，标记完成并停用本规则" |
| 「查到降价就订」 | 越过授权边界 | 改为"告知用户并附入口，确认后才订" |
| 「用工具查一下」 | 没有真实工具名，执行时无从加载 | 写实际 Skill / 工具名称 |
| 「持续关注岗位情况」 | 没有结束条件，永久运行 | 补"到什么时候停 / 命中后是否继续" |
| 没写无结果时怎么办 | 没料的日子会凑内容 | 补"无新增不通知，只记录检查时间" |
| 把「更新 Todo」写成唯一动作 | 用户什么也没得到 | 业务动作与维护都要写 |

## 4. 时间写在哪个字段

Schema 按字段分别定义了格式，但没给出四个位置的分工。写重了改期时容易改漏：

| 位置 | 记什么 | 例子 |
| --- | --- | --- |
| `schedule_info` | 事项本身发生的时刻 | 每天 7:00 起床 |
| 规则的 `schedule.start_at` | 什么时候提醒或执行 | 6:30 提醒 |
| `description` 的「时间」行 | 业务截止，哪天前要做完 | 12 月 14 日考试 |
| 规则 `schedule.rrule` 的 `UNTIL` | 这条规则跟进到哪天停 | 跟到 12 月 14 日 |

时间规则的跟进期限由 schedule.rrule 承载（`COUNT` 与 `UNTIL` 按用户说法选），**别把期限写进工作指令让模型自己数轮次**。

纯事件监测使用 `schedule_info.kind=MONITOR`，不填 time；event.source_id 描述事件来源，不冒充 Todo 时间。EVENT 不接受时间型 UNTIL。

**受托自动跟进时，`schedule_info` 与 `rule_ids` 成对**：填了时间安排且用户要求自动跟进的任务必须配规则；用户明确不要提醒或自动执行时保留安排，不建规则。计划类内容（每天背单词、每周模考）默认留在计划正文里，**不建成「有 schedule 没规则」的任务**——界面会显示时间而到点没有任何动作。

## 5. 创建流程示例

两种调用路径各示范一次，选择条件见 SKILL.md「创建」。示例日期假定当前为 2026-09-26、用户时区为 Asia/Shanghai；实际使用用户指定时间和真实回包 ID。

### 快捷创建 · 明天 8:00 提醒喝水

用户要求创建一个一次性喝水提醒，时间已明确。先调用一次不带 keyword 的 `get_thing`，本轮已查则复用结果；若已有相同目标、时间的安排则复用，不重复创建，也不为查重追加关键词搜索。本例查询后无匹配，继续调用 `create_thing`：
```json
{"title":"喝水提醒","todos":[{"title":"喝水","description":"只提醒，无需用户回报；提醒发出即完成本次任务。","schedule_info":{"kind":"TIME","time":{"cycle":"ONCE","date":"2026-09-27","time_of_day":"08:00","timezone":"Asia/Shanghai"}}}]}
```
再用回包 ID 调用 `trigger/create_trigger`：
```json
{"thing_id":"<返回的 thing_id>","todo_id":"<返回的 todo_id>","type":"schedule","schedule":{"start_at":"2026-09-27T08:00:00","timezone":"Asia/Shanghai"},"prompt":"重读本任务；提醒用户喝水并按卡片约定触达。确认提醒发出后记录进展、完成本次提醒任务并停用本规则；不代表用户已喝水，无需回执。","bind_and_enable":true}
```

### 普通创建 · 批量跟进减脂方案

一个事项包含 4 条任务、4 条时间规则。

**输入**：场景 Skill 给出一份含 21 条执行动作的减脂方案。

用户已同意跟进以下 4 项；只说了"早上/晚上"的按 SKILL.md「缺信息怎么办」的默认钟点建，回复里说明可改。任务标题不重复写时间、频率：

| 任务 | 说明要点 | 规则 |
| --- | --- | --- |
| 力量训练 | 由谁做：你。完成标准：本周完成三次即算。结果确认：每周日问一次完成几次 | type=schedule，每周日晚 |
| 饮食安排 | 由谁做：元宝。完成标准：出一份含采购清单的周菜单 | type=schedule，每周日 |
| 称重记录 | 由谁做：你。完成标准：你报数即算本周完成 | type=schedule，每周一早 |
| 复盘调整 | 由谁做：元宝和你。完成标准：给出下一周的调整建议 | type=schedule，每周日 |

要点：

- 上述每周安排使用 WEEKLY；Todo 写任务安排，Trigger 写已确认的提醒或执行时间。不要虚构 BIWEEKLY 等 Schema 中没有的周期。
- **21 条动作不全建成任务**。训练的组次重量、每天吃什么，留在原方案里不入库。
- 硬约束（当前体重、目标、忌口、可用器械）写进事项的 `goal`，不重复写进每条任务。
- 饮食安排需要已加载的菜谱能力。**没有就说明缺口、只建剩下 3 条**，不整批放弃，也不悄悄降级成"提醒你自己做饭"。

按以下顺序完成创建：
1. 按普通流程定位事项，确认是新目标后用 `create_thing` 创建，不传 todos；goal 保存已确认的减脂目标与约束。
2. 为本批 4 个 Todo 准备稳定 ID、description 和 schedule_info。
3. 分别调用 `trigger/create_trigger` 创建 4 条规则（Todo 尚未写入，不传 bind_and_enable，建成停用）；每条使用对应的 Todo ID，prompt 写清该项执行、交付与回写要求。
4. 一次 `write_todos` 写入 4 条 Todo，各自的 rule_ids 填对应规则的真实 ID；expected_version 使用最新 Thing 回包版本。
5. 写入成功后逐条 `trigger/update_trigger(enabled=true)` 启用；需暂缓执行的保持停用，如实说明。

## 6. 业务语义示例

以下只说明任务内容、判断条件与完成标准；创建方式按 SKILL.md「创建」选择。工具名称与参数以实际加载的定义为准，不直接提交说明占位符。

### 单次有雨提醒带伞：judge 与无结果处理

重点是区分条件命中、未命中与查询失败。检查时刻和天气工具参数须已明确。

- Todo：title 写“带伞”，schedule_info 写 `{"kind":"MONITOR"}`；description 写“有雨时提醒，没雨不通知”。
- Trigger：schedule 写已确认的检查时刻，不传 rrule；judge.tool_call 使用真实天气工具及符合其 Schema 的北京、目标日期参数，目标日期按用户这次请求确定并固定（如 2026-09-27），不能在执行时重新解释“明天”。
- judge.condition：有证据确认目标日期北京有降雨时命中；查询错误既不能当作有雨，也不能当作无雨。
- prompt：重读本任务，告知目标日期北京有雨并提醒带伞，按卡片约定触达；提醒成功后记录进展、完成任务并停用本规则。

judge 未命中不会执行 prompt，也不会由 prompt 回写完成。若用户要求无论晴雨检查后都结束任务，使用不带 judge 的单次检查，在 prompt 中分别处理有雨、无雨和查询失败。

若是“每天查北京明天的天气”，则设置每日 rrule，查询日期随每次执行滚动到次日；提醒后保持监控，不沿用上例的固定日期、完成任务和停用规则。

### 新岗位通知：去重基准

重点是可靠去重：查询工具读取已通知岗位基准，交付成功后再记录已通知状态。Todo.schedule_info 用 MONITOR。

- `description`：`内容：筛选广深新增产品岗。由谁做：元宝。完成标准：有新增匹配岗位时通知，无新增静默。`
- 规则：`type=schedule`，schedule.start_at 写实际展开起点，schedule.rrule 写 `FREQ=WEEKLY;BYDAY=MO` 并按已确认期限填写 UNTIL；带 judge
- `judge.tool_call`：已确认的岗位检索工具
- `judge.condition`：`检索结果中存在尚未通知过、地区为广州或深圳、职能为产品的岗位`
- `prompt`：`先加载【实际岗位检索 Skill 名称】，重读任务，整理未通知过的匹配岗位并按卡片约定交付；交付成功后用已就绪的状态写入能力记录已通知岗位，并覆盖任务进展行；保留每周检查，按用户约定期限结束，未约定则持续到用户取消`

要点：**去重状态必须有真实的读取与写入能力**，不能把 Todo 进展文案当作工具必然能读取的基准。没有这套能力就先说明缺口，不创建声称能去重的规则；judge 未命中不会执行 prompt。这里只查询和通知，不自动投递。

### 机票确认后下单：授权停点与完成标准

重点是确认停点与完成标准：用户确认前不下单，出票成功才完成。Todo.schedule_info 用 MONITOR。

- `description`：`内容：筛选深圳飞成都的机票，确认后下单。由谁做：元宝和你。完成标准：出票成功。结果确认：下单前确认。`；出行日期写入 goal
- 事项 `goal`：已确认的出行日期（含年份）、预算上限、时间偏好、可接受的中转条件
- 规则：`type=schedule`，用户说了检查频率就照用，没说按默认每天 09:00（要"第一时间"再加 19:00），回复里说明可改；使用真实机票查询 tool_call 和预算条件 judge。
- `prompt`：`先加载【实际机票查询 Skill 名称】，重读任务与状态，按事项 goal 里记的预算与时间偏好选出 1 到 3 个候选报给用户，说明为什么选它们并发布候选卡；停在这里等用户确认，不要直接下单；把候选与本次报价更新进该任务的说明进展行；用户确认后再调下单能力，出票成功才把任务置完成`

三条不能错：

1. **报了候选不等于完成**——状态转 `PENDING_CONFIRMING`，不是 `DONE`。
2. **用户点同意不等于业务已完成**——出票成功才算。
3. **下单前若不确定上一轮是否已下过单，先查业务回执再动作**。重复下单是不可逆事故。

工作指令里"停在这里等用户确认，不要直接下单"这句是授权停点，必须显式写。

### 位置事件：事件不等于条件成立

重点是根据事件数据判断条件，而不是收到任意位置事件就提醒。以“到家提醒取快递”为例，家位置已写入 goal：

- Todo.schedule_info 用 MONITOR；Trigger.type 用 event，event.source_id 用已确认的 yb_geo_location，不填 schedule。
- 核对事件位置是否足以确认到家；未到家不通知，位置缺失不猜测。
- 确认到家后提醒取快递并按卡片约定触达；成功后记录进展、完成本次提醒任务并停用规则。不代表用户已取到快递。

## 7. 查询与更新参数示例

下列日期仅示意格式，实际创建按当前时间和用户要求填写；标识替换为真实回包值。schedule 在更新时整体替换，因此改期要从查询结果保留 rrule 和 timezone；事件规则不传 schedule。添加 Judge 时传完整 condition/tool_call，prompt 不需要搬动。以下改期示例假定查询回包中的原规则为每两周周一 08:00、Asia/Shanghai；只改到 09:00，保留其余配置。

**查询** · `trigger/list_triggers`

```json
{
  "thing_id": "<真实 Thing ID>",
  "todo_id": "<稳定 Todo ID>",
  "enabled_only": false
}
```

**改期并保留双周频率与时区** · `trigger/update_trigger`

```json
{
  "trigger_id": "<查询所得 trigger_id>",
  "schedule": {
    "start_at": "2026-09-28T09:00:00",
    "rrule": "FREQ=WEEKLY;INTERVAL=2;BYDAY=MO",
    "timezone": "Asia/Shanghai"
  }
}
```

**清除判断，保留执行指令** · `trigger/update_trigger`

```json
{
  "trigger_id": "<查询所得 trigger_id>",
  "judge": null
}
```

**取消规则** · `trigger/delete_trigger`

```json
{
  "trigger_id": "<查询所得 trigger_id>"
}
```

删除成功后再从 Todo.rule_ids 移除该 ID；临时暂停用 update_trigger 的 enabled=false，不调用删除。
