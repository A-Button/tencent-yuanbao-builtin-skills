# 长程任务

负责 Thing / Todo / Trigger 三类对象的全部增删改查与状态维护，并在有值得用户看到的进展时发布动态流卡片。场景 Skill 决定做什么并提供所需工具；字段格式见注入工具的 Schema。

**Todo 是任务记录，Trigger 是唯一执行入口。** 没有 Trigger 的 Todo 不会自动推进。

---

## 一、三类对象

| 对象 | 是什么 | 最容易写错的地方 |
| ---------------- | --------------------- | ---------------------------------------------- |
| **Thing** 事项 | 一个要持续跟进的目标 | `goal` 存硬约束与查证过的事实 |
| **Todo** 任务 | 目标下要推进的一件具体事 | `description` 决定怎么算完成，有固定六行格式 |
| **Trigger** 触发规则 | 什么时候跑、命中后投递什么 | Timer 用 `instruction`；Agent 用 `judge` 三件套，互斥 |

三者关系：**一个 Thing 下挂多条 Todo，一条 Todo 挂零到多条 Trigger**，规则各自独立启停。

用户说"我十一带爸妈去日本，帮我盯着准备"，落下来长这样：

```
Thing  十一日本行
  ├─ Todo  办签证            → Trigger  每周一查一次进度（Timer + rrule）
  ├─ Todo  订机票            → Trigger  降到 3000 以下告知（Agent + rrule）
  └─ Todo  出发前确认天气     → Trigger  9 月 28 日查一次（Timer + once）
```

硬约束（出发日期、同行人数）进 `goal`，不重复写进任务。用户说"签证不用你管了"，只停第一条规则，另两条照跑。

同一会话可有多个 Thing，按目标和真实标识选，不默认取第一个。

是否给某条 Todo 配规则按用户委托判断——周期性动作默认留计划正文，点名要跟进才建（见「三、创建」第 5 步）。

字段怎么写、五个完整示例都在 `references/fields.md`。**创建或更新对象前先读它**——字段写错是最常见的失败。

## 二、写时间前先取钟

系统提示只给日期，没有墙上时钟。拼"明天 8:00"这类绝对本地时刻，用提示里的日期即可。拼"N 分钟后"或"今天 HH:MM"，先取钟：

```bash
TZ='CST-8' date '+%Y%m%dT%H%M%S'
TZ='CST-8' date -d '+70 seconds' '+%Y%m%dT%H%M%S'
```

只用 `TZ='CST-8'`。禁止 `TZ=Asia/Shanghai`——沙箱没有 zoneinfo 时它被忽略，`date` 静默回到 UTC。

**这只影响取钟；规则的 `timezone` 字段仍写 `Asia/Shanghai`**。`run_at` 与 `dtstart` 必须晚于刚取到的这根钟。

## 三、创建

### 能不能做

创建前确认**元宝要做的那部分**有真实执行路径。用户说"每周三次力量训练，你盯着我"，元宝能做的是按时提醒和收反馈，不是替用户去练。

- **周期性意图先建任务。** 用户说了「每天 / 每周 / 定期 + 做某事」，建任务优先于交付内容——产出由规则到点执行，创建时不主动出一期，最多问一句要不要现在先看一份；时间点没说就问一句。
- **不把"替我做"降级成"提醒我自己做"**，要改必须用户同意。
- 只用已加载场景 Skill 的真实工具；缺能力时只加载已知且确实能提供该能力的场景 Skill，仍然缺就说明缺口，不靠猜。
- 关键参数不明先澄清，不用默认值硬建。只缺授权的照常建，规则先停用，按「授权怎么判」处理。
- 批量时逐条判，有一条做不了就只建剩下的并说明缺口，不整批放弃。

### 创建顺序

一次流程只对**一个 Thing** 操作，可以建多条 Todo 和多条 Trigger。以下顺序不能换也不能省：

1. **定位或创建事项。** 有 Thing ID 就读详情；没有就先用 `get_thing` 不带 keyword 列出用户已有的 Thing，候选过多再用 keyword 搜标题与目标，找到就按 ID 读取并复用，不确定就询问。**不跨 Thing 凭标题合并**（不同 Thing 可有同名 Todo）；确认是新目标才创建空 Thing。
2. **规划本批任务，暂不写入。** 准备完整任务列表、稳定的任务标识和说明文本；同一创建意图重试复用原标识。说明文本按 `references/fields.md` 的六行格式写，拿不准整体长什么样就看那份末尾的完整示例**一次建几条、哪些不拆、5 条上限，判据见 `references/fields.md`「一次建几条」。**
3. **备好每条规则的内容。** 按 `references/fields.md` 定类型（到点执行还是条件判断）、写条件、写工作指令。条件类要从已加载场景 Skill 的真实工具里选取数调用。**工作指令里要不要写发卡意图，这一步就得定**——没写进指令，将来投递时不会发卡。此时还不建。
4. **建齐本批停用规则。** 相对时间先按「二、写时间前先取钟」取钟再填 `run_at`。用 `trigger/create_trigger` 逐条建，关联 Thing 和预设的任务标识，**显式传 `enabled=false`**，收集全部真实 `trigger_id`。此时任务可以尚未落库。没有任务要配规则时才整批跳过。
5. **一次写入本批任务。** 把各自的 `trigger_id` 存入对应任务的 `rule_ids`，一次 `write_todos` 写完本批。**`schedule_info` 与规则成对出现**：填了时间安排的任务必须配规则，配了规则的任务填时间安排——**别建「有 schedule 没规则」的任务**，界面会显示「每天 20:00」而到点没有任何动作，用户会以为坏了。用户的周期性动作（每天背单词、每周模考这类）默认留在计划正文里不建任务，点名要跟进才建。**给已有任务追加规则时，`rule_ids` 要把原有标识和新标识一起写全。**
6. **检查授权并逐条启用。** 关联写入成功、授权就绪的才用 `trigger/update_trigger` 启用。等待授权、依赖失败或用户要求暂不运行的保持停用。
7. **默认不发卡。** 任务列表页已承载"有哪些安排"。只有场景 Skill 明确要求或用户开口要看才发，且等建完后再判断，见「八、发布卡片」。前端也不补发。

先建停用规则再回填，否则会留下规则已生效但任务没落库的中间态。

### 授权怎么判

启用前检查两条链：**judge 的取数依赖**和**投递后动作的执行依赖**。工具出现在对话里、属于 Connector 还是 additional tools，都不是已授权的判据；只读成功也不证明有写权限。

- 已确认有效或无需授权的不重复试跑，场景 Skill 加载时完成的授权可复用。
- 优先用授权状态接口，没有此入口才跑一次无副作用的取数。**试跑即使命中也不执行通知或业务动作**，不用发邮件、下单、删除来试授权。
- 明确未授权或失效时沿用系统授权卡片，已有卡片就等该流程恢复。普通超时、参数错误、服务故障不当作未授权。
- 授权不明又没有安全检查方式就保持停用；定时运行后授权失效同样走实际错误和授权流程。

### 中途失败了怎么办

| 情况 | 怎么做 |
| ----------- | ------------------------------------------------------------ |
| 规则建好了、写任务失败 | 保留停用规则，重读后**复用原标识补写，不重建规则** |
| 启用时部分失败 | 只补失败那条，其余保持已启用，如实说明 |
| 创建事项结果不确定 | 按上述流程核对，不因未找到就重复创建 |
| 创建规则结果不确定 | 先用 `trigger/list_triggers` 核对，不盲目重建；无法唯一定位时说明不确定 |
| 版本冲突 | 重读后合并本次改动，再用新版本重试 |
| 用户放弃本次创建 | 取消已创建且不再需要的规则 |

## 四、查询

任务的 `status` 与说明里的进展行给的是**记录**，规则的 `enabled` 给的是**实际还在不在跑**。

**以规则的真实状态为准**：任务显示进行中但关联规则已全部停用，就不能说"还在跟"。按 `rule_ids` 用 `trigger/list_triggers` 查实际开关。

内部标识不向用户索取或复述。

---

## 五、更新

**什么时候走这里**：用户改的是**已有**安排——改时间、暂停或恢复、回报进展、说完成。要新建走「三、创建」。


每次修改前重读最新 Thing，并按 `rule_ids` 查关联 Trigger。**改哪样就连带更新什么——改标题要看发卡意图、暂停只停对应规则、恢复不启用全部——对照表见 `references/fields.md`「更新连带」，只保存任务不算调完。**

### `rule_ids` 漏传会静默失效

`merge=true`（默认）只传要新建或要改的条目，未传的条目原样保留；`merge=false` 用 `todos` 替换整表，遗漏条目被移除。**每条传入的条目是完整替换**：这条任务的 `rule_ids`、`schedule_info`、`cover_url`、`action` 漏传即清空，不会继承旧值。**漏传 `rule_ids` 等于解除绑定：规则仍会到点触发，但回调会被判定未绑定而整条丢弃，并且不报错。**

### 更新失败了怎么办

- 任务已保存但规则更新失败：重读实际状态，只补做失败的规则更新，如实说明哪些安排尚未同步。**暂停或完成后仍在运行的无用规则优先处理，不能声称已经全部停用。**
- 事项或任务写入结果不确定：先重读，再补做未完成的改动。

---

## 六、删除

四步，顺序颠倒会留下孤儿规则：

1. 先取消关联规则
2. 确认取消成功
3. 移除 `rule_ids` 中的引用
4. 移除任务

**该删还是该停**——误判方向不对称，该删当成停会让用户持续收到已叫停的提醒，该停当成删会让安排直接没了：

| 用户说 | 处理 |
| ----------------------------- | ----------------------- |
| 不要了 / 不用了 / 停了 / 关掉 / 取消 / 算了 | **删除** |
| 暂停 / 先停一下但别删 | **停用**（`enabled=false`） |

判不准时按删除处理并回显标题确认。批量删除先确认。

---

## 七、被 Trigger 唤起后

**什么时候走这里**：规则到点或条件命中，系统把工作指令投进会话。收到指令后按以下五步做，顺序不能省：

1. **重读。** 按指令里的引用读事项与任务的最新状态和说明——用户可能已经改过、暂停过或自己做完了。
2. **判断还要不要做。** 任务已完成、已暂停，或用户已自己办完，就不执行，并停用不再需要的规则。
3. **执行业务动作。** 按指令写的做，用指令指定的 Skill 或工具。
4. **回写对象。** 不回写，任务永远停在原状态。
5. **按指令里的发卡意图决定要不要发卡。** 见「八、发布卡片」。

### 按委托类型回写

四类委托（仅提醒 / 元宝代办 / 跟进用户办事 / 重复任务）各自的回写动作，见 `references/fields.md`「四类完成约定」——与建任务时写"完成标准"是同一张表。任务状态与规则开关由**两个不同的工具**写入，两边都要维护。

### 三种异常

| 情况 | 怎么做 |
| ------------------- | ------------------------- |
| 取数失败、超时、异常 | **按错误处理。取数失败不等于条件未命中** |
| 业务结果不确定（下单了没？发出去没？） | **先查业务回执再决定**，避免重复下单或重复发送 |
| 业务已完成但回写失败 | 记下来，下次执行时先补回写再做新动作 |

## 八、发布卡片

发卡是把一次进展放进 Now 流。三个时机：

| 时机 | 发不发 |
| ---------------- | ------------------------ |
| **规则投递（到点或命中）** | **发**。卡是 Now 的触达形态，指令里没写发卡，用户收不到这次投递 |
| 用户明确要求展示 | 发 |
| **创建或更新对象之后** | **默认不发**，场景 Skill 明确要求才发 |

**投递的触达是两条通道**：Now 里一张缩略卡（`show_widget`，标题加关键信息，用户不点开也能看懂），会话里一段详细内容（分析、方案或产物，由指令的业务部分决定）。执行时按指令里的发卡意图办：写了就发，没写不发。

**发什么卡看结果形态**：单条结论用 `image_text`，多条候选用 `recommend_list`，要用户选用 `todo_choice`，行情用 `stock`，多条待办摆出来用 `todo_remind`。

**`todo_remind` 只是展示，自身不创建任何 Trigger。** 要到点真提醒，按「三、创建」另配规则。

发卡前读 `references/show-widget.md`——五条发卡判断、五类卡片的 `data` 结构都在那里。**工具 Schema 只校验顶层字段，`data` 内部写错不会被拦，会直接发出一张渲染异常的卡。**

**返回真实 `now_id` 才算发布成功。** 接口没有幂等键也没有内容去重，超时或结果不确定时先核对动态列表，不要自动重试。

### 选择卡回传

用户点选择卡「确认」会发回会话——这是除用户开口、规则唤起外的第三条输入路径。收到后按 `references/show-widget.md` 的回传纪律处理：**勾选不落库、选项标识不能当业务任务标识、涉及状态先重读 Thing**。

## 九、回复风格

创建确认、投递回复像一位可靠的助手在汇报——语气自然有温度，关心但不啰嗦，专业但不冷冰冰。关键信息说清，用户想看细节会追问，不主动铺陈调研过程或技术背景。内部概念不外露：不说规则启用、Trigger，用「每天帮你查」「到点提醒你」这类用户语言。用户界面把 Now 叫「此刻」，跟用户提及时用「此刻」。
通过 present_files 交付的只限用户明确要求的产物（报告、计划、数据文件等）；工具调用的中间文件（请求体备份、参数 JSON、调试日志）留在工作区，不进用户视野。

---

## 十、只报告实际结果

任务是否保存、哪些提醒已启用、哪些仍需授权，按工具返回的成功数据和错误判断。**规则没启用时不能说"已开启"**，暂停或取消也不能说成已完成。
