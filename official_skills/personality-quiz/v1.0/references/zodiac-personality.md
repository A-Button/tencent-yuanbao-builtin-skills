# 星座性格与相处方式

用于无需新排盘的星座轻解读。把星座作为趣味文化中的性格观察线索，围绕用户的真实情境展开。已有标签即可开始，默认在聊天中完成，不进入 HTML 排盘、深度报告或人格测评流水线。

个性化解释前读取 [safety.md](safety.md)，输出表达在本文件维护，公共语气见 [chart-language.md](chart-language.md)。本路由的星座标签只支持象征联想；用户已经描述的行为与需求决定个性化内容，不能把标签当作已验证的人格事实。

## 识别请求与复用信息

| 用户输入 | 当前处理 |
|---|---|
| “我是天蝎，聊聊我的性格” / “狮子座有什么特点” | 直接围绕该标签回答；不要求生日、时间、城市、性别或重做测试 |
| “看看我的星座性格”，没有任何标签 | 只问一次“你是什么星座？”；用户不知道时再按其已有生日资料处理，不先列完整能力菜单 |
| “我是 INFP＋双鱼，为什么有时很理性” | 按下方 MBTI 对照方法直接回答，复用已有结果和真实情境 |
| “天蝎和水瓶合不合” | 讨论沟通节奏、需求表达和分歧处理，不需要双方出生资料 |
| “我不像自己的星座” | 接受反馈，讨论哪些描述不符合或只在特定情境成立；不反推其他星座来圆说 |
| “我的太阳是双子、月亮是金牛” | 按用户自述的两个标签轻聊，并说明是按其提供的信息；不补算相位、度数或宫位 |
| “我生日是……，帮我确认太阳 / 月亮星座” | 属于计算请求，转 [chart-flow.md](chart-flow.md)，复用已有资料；日期级只使用稳定字段 |
| 用户提供第三方星盘截图、表格或导出数据 | 转 [imported-chart.md](imported-chart.md)，核对可读字段和来源后解释 |
| 用户明确要测试、星盘、每日内容或历史考据 | 分别回到 `personality`、`chart`、`entertainment`、`knowledge` 主路由 |

只有月日、只给农历日期或正好涉及换座边界时，不靠固定生日表宣布精确的个人星座；只问常见日期划分可作概略说明，需要确认个人归属则走计算流程。用户不愿提供计算资料时，可继续解释其自选标签的文化含义，不把自选标签写成计算结果。

用户说“我是双鱼”等未指定天体的日常表述，按其自述太阳星座标签开始，不再追问是否指月亮或上升。用户指定了天体时保留该区别。描述自己的已知上升标签可以轻聊；要求计算上升时转 `chart`，复用准确出生时间或明确起止时段及可靠地点坐标，由引擎核验后展示稳定结果或真实跨界候选。未知或不愿提供时间时，上升保留待定，不反推补值。

## 输出表达

先用一句平实的话概括用户问的侧面，再挑二至三个相关情境展开。语气可以自然、亲切，像认真解释一种相处偏好，不像给一个星座盖章。只有标签时说明文化语境；已有真实情境时围绕情境说，不重复标签介绍。

MBTI 对照分别说明两类线索的用途，不把形容词相加。关系问题可解释不同需要在日常互动中怎样表现；用户问怎么办或已有困扰时，再给具体说法或小建议。可以温暖，但不靠“你内心深处”“天生注定”显得了解对方。

用户说不符合时接受，不用未知配置圆说。展开不自动升级为星盘或报告；保持原有一次末尾说明。

## 写出可对照的生活表现

默认选 2—3 个与问题直接相关的观察点；用户只要一句话就给一句，要求展开才增加场景。先交付内容，再决定是否附一个可跳过的校准问题。

- 概括、展开和收尾按上方输出表达执行；必要的文化语境仍应简短说明，不宣称“精准看透你”。
- 把符号联想落成有触发条件的观察：什么场景容易出现、具体会怎么做、这种做法有什么好处或代价。不要只堆“敏感、善良、独立、外冷内热”等形容词。
- 每条只选一个有区分度的侧面。若“喜欢独处，也需要陪伴”适用于几乎所有人，改成一个能让用户回答像或不像的场景，或删去该条。
- 已有用户情境时，以情境组织回答。例如用户说“冲突时会暂时不回消息”，先区分是在整理情绪、组织措辞还是回避对话，再借符号提供观察角度；不能仅凭星座认定动机。
- 没有真实情境时，用“可以观察自己是否……”或条件句引入联想。仅一个太阳标签，不扩写完整人格档案、过去经历或依恋类型。
- 校准问题允许否定，如“遇到分歧时，你更常当场说开、独自整理后再说，还是两种都不像？”用户说不像就舍弃该条，不用未知月亮、上升、隐藏人格或“你还没发现”解释不命中。

只有用户问怎么办或提出具体困扰时才给建议，不把每一段描述变成指导。例如用户已经说明自己需要暂停争论，可给一句沟通表达：“我需要一点时间想清楚，晚饭后我们再聊。”不要用幸运色、转运物或配对排名替代相处建议。

## MBTI × 星座

只在用户要求结合、或当前问题明确涉及两者时对照，不主动给每份人格结果加星座解释。

1. 已有四字母就复用；有 `PERSONALITY_RESULT_V1` 或连续分数时，先按 [personality.md](personality.md) 校验与解读。保持现有量表、计分、结果码和类型不变，不因星座增减某一维度，也不强迫重测。
2. 说明两种输入的不同用途：MBTI 类结果提供自述或问卷中的偏好线索；星座提供文化象征联想。两者相似不构成相互验证，也不能推出更高准确率。
3. 选择一个共同问题对照，如“冲突时怎么表达需求”。分别交代各自带来的观察角度，再用用户的具体表现判断哪个角度有帮助；不要把两套标签的形容词简单相加。
4. 表面不一致时保留差异。例如用户既重视关系又会理性决策，可以讨论决策情境；不能因为是 `F` 就判定其不理性，也不能用某星座否定其四字母结果。
5. 缺一个输入时先回答已有部分；只有用户明确要求两者对照且缺失项确实必要时，补问那一个标签。不从星座推 MBTI，不从 MBTI 推星座，也不生成新的混合类型、比例或准确度分数。

## 相处方式与关系问题

“配不配”可转成两个具体的相处维度：例如一方希望及时回应，另一方需要整理后再说，双方怎样约定时间。只有星座标签时，这些是待验证的情境示例，不能直接说成双方的现实偏好。

用用户已经提供的互动事实调整分析；同星座的人也无需有相同需求。不生成契合百分比、星级、最佳伴侣排名、“正缘 / 克星”结论，不据此判断第三方喜欢谁、忠诚度或是否值得交往。关系判断落在双方可观察的行为、尊重和协商上。

## 升级与收尾

星座轻解读无需遵循盘面先展示 HTML 的要求。用户明确想了解更细的行星配置或要基于出生信息分析时，才转 `chart`；只说“多讲一点”继续当前轻解读，不自动索要出生信息或生成正式星盘报告。

转入计算时才读取 [chart-flow.md](chart-flow.md) 及其按阶段要求的计算参考；计算能力、精度和展示范围由该链路管理。不要把当前聊天中的象征联想当成引擎事实。

轻量个性化结果结尾保留一句：

`AI生成内容｜星座趣味解读，供自我观察，不是科学人格测评。`

纯概念回答不机械追加个性化说明。转入星盘或报告后使用主 Skill 对应的交付与收尾规则。
