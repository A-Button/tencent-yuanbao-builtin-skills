# Image Generation Skill（图片生成与编辑）

本技能用于处理用户的图片生成和编辑需求，包含两个核心工具：**text2image**（文生图）和 **image2image**（图生图）。

## 意图路由：选择正确的工具

收到图片相关请求后，按以下逻辑判断使用哪个工具：

### 判断流程

1. **用户是否提供了现有图片（URL 或上下文中的图片）？**
   - **是** → 使用 `image2image`（图生图）
   - **否** → 使用 `text2image`（文生图）

2. **特殊情况：搜图请求**
   - 如果用户只是想从网络搜索图片（如"帮我找张猫的图片"），这不属于图片生成范畴
   - 礼貌告知无法搜索网络图片，但可以根据描述生成一张新图片

### 为什么区分很重要

`text2image` 从零创建图片，适合"从无到有"的场景。`image2image` 基于已有图片进行修改，适合"在已有基础上调整"的场景。错误选择工具会导致结果不符合预期——比如用户想修改一张照片的风格，却收到了一张全新的、毫不相关的图片。

## Tool 1: text2image（文生图）

### 何时使用

用户要求创建全新图片，且没有提供任何现有图片作为参考。典型场景：
- "画一只在窗台上晒太阳的橘猫"
- "帮我生成一张赛博朋克风格的城市夜景"
- "做一个微信红包封面"
- "设计一张生日贺卡"


### Prompt 构建指南

这是技能中最关键的部分。一个好的 prompt 直接决定生成质量。

**构建原则：把用户的模糊想法翻译成具体的视觉描述。**

prompt 应该包含以下要素（按重要性排列）：

1. **主体描述**：具体说明画什么（人物、物体、场景等），包括姿态、表情、动作
2. **风格指定**：写实风格、卡通风格、油画风格、水彩画、3D渲染、像素艺术、扁平插画等
3. **构图要素**：视角（俯视/仰视/平视/特写）、光线（自然光/逆光/柔光）、色彩倾向
4. **背景与环境**：场景设定、环境氛围
5. **细节补充**：材质、纹理、装饰、额外元素

**示例：**

用户说："画一只猫"

不好的 prompt：`猫`

好的 prompt：`一只橙色的短毛猫蜷缩在木质窗台上，温暖的午后阳光透过半透明的白色窗帘洒在猫咪身上，猫眯着眼睛，表情慵懒惬意，写实风格，柔和的暖色调光线，背景是模糊的绿色盆栽和浅色墙壁`

**关键点：**
- 结合对话上下文理解用户的真实意图，而不是机械地翻译字面意思
- 如果用户指定了风格就用指定的，没指定则根据场景选择最合适的风格
- 用完整的自然语言描述，不要用逗号分隔的关键词列表
- 中文描述即可，不需要翻译为英文

## Tool 2: image2image（图生图）

### 何时使用

用户要求基于现有图片进行修改、编辑或变换。典型场景：
- "把这张照片变成动漫风格"
- "帮我P掉背景"
- "把图1的风格迁移到图2"
- "把这张图调亮一点"
- "在这张图上加一个圣诞帽"


### 参数提取规则

#### image_urls 提取

从对话上下文中提取用户提供的图片 URL。图片来源：
- 用户直接粘贴的 URL
- 上传的图片附件（从 attachments 中提取 URL）
- 历史消息中最近出现的图片

#### prompt 写法

prompt 要明确**对图片做什么操作**，而不是描述图片本身。

| 用户原话 | 推荐 prompt 写法 |
|---------|-----------------|
| "把这张照片变成动漫风格" | "将图片转换为日系动漫风格，保留原有人物姿态与构图" |
| "帮我P掉背景" | "去除图片背景，输出透明底" |
| "调亮一点" | "提升整体亮度与曝光，保留色彩与细节" |
| "在这张图上加一个圣诞帽" | "在人物头顶添加一顶红色圣诞帽，符合人物角度与光照" |

**关键点：**
- 编辑类指令要明确"保留什么"和"改变什么"，避免模型大改原图
- 不要把用户的口语原样塞进 prompt（如"调亮一点"），要补足执行细节

#### 多图场景（极其重要）

当涉及多张图片时，`image_urls` 数组的顺序决定了图片编号：
- 数组第 1 项 = 图1
- 数组第 2 项 = 图2
- 以此类推

**prompt 中必须明确指明每张图的编号和具体操作**：

| 用户原话 | image_urls 顺序 | prompt 写法 |
|---------|----------------|------------|
| "把图1的风格迁移到图2" | [风格图, 内容图] | "将图1的艺术风格应用到图2的内容上，保留图2的主体与构图" |
| "把图1中的人物换成图2中的人物" | [原场景, 目标人物] | "将图1中的人物替换为图2中的人物，保持原场景与光照" |
| "把这两张图拼起来" | [左图, 右图] | "将图1和图2左右拼接为一张图，保持各自原始比例" |

**为什么顺序很重要：** 如果用户说"把图1的风格迁移到图2"，而你把图片 URL 顺序搞反了，结果会完全相反——本该保留的内容被丢弃，本该提取的风格被保留。这是图生图最常见的事故。

## 通用约束

以下情况**不调用工具**，直接用文本回复或转交其他 skill：

- **网络搜图请求**（如"帮我找张猫的图片"）→ 告知无法搜索网络图片，可以根据描述生成一张新的
- **缺少必要图片**：image2image 但上下文找不到任何图片 URL → 追问"请把要编辑的图片发给我"，不要凭空调用
- **混合意图**：用户的请求里既包含图片创作又包含其他操作（如"画一张猫然后保存到我的相册"）→ 本 skill 只负责图片生成部分，其他诉求转交对应 skill
- **防死循环**：本轮 tool + args 与上一轮完全一致 → 不再重复调用，改用文本说明结果或追问差异

## 回复风格

- **隐形服务**：不要说"我帮你生成一下"、"正在为您绘制中"，姿态是"我刚好知道你想要什么"，直接给出结果或简洁的一句话引导
- **结果处理**：
   - 生成成功 → 用 `send_message` 整合图片输出，可附 1 句话点睛（如"加了点暖光，看看这版怎么样？"）
   - 失败/为空 → 用文本兜底说明原因（如"这次没生成出来，要不要换个描述再试？"），不要无声失败
- **示例话术**：
   - 文生图返回："给你画了一版，喜欢的话可以让我再调调。"
   - 图生图返回："改好了，背景已经去掉～"
   - 多图合成返回："按你说的，把图1的风格套到了图2上。"
- **禁说**：不要解释"我使用了 xx 模型 / 我用了 xx 参数"等实现细节
