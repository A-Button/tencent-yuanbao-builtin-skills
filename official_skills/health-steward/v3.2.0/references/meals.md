# 饮食 SOP：记、算、查、改、删、跳过

调用方式和统一成功条件见 SKILL.md。本篇只规定饮食判断、单次调用与回复格式。

## 1. 接入与分流

接：记录已吃的一餐；测算菜谱、配料表、生食材或文字食物；查询某日与近 1/7 天统计；补记、纠错、删除、跳过正餐。

以下情况不调饮食工具，只用一句话说明能力边界：知识问答、推荐/点单建议、餐厅菜单或外卖候选、与饮食无关的图片、恢复删除、收藏或导出。即使咨询同时带食物图，也不把它擅自记成已吃。

### 已吃还是只算

| 输入 | 判断 |
|---|---|
| 只发食物图，未说「多少卡 / 别记」；餐盘、打开的外卖盒、吃了一半 | 默认已吃，走 `diet_record` |
| 菜谱、配料表、包装标签、生食材 | 说「按这个做的，吃了」才记录；只问热量走 `diet_estimate` |
| 纯文字 | 「我刚吃了」走记录；「多少卡」走测算 |

拿不准时：有图按已吃，纯文字问热量按测算。测算后用户确认已吃，必须复用刚才完整 `items` 单次调用 `diet_record`，不用用户重发。

## 2. 调用前统一准备

### `items`

每样食物一项，只估 `name`、`portion`、`kcal`、`protein_g`、`fat_g`、`carb_g`、`sodium_mg`。不传 `title`、`emoji`、`story`、`narrative`、`sceneOneliner`、`aiPrice`、`totals`：标题按食物名由脚本补，食物 emoji 按菜名由脚本补，场景速写没传时脚本按桌上的食物补一句，合计和 4-4-9 交叉核验也由脚本算。参数直接写进命令，不要先写成文件。品牌食品拿不准时可查公开营养表，不硬猜。

`portion` 只写最多 3 个字的份量词，如「1个」「一份」「一碗」「半份」「两块」「二两」。克重、部位、生熟重和烹饪假设放在正文表格的「识别/估算依据」，不要塞进 `portion`。

### 图片

本轮有图时，`diet_record` 和 `diet_estimate` 都传本轮图片的 `photoUrl`：有 `[user_image_url]` 用 URL；只有 `[user_image_path]` 用路径；两者都有用 URL。不得翻历史消息复用旧图、编地址或把二进制描述当地址。Now 卡的 `image`、封面，以及历史里 `show_widget` 的图片地址，禁止当作 `photoUrl`，也禁止贴进正文或 `<media_info>`。`photo_warning` 表示可能串图，核对后必要时用 `diet_update` 修正。

### 餐次与时间

按以下优先级：

1. 用户明确说早餐/午餐/晚餐等：传 `mealType`。
2. 有照片拍摄时间：传 `eatenAt` 和 `eatenAtSource: "photo"`，由脚本按时间窗派生餐次。
3. 其余不传，由上传时刻派生。

用户说具体钟点时传完整 ISO 时间并配 `eatenAtSource: "user"`；只说某天时只传日期，不拼 `T00:00:00`。时间窗为：05–11 早餐，11–14:30 午餐，14:30–17 下午茶，17–21 晚餐，其余夜宵。整餐只有咖啡、奶茶、果汁、酒等纯饮品才传 `beverageOnly: true`。

## 3. 可直接执行的 SOP

统一成功判断：命令退出状态为 0 且业务 JSON 为 `"ok": true`。失败不重说成成功，按「原因 + 下一步」回复；成功写操作通常只补 1 句。

### SOP A：记录已吃一餐

1. **触发**：食物图默认已吃，或用户明确说已吃。Now「去记录」只上屏「这是我今天的早餐/午餐/晚餐」时，这条消息没有食物也没有图，不算已吃：不要调用，请用户拍一张或说出吃了什么。下一句再按本 SOP 记，有图必须带 `photoUrl`。
2. **必要判断**：拆全量 `items`；确定本轮图片、餐次和时间；一句话涉及两餐时分成两次独立记录，不揉成全天合计。
3. **单次调用**：`diet_record`。
4. **成功判断**：统一条件；写成功后不为确认展示而重跑。
5. **回复/出卡**：出饮食卡；正文按第 4 节的「记录模板」。

### SOP B：只测算

1. **触发**：明确问热量、营养或说只算不记。
2. **必要判断**：拆全量 `items`，本轮有图必须带 `photoUrl`。
3. **单次调用**：`diet_estimate`。
4. **成功判断**：统一条件且回执 `saved` 为 `false`，不得说已存入。
5. **回复/出卡**：出饮食卡；正文只用一张合并表、交叉核验、是否已吃的追问和免责声明。

### SOP C：测算后确认已吃

1. **触发**：用户对刚才的测算确认「已经吃了」。
2. **必要判断**：直接复用刚才完整 `items`、图片及用户已提供的餐次/时间，不让用户重发。
3. **单次调用**：`diet_record`。
4. **成功判断**：统一条件。
5. **回复/出卡**：出卡，正文只用 1 句确认；若仍需展示营养明细，沿用第 4 节记录模板，不重复两套分析。

### SOP D：分析或查看某日

1. **触发**：「分析今天的饮食」「今天吃得怎么样」「今天吃了什么」「某天饮食」。
2. **必要判断**：用 `date`，不传就是今天。不要用 `nutrition_summary` 代替这次调用。
3. **单次调用**：`diet_day`。
4. **成功判断**：统一条件；`card_empty` 是成功空态，不是读取失败。
5. **回复/出卡**：当天有记录出饮食卡，正文 1–3 句，不把卡上的图贴进正文。无记录时只回一句纯文本「这天还没有饮食记录。」，不出卡，不展示 0 值统计、不加 CTA。

### SOP D2：统计

1. **触发**：「这周吃得怎么样」「近 7 天统计」。
2. **必要判断**：只选 `day` 或 `week`，不额外联调其它查询。
3. **单次调用**：`diet_stats`。
4. **成功判断**：统一条件。
5. **回复**：正文 1–3 句，不出卡。

### SOP E：补记新食物

1. **触发**：「还吃了个酸奶」「另外有杯豆浆」。
2. **必要判断**：确认这是实际新增摄入，不是原记录写错。
3. **单次调用**：`diet_record` 新建一条；不要把旧记录的 `items` 加料后整体覆盖。
4. **成功判断**：统一条件。
5. **回复/出卡**：出新记录卡，正文通常 1 句。

### SOP F：纠错

1. **触发**：「不是鸡腿是鸡翅」「份量写多了」。
2. **必要判断**：`mealId` 只能来自既有回执或 `diet_day`；定位不清先询问，不猜。修改 `items` 时提交纠正后的完整清单，合计由脚本重算。
3. **单次调用**：`diet_update`。
4. **成功判断**：统一条件。
5. **回复**：通常 1 句说明已改成什么，不出卡。

### SOP G：删除

1. **触发**：用户要求删除记录。
2. **必要判断**：先明确标题、时间和热量并取得确认；当天多条且指代不清时，先用 `diet_day` 定位，当前轮不删除。
3. **单次调用**：确认后 `diet_delete`。
4. **成功判断**：统一条件。
5. **回复**：通常 1 句，不出卡。

### SOP H：跳过

1. **触发**：「早餐/午餐/晚餐不吃了」。
2. **必要判断**：必须映射到 breakfast/lunch/dinner；不明确就先问。饮品、下午茶、夜宵不标跳过。
3. **单次调用**：`diet_skip`，不得造 0 kcal 记录。
4. **成功判断**：统一条件；若返回 `SLOT_RECORDED`，说明该餐已有记录并询问是否修改。
5. **回复**：只回 1 句，不出卡。之后用户又吃了，正常 `diet_record`，跳过标记由脚本清除。

## 4. 正文模板

卡片由工具旁路下发。正文不写图片网址、沙箱路径（如 `/data/inputs/...`）、`<media_info>`、`meal_id` 或流程性套话，也不重复卡片已有的标题、时间和清单。照片只出现在饮食卡上。所有数字必须来自回执。

### 记录已吃一餐

原则上只写：**一句结论 + 一张表 + 最多 2 条关键信号 + 1 句行动追问 + 免责声明**。

| 食品 | 份量 | 识别/估算依据 | kcal | 蛋白 | 脂肪 | 碳水 | 钠 |
|---|---:|---|---:|---:|---:|---:|---:|
| … | … | 可见份量、克重折算、品牌数据或关键假设 | … | …g | …g | …g | …mg |

表后紧跟一行交叉核验：`{cross_check} kcal` 对比合计 `{totals.kcal} kcal`，偏差 `{delta_pct}%`。回执有 `warning`（偏差超过 5%）时必须说明并先纠正估算；需要回写时只调用一次 `diet_update`。

关键信号最多 2 条，只选最影响当前行动的蛋白、脂肪、碳水或钠信息。最后用 1 句具体行动追问，不问「要我重算吗」。

### 只测算

只保留同一张合并表、交叉核验、追问「这是已经吃了吗？是的话我帮你存进今天的记录。」和免责声明；不要另做识别结果表或重复营养表。

### 来源 / 历史故事

不是必出模块。确有辨识或决策价值时最多在正文展示 3 项；食物超过 3 项时按「主菜/能量贡献高 → 营养特征突出 → 来源辨识度高」选择。故事只写在正文里，不要写进工具参数。

### 查改删跳过

查询 1–3 句，成功写操作通常 1 句；有卡时不复述卡片。失败按「真实原因 + 下一步」回复。`diet_day` 有记录出饮食卡，无记录严格按 SOP D 的一句纯文本空态处理。

每次记录或测算正文末尾保留以下免责声明，原文不改、不加粗：

> 估算结果可能因食材差异、烹饪方式、克重偏差与真实摄入存在出入，仅作日常健康参考。

## 5. 数据边界

- 一餐一个对象持久化。不要用 bash 直接读写 `meals/` 或 `diet.db`。
- 照片在记录时复制进档案；复制失败按无图处理，不影响记录落库。
- 同一记录并发修改以后写为准；并发新增可能产生两条，按用户明确指认删除，不猜。
- 规律性评分按最近 7 天；样本不足可能返回默认 99，只照抄，不解读成「很规律」。
