# 大纲与仿真写作方法

## 大纲与信息分布

### 创作简报

大纲开头保存以下信息。未知项标记“待确认”或“作者假设”，不能默默补成用户要求。

|字段|要明确的内容|
|---|---|
|scenario|用户原目标、现实限制、变更前交付物|
|skill_sources|用户提供的Skill名称、版本、能力/边界/依赖、材料出处|
|scale|历史Session数 + 留出Session数，是否按用户人数分组|
|side_events|关联分支与无关干扰分别是否启用、事件数、Session占用及长度；计入总量还是额外增加；附加问题数量|
|length_targets|每Session最低用户发言数/正文字符数；常见助手长度与上限；计量单位|
|timeline|创作日期与故事发生日期分开；只给Session日期或是否允许消息时间|
|voice|语言、口语程度、用户与助手风格、参考材料|
|held_out_change|最后真正改变的条件、仍应继承的要求、需要重新核实的范围|
|deliverables|仅大纲或全量；消息schema；报告与评分材料是否需要|

用户可能只有一个模糊需求。先帮其收敛到可写的故事，再提出规模建议，不要求填写所有技术字段。

### 每Session设计表

|Session/日期|主题和用户目标|目标信息与状态变化|Skill放置位置及能力|阶段交付物|长度目标|
|---|---|---|---|---|---|
|S01/日期|具体的小目标|明确列出本段引入或更正的信息|在什么用户意图之后使用，能做什么/不能做什么|用户这一段实际得到什么|最低用户轮数及其他已约定指标|

不要把一列写成“继续交流”“丰富背景”而不说明具体信息。Session只是对话容器，不等于Event/MU；不要将一段一个Event写成默认gold。

启用分支/干扰时，为设计表补充作者侧类型、事件ID与关联问题；设计规则见 [branches-and-distractors.md](branches-and-distractors.md)。跨Session分支使用稳定事件ID，纯干扰的关联问题留空；不同类型共处一段时定位到消息范围，不给模型可见消息加类型标签。

### 信息安排的四条原则

1. **先有局部决策，再有全局方案。** 让需求通过选项、取舍和修改出现，不让用户第一条消息就交出完美PRD。
2. **重要要求可自然重现。** 例如在选住宿时再次影响选择；别把所有必考事实藏在孤立无关半句话里，也别每一轮都重复。
3. **阶段成果完整，全局画像分散。** 可以有完整日历/设计/比较表，但最后一轮不打包所有偏好、例外、旧订单和否决历史。避免单一总汇总MU包含全部答案。
4. **噪声要有生活原因。** 误发、替他人问、短暂跑题、口语自我纠正少量出现即可；不靠毫无意义的长串材料制造检索难度。

### 作者约束台账（独立于模型可见历史）

每条记录：`信息 / 属于谁 / 适用范围 / 最早出现Session / 更新或否决Session / 最终状态 / 对留出任务的意义`。

区分稳定偏好、任务硬约束、单次例外、候选建议、拒绝方案、已确认决定、已完成动作、待处理事项。重要状态变化必须在消息里有证据。不得把“助手推荐过”写成“用户同意过”。

### 留出任务的难度

优先改变能引发多处依赖变化的条件：目标地点/对象、期限、预算、参与人、设备平台或成果形式。旧历史先完成原目标，最后变更才有连锁影响。

留出问题要有自然指代和检索入口，比如“之前那份方案”“之前说的条件仍算数”，但不把所有待召回条件再列一遍。也不要模糊到不知道在说哪个任务。

新任务可能使一些旧要求无法满足。允许Agent指出冲突并做必要澄清，不强迫它编造兼容解。难度来自有效信息的组合、更新和迁移，不来自只能作者知道的事实。

## 仿真写法与审校

### 用户

- 多数发言短而有针对性，只纠正刚才最在意的一点；保留“啊”“不是”“先别”“我不是说了吗”等自然语气，但不要每条都有。
- 可以情绪化、不精确、先咨询后否决。用户不是评测员，不会反复说“请区分长期偏好与局部例外”。
- 少数消息粘贴较长条款、通知、工作材料。粘贴内容与口语外框有明显风格差异；合成订单和资料不使用真实证件/支付账号。
- 允许连续用户补充，保持消息顺序和独立index；不要为凑对话硬插助手。

### 助手

- 用真实信息量使回复比用户长：比较几个选择、给完整方案、解释费用/步骤、说明取舍。不是扩写“已记录、已更新、收到”。
- 短确认、澄清可以短；整段任务交付必须展开。不要每条都长，也不要所有方案都压成一句话。
- 语气客观为主，可以偶尔热情、讨好或出现被用户纠正的轻度错误；不让“殷勤”变成无依据地认同所有要求。若故意加入错误，须有明确纠正和可追踪的有效版本。
- 不泄露内部作者台账或评分意图，少用“这将测试你的记忆”之类不属于日常对话的话。
- 用户未授权或Skill不具备的动作，不写成已完成。模拟故事中需要完成状态时，应有能力定义支持并有用户确认，或由用户自己报告外部完成。

### Skill标记

只在恰当回复开头标注，例如：

`【调用了 <规划Skill> Skill】` 然后给出这一轮实际交付的完整计划或修改。

`【调用了 <执行助手> Skill；提醒管理依赖 <提醒Skill>】` 仅在材料明确依赖关系且用户确实委托提醒时使用。

不要求模型真的调用这些Skill；不伪造供应商工具schema/精确轨迹。若材料只支持查询，不能靠名称带“助手”就推断能支付、取消、提交或监控。

### 长度

以用户约定为准。没有约定时，可提出多数用户20—100中文字符，粘贴材料例外；助手普通解释约200—600字符，完整方案约600—1400字符，简短确认可更短。这是写作参考而非刚性配额。

“通常2K token以内”不是“每条要凑2K token”。不同语言和模型分词不同；没有精确分词器时留余量并报告字符统计，标注token未测量。

如果一段达不到最低长度，补上尚未自然展开的决策：方案比较、真实交付、具体反对理由或执行状态，而不是重复五遍“我记住你的要求”。

### 一致性检查

- 日期与先后顺序：后说的条件不提前出现在早期角色口中，除非是合理的助手建议而非冒充已知用户要求。
- 人物归属：同行者/同事/家人/用户自己的需求不混合。
- 适用范围：一顿、一天、一次尝试与长期偏好分开。
- 数字：人数×单价、晚数、预算、退款、现金流、净成本一致；未知外部价格不要硬凑总额。
- 状态：候选→确认→提交→成功/待审核的过程有证据；缺一步时不编补。
- 截止：只有日期没有时刻时，不能断言还在某个小时的办理窗口内。
- 最后任务：只在留出Session提出，不在之前解决，也不附助手答案。
