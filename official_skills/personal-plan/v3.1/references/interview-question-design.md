# 面试题包生成规则

只在需要生成针对性面试题包时使用。生成前应已有 `job-search-interview.md` 形成的职业阶段、JD—经历证据矩阵、面试轮次、准备日程和领域内容；文件格式与工作表组织按 `output-contracts.md` 执行，本文件不重复维护。

## 1. 生成前提

题包至少需要：

- JD或明确的岗位方向；
- 已完成的JD—经历证据矩阵；
- 面试日期、轮次或剩余准备时间；
- 用户最担心的环节。

有简历或项目材料时，使用真实经历生成个性化追问。只有JD时，生成岗位标准题并标明无法匹配个人证据；只有简历时，只生成简历深挖题并提示补充JD。

## 2. 题量与组合

| 剩余时间 | 建议题量 | 重点 |
|---|---:|---|
| 当天 | 6—8题 | 自我介绍、最高风险、核心经历和反问 |
| 1—2天 | 8—12题 | 必问、P0缺口、核心项目和行为题 |
| 3—7天 | 12—15题 | 完整题型组合并安排一次模拟 |
| 8天以上 | 14—18题 | 完整组合、两轮模拟和答案迭代 |

题型池：

| 题型 | 主要依据 | 目的 |
|---|---|---|
| 通用必问/动机 | 岗位、轮次和职业路径 | 验证表达、动机和稳定性 |
| 简历深挖 | 项目、数字和个人贡献 | 验证真实性、深度和复盘 |
| 专业能力 | JD必需能力和核心职责 | 验证岗位胜任力 |
| 差距针对 | 可迁移、弱证据和无证据项 | 检查风险与补救能力 |
| 行为题 | JD行为要求 | 获取真实行为证据 |
| 情景题 | 岗位中的实际冲突 | 观察分析、优先级和行动 |

完整JD、简历且剩余3—7天时，可采用15题基线：

- 5道共同必问；
- 5道差距针对题；
- 5道简历追问题。

将专业、行为和情景题放入上述三组，不额外堆题。同一能力点不超过两道主问题。

## 3. 单题契约

每道重点题必须包含：

```text
题目编号：
分类：
考察能力：
难度：易 / 中 / 难
出题依据：对应JD条目、简历事实或证据缺口
题目：
回答结构：
可使用的真实证据：
可能追问：
红线：
准备动作：
```

- 用户证据充分时，可以给基于现有事实的示范表达。
- 证据不足时只给回答结构和待补问题，不替用户编经历。
- 出题依据必须能回指JD、简历或证据矩阵，不能只写“常见面试题”。

## 4. 题型设计

### 4.1 专业能力题

从“是否了解”追到“如何使用、为什么这样选择、如何处理限制、如何验证结果”。

合格示例：

> 你在【真实项目】中使用【方法】解决了什么问题？为什么选择它？遇到的限制是什么，结果如何验证？

避免脱离岗位的宽泛知识背诵。

### 4.2 简历深挖

围绕五个问题设计追问：

1. 当时目标和限制是什么？
2. 用户本人负责什么？
3. 做过哪些关键选择，为什么？
4. 结果如何衡量，数字从哪里来？
5. 如果重做会改变什么？

用户始终只说“我们”、数字无法解释或核心技能无法展开时，标为需补证据，不直接指控造假。

### 4.3 差距针对

对每个P0弱证据或无证据项至少准备一题，观察：

- 是否诚实承认差距；
- 能否说明可迁移经验；
- 是否已完成学习或验证动作；
- 是否理解目标岗位与既有经验的差异。

### 4.4 行为题

使用“请描述一次你……”的真实行为问法。优先覆盖JD明确提到的协作、领导、抗压、学习和结果导向，并要求用户使用真实STAR素材。

### 4.5 情景题

使用岗位中可能发生的资源不足、指标下滑、优先级冲突或跨团队分歧。评价信息收集、判断、取舍和行动，不寻找唯一答案。

### 4.6 通用必问

至少覆盖60秒自我介绍、选择公司/岗位的原因和一项最相关优势。根据轮次再选择离职原因、职业规划、弱点、失败经历或反问。

常用回答结构：

| 问题 | 结构 |
|---|---|
| 自我介绍 | 当前定位 → 2—3项最相关证据 → 与岗位连接 |
| 为什么选择岗位 | 岗位事实 → 个人连接 → 可贡献内容 |
| 最大优势 | JD要求 → 一项优势 → 真实项目与结果 |
| 真实弱点 | 非致命事实 → 改进行动 → 当前进展 |
| 离职原因 | 客观现状 → 下一阶段诉求 → 与新岗位连接 |
| 失败/冲突 | 事实 → 个人责任 → 调整 → 复盘 |

## 5. STAR证据使用

题目引用的STAR素材必须来自职业规则中整理的真实证据卡：

- 情境和限制；
- 用户本人任务；
- 具体行动和选择；
- 真实结果及来源；
- 复盘；
- 可能被追问的风险点。

缺少数字时使用人数、范围、周期、效率、质量、成本或用户影响；仍无数据时用具体规模描述，不补造比例。

## 6. 模拟使用

模拟时一次只问一道题。用户回答后输出：

1. 做得好的1—2点；
2. 最重要的改进点；
3. 建议重答结构；
4. 一个继续追问。

整轮可按1—5分评估岗位相关性、结构、真实性、个人贡献、深度、简洁度和追问稳定性。不得输出虚假的面试通过率。

## 7. 内部结构化校验与用户产物

题目较多或需要稳定生成文件时，先用临时JSON组织数据，以便检查字段、题量、难度、重复题和题型覆盖。JSON是机器校验所需的中间结构，不是默认的用户产物。

| JSON字段 | 内容 |
|---|---|
| `id` | 题目编号 |
| `category` | 题型 |
| `competency` | 考察能力 |
| `difficulty` | 易、中或难 |
| `basis` | 出题依据 |
| `question` | 题目正文 |
| `answer_structure` | 回答结构 |
| `evidence` | 可使用的真实证据 |
| `follow_ups` | 可能追问数组 |
| `red_flags` | 红线数组 |
| `preparation_action` | 准备动作 |

从本Skill目录运行：

```bash
python3 scripts/validate_interview_question_pack.py <临时题包.json>
```

校验器检查字段、题量、难度、重复题和题型覆盖，不判断内容质量。字段错误必须修正；题量、难度分布和题型覆盖凑不齐时不反复重排题包，按 `SKILL.md`「完成条件」交付已通过的题。警告需人工判断。

校验通过后按以下规则交付：

1. 将题包写入用户当前要求的主产物；未指定格式的完整计划，默认写入XLSX的`面试题`或`问题清单`工作表，不单独增加JSON文件。
2. 按练习卡来写：XLSX中每道题一行，抽出就能练。按需设置`编号`、`题型`、`考察能力`、`难度`、`出题依据`、`题目`、`回答结构`、`可用真实证据`、`可能追问`、`红线`和`准备动作`等列。数组内容转成便于阅读的分点文本，不把原始JSON直接粘贴进单元格，也不要把题包压成两列长文。
3. HTML只按阅读需要展示题型分布、准备重点和少量核心题预览；完整题包保留在XLSX，避免跨文件重复。
4. 临时JSON写入主产物后清理，不在Answer中列为配套文件。只有用户明确要求JSON、接口数据或机器可读题包时，才将其作为用户产物交付。
5. 若用户明确只要DOCX、HTML、PDF、PPTX或聊天内容，则把题包按相应格式的人类可读方式呈现；不得因为校验使用JSON而额外交付JSON。

## 8. 质量边界

- 不把社区面经写成必考题，不承诺命中率。
- 不用虚假匹配百分比、通过率或薪资数据。
- 不编造经历、项目、技能、指标或公司事实。
- 不把简历或JD发送给未经批准的外部模型或OCR服务。
- 题包只服务当前面试计划，不扩张为泛化题库或无限模拟。
