# 个人计划

将一个主目标转化为现实、可执行、可检查的一次性计划。吸收规划复杂度，不要求用户理解模型、工具或工作流。

## 执行流程

1. **确定主目标**
  - 从请求中识别目标、期限、完成标准和所属领域。
  - 识别到多个目标时，主目标由用户确定，是这段时间优先要完成的重点。这一问放到第 3 步（补齐最小信息）一并提出，本步不单独调用工具；用户也可以选「几件都要、差不多重要」。其他目标写进同一份计划，按剩余时间和精力安排，合成一份完整计划。用户选「都要、差不多重要」时，几件一起排时间，不分成主要和次要。
  - 仅当主目标属于旅行、理财、写作创作、工作项目排期或普通提醒时，停止本流程并交给对应能力。这些类型若只是从属目标，仍留在本计划里一并安排。
2. **读取适用规则**
  - 每次先读 [planning-core.md](references/planning-core.md)。
  - 某个目标属于下面哪个领域，就加读哪个文件；主目标和从属目标同样处理：
    - 学习备考：当目标属于考试、证书、语言、课程或技能学习计划时，读取 [study-prep.md](references/study-prep.md)。完成标准是求职、面试或改材料，学习只是手段时，按职业与求职处理。
    - 健身减脂：当目标属于一般成年人的减脂、增肌、体能、居家训练或健身房计划时，读取 [fitness-fat-loss.md](references/fitness-fat-loss.md)。目标是伤病诊疗、用药或报告解读时，不读本规则。
    - 职业与求职：当目标属于职业规划、职业定位、材料准备、求职投递、面试备战、Offer谈判或入职准备时，读取 [job-search-interview.md](references/job-search-interview.md)。完成标准是通过考试或学会一项技能、求职只是背景时，按学习备考处理；目标是公司或团队项目交付时，不读本规则。
  - 其他个人目标：以通用规则为主，并按 `planning-core` 查证该领域的官方或专业来源（时效限制、权威方法、可用资源、验收标准），不凭空编造专业方法。
  - 只加载当前目标需要的规则文件。已经完整加载且上下文仍有效时无需重复读取；如果上下文压缩、目标发生变化，或需要核对具体字段和规则，可以重新读取相关章节。
3. **补齐最小信息**
  先复用对话、附件、记忆和用户已提供的信息，对照已读规则看还缺什么，再决定问不问。
  - 这一轮要补哪些信息：已读的 planning-core「2.1 计划所需信息」，加上命中领域文件的最低输入——学习备考看 study-prep「1.1 最小输入」，健身减脂看 fitness-fat-loss「1.1 最小输入」，职业与求职看 job-search-interview「2.1 最小输入」里当前阶段那一行。没有命中领域文件时按通用六项：主目标、完成标准、期限、当前状态、可投入时间、硬约束。领域文件只是把同一项要求得更具体，同一项不要问两遍。
  - 不是每个缺口都问。是否值得打断用户，按已读的 planning-core「2.1 计划所需信息」里那五条判断；问哪些、先问哪几个按「2.2 追问优先级」；多个目标还没定先做哪件按「2.3 多目标处理」。
  - 默认通过 1 次 `ask_user_question` 集中补齐信息，每次最多 4 个问题。只有用户第一次回答后，仍缺少会显著改变计划目标、负荷、方法或安全边界的关键信息，并且不能用清楚、保守且不危险的假设继续时，才进行第 2 次；第 2 次只问剩余关键缺口。第 3 步（补齐最小信息）合计最多调用 2 次。第 5 步（诊断目标合理性）因目标需要确认而进行的诊断追问不计入这两次。
4. **读取材料并核验事实**
  先读用户已经给的材料。诊断目标前，只核验会改变目标合理性、范围、资格或安全判断的硬事实；方法、资源和渠道留到第 6 步（生成与交付产物）查证。查证细则按 planning-core「4. 信息查证与方法选择」。
  - 有附件或用户贴了正文时，只用现有 `read`、`pdf`、`docx`、`xlsx` 和图片理解读取。用户贴了链接时，用 `web_fetch`。读附件不另写脚本、不安解析库。原生能力失败最多再试 1 次（合计最多 2 次），然后用已读到的内容继续；读不全的当作假设写进后续计划，不为读全附件继续尝试。解析脚本份数为 0，和生成表格的那一份脚本不是同一类。

    | 做 | 不要 |
    | --- | --- |
    | 用现有 `read` / `pdf` / `docx` / `xlsx` / 图片理解 | 写 `extract.py`、`ocr.py`、`fix.py`、`parse_pdfs.py` 等解析脚本 |
    | 原生读失败最多再试 1 次后继续 | 为读附件安装识别库或另一套读 PDF 的库；连写 `ocr1`…`ocr9`、`fix1`…`fix7` |
    | 读不全的当假设，进入诊断和出表 | 为抠全附件耗步数 |
  - 公开可查、且会改变目标诊断时，使用 `web_search` 或 `web_fetch`。出现以下任一情况即查：
    - 计划依赖可能变化的官方事实，如考试或报名窗口、资格、考纲、招聘批次、岗位硬要求；
    - 用户材料缺失、过期或相互冲突，不核验就无法判断目标范围、资格或时间容量；
    - 目标涉及健康或劳动权益，需要权威安全边界、停止条件或规则才能判断能否继续。
  - 不搜、不打开用危险手段达成目标的做法，如极端节食、脱水、违禁药物、惩罚性训练。安全只查已读规则和权威停止条件。
  - 只有用户本人知道的不搜：自己哪天考试、哪天面试、每周能花多少时间、伤病、个人经历。本步发现缺这些，如果第 3 步（补齐最小信息）仍有追问配额且符合第 2 次追问条件，可以补问；配额已满时，不再改用普通聊天追加追问。能够保守假设的，明确列出假设；不能安全假设的，不生成对应的高风险安排，并说明补充信息后才能继续细化。
  - 用户已经给了足够的最新官方材料，或搜了也不会改变任何阶段、任务或负荷：不搜。人人都知道的常识、只为多几条出处，都属于这种情况。
  - 本步不搜一句「如何完成某目标」，也不展开课程、题库、训练方法、求职渠道等资源研究。来源优先级为：官方/原始来源 > 专业机构或研究 > 可信行业资料 > 社区经验。社区内容只作为线索，不作为唯一依据。
  - 只记下查到了什么、来源与日期、如何影响目标诊断、还有哪些不确定。阶段和任务在第 6 步（生成与交付产物）写。
5. **诊断目标合理性**
  本步只检查目标合不合理，不写阶段和任务，不出文件；诊断只决定要不要追问，不换掉用户目标。看这份计划里全部目标合计，不是只看主目标；单件都能做、加在一起超出每周时间，也要提出来。
  - 从已读章节里发现问题：
    - 通用：已读的 planning-core「3. 目标合理性判断」
    - 学习：已读的 study-prep「3. 目标与时间校验」
    - 健身：已读的 fitness-fat-loss「2. 安全筛查」「3. 目标合理性」
    - 职业：已读的 job-search-interview「1. 阶段路由」「8. 计划阶段与任务」「10. 质量边界」
    - 未命中领域：只走通用判断和第 4 步（读取材料并核验事实）的查证结果，不编专业方法
  - 时间明显不够、标准不可控、可能伤身等，把原因说清楚即可，不要先贴「合理 / 能实现 / 安全」三种标签。
  - 用户原话已经够排期时，按原话写，查到的官方口径列为假设，不要再问。例如用户已说今年能报名、报几科、保几争几，就按这个排。只有两种答案会改变「今年还能不能报 / 还要不要排这科或这个目标」时，才需要确认。
  - 没有需要确认的问题：直接进入第 6 步（生成与交付产物）。有：只调用 1 次 `ask_user_question`，一次里可以多题（最多 4 题）；多件目标有问题时一题对一件，不再开第二次诊断追问。这次不计入第 3 步（补齐最小信息）的 2 次。写在普通回复里不算停：本轮一旦调用追问，就不出文件，等用户选择或超时后再进入第 6 步。不要一边说先确认、一边继续生成。
  - 题干讲清哪件目标有什么问题、希望怎么调整。每题第一项固定为不调整 / 按原目标继续（超时默认这项），其余项按本题诊断写成具体可执行的目标，不要空的「按建议调整」，含第一项总共不超过 4 项；用户要自己改，用工具自带的输入。
  - 完成选择或超时后立即进入第 6 步（生成与交付产物）。超时按第一项处理，不停在诊断结果，也不再要求二次确认。
6. **研究方法、生成与交付产物**
  目标确定后，先按 planning-core「4. 信息查证与方法选择」判断是否需要补充研究可靠方法、可用资源和渠道。只有研究结果可能改变计划路径、顺序、效率或任务对象时才搜索；使用第 5 步（诊断目标合理性）确认后的目标，不重复核验仍然有效的硬事实。然后读取 [output-contracts.md](references/output-contracts.md)，按该文件交付。
  - 三份文件怎么配合：已读的 planning-core 管通用阶段、任务和标准计划数据；已读的领域文件管该领域核心内容和本题触发的条件内容；本步读的 output-contracts 只管用什么形式呈现。先按已读的 planning-core「5. 进度和任务生成」「6. 标准计划数据」想清楚一份与格式无关的计划（目标、阶段、任务、标准），再加入领域核心和条件内容，按 output-contracts 直接写成用户要的文件。不要先落中间数据文件再渲染。
  - 一份完整计划最多一个执行版和一个阅读版。没提格式时执行版是 XLSX、阅读版是 HTML，两份都要写出再回复，不要只交一份再问。用户指定了 PPT / 汇报 / 演示 / 家长会 / 给家人讲 时，指定的就是阅读版，本轮不再产出 HTML；同时还要计划表再加 XLSX。只指定一种格式时，该格式就是全部文件产物。轻量安排只输出聊天计划卡。指定的文件未能生成时，按本文「完成条件」一节交付。用户没要求压缩包时不要打 zip。脚本、临时 JSON 等中间文件不是用户产物，不在 Answer 中列出或交付。
  - 颗粒度、起始日和「按周」怎么写，按已读的 planning-core「5.1 颗粒度」：8—30 天详细拆首周、其余按周；30 天以上详细拆前两周、其余给周节奏。不把数周以上的计划逐日铺满。用户没给开始日时，起始日从生成当天起算，不要输出大部分日期已经过去的日历。超出拆到日的时间段，执行表按周一行（日期范围、本周重点、做多少、完成标准；学习写题量或产出，健身写组次或时长），不要按日空转或把整周写成一段散文。同一张表里前半逐日、后半按周时，按周段另起一行表头，不要继续填进逐日那几列。从起始日到结束日中间不能断档：拆到日的每天都有行（休息日也写），按周的每一周都有行，两段日期要接上。日期、星期和周次按起始日推算，不要逐行手写再对日历。同一天的安排写在一起，里程碑并进当天，不单开里程碑行；同一天多个动作可以分多行，日期列可重复或合并，不要把当天所有动作堆进一格。发现周数或日历对不齐时，只改起始日或周数再出表，不重排任务。用户指定的具体日期原样保留。阶段切分和面向用户的称呼按已读的 planning-core「5.2 进度结构」：按策略转折切，不按自然月切；用户看得见的文字少用代号、多用白话，短但能看懂。
  - 本轮所有文件必须是同一套字段、同一份计划：阅读版帮助用户快速理解判断、路线和重点；执行版承载完整任务及用户自行填写的执行记录。阶段切分只做一次，先写入执行主产物（默认 XLSX 的阶段路线）；HTML、PPT 和聊天计划卡只引用这套阶段名和起止日期，不为「看起来整齐」重切。聊天计划卡最后写，阶段名、日期和关键数字从已写出的文件抄。不得分别生成两套计划，也不要写完再对字段。
  - HTML 阅读版用一次 `write` 直接写自包含完整页面。不要另写 Python 来生成或拼接 HTML（包括 `build_html.py`），不要用 f-string 拼，不要分段反复改，写完报错只 `edit` 这一份 HTML。阅读版按 output-contracts「4.4」写：内容可以全，细度不必跟执行表一样；第一次读就能看清全貌、里程碑和要做什么。不要把执行表明细贴进页面。页面里不要出现任何下载按钮或下载链接（包括 `href="#"`、`download` 属性、「见下方附件」），也不要把 HTML 再转成 xlsx。阅读版文件名用中文计划名。
  - PPT 按 output-contracts「4.3」一次生成完整稿（或一份脚本只跑一次），不配图也能交；生图失败跳过配图，不重试。阶段路线只写一次，后面页不重写日期。不要按页改文案，不要为单页溢出逐页打转。检查一次、修复一次，最多再生成一次，然后停。工作区里一旦有可打开的完整稿（常见文件名 `final.pptx`：演示文稿流水线产出的成品），立刻复制成中文计划名的 `.pptx`，这一步就是交付。指定了 PPT / 汇报 / 演示 / 家长会时，不要用 HTML 顶替；片子已在工作区后，不要回头重做执行表，也不要再写 HTML。步数将满时有片子就交片子。
  - XLSX 按 output-contracts「4.1」一次写入含样式。只写一份 JSON 数据，用一次 `write` 写完，再从本 Skill 目录运行 `python3 scripts/render_xlsx.py <数据.json> <中文计划名>.xlsx`。JSON 里必须有一张执行用的 `table`：表头有日期或周次（或日期范围），并且有数据行。列头按已读领域文件写，不要为过报告改成「动作」「数量或输出」。学习用 `学习内容`（或 `科目/模块`）和 `题量或产出`；健身用 `动作`（或 `训练内容`）和 `组次` 或时长；求职用 `任务` 或 `投递动作`。填写列 `状态`、`实际结果`、`反馈/问题` 整本至少出现在一张表里，格子留空；不要预填「未开始」「进行中」「完成」或「跳过」，下拉选项可以有，格子里不要先写字。标明「示例」的示范行可以带字。执行表不能整张只写 heading / kv 共用规则；规则最多放在该表上方几行。健身用 `训练安排` 当执行表，组次 / RPE 写在行上或动作说明阅读表，不要只用「每周 3–4 次」代替排期。JSON 语法错了只 `edit` 这一份 JSON。计划数据只手写这一份 JSON，不要另写 Python 来生成 JSON 或 HTML（包括 `gen_plan.py`、`build_plan.py`、`build_json.py`、`ielts_plan.py`、`gen_testdata.py`、`build_html.py`、`fix_plan.py`、`check.py`、`check2.py`、`check_plan.py`、`peek.py` 或任何 openpyxl 脚本），不要读或改 `render_xlsx.py`。表太大就按已读颗粒度缩小（按周不按日），不要拆成很多次写入。不要 `load_skill` 读取 `xlsx` Skill，不要写公式；只有用户明确要求表格能自动汇总时才用公式。耗时合计、完成率直接写静态值。
  - 字体、表头、列宽由 `render_xlsx.py` 写入。渲染成功时回包会打 5 行结构报告（写出路径、表名、执行表、填写列、预填）。结构项只看这 5 行：有 FAIL 就只改这一份 JSON，再跑一次渲染，然后停——第二次之后无论还是否 FAIL，都写阅读版并回复。不要另写 `check.py`、`check2.py`、`check_plan.py` 或任何核查脚本，不要扫 `font.name`，不要用 `head` / `tail` 截断回包，不要打开 `render_xlsx.py` 对判定逻辑。用途和内容（概览是否墙、一格一事、列头是否像该领域、是否跟已读领域规则一致）在脑子里过一遍，和结构 FAIL 一起改，不要为此写脚本。没写出、打不开或空表（看不到阶段或具体安排才算空表）时，报错一次看完，只改这一份 JSON，再跑到打得开且不是空表。空格或合并区里空着的格子的默认西文字体不算没过。渲染失败也不要改写 openpyxl 自己出表。
  - 需要默认 HTML 阅读版时：xlsx 打得开且不是空表后，下一动作是一次 `write` 写出 HTML，阶段名和起止日期从执行版抄。不要先写 `build_html.py`。指定了 PPT 时阅读版就是 PPT，xlsx 打得开且不是空表后立刻做 PPT 并复制成中文交付名，不要写 HTML。步数将满且 xlsx 已写出、指定的阅读版还没有时，先补阅读版再回复，不要再改表。
  - 写哪一套跟第 5 步（诊断目标合理性）的选择：第一项或超时，该件按原目标写；选了某调整项，按该项写；自定义输入按写下的写；多题各跟各的选择；没问到的目标保持原样。
  - 已读的 planning-core「3.3 激进目标与用户选择」：只写用户选定的一套阶段和任务，不要写成推荐加挑战两套执行任务，也不加`方案`列。用户坚持原目标时仍按原目标写一套；问题和建议写在计划判断或概览区域。危险动作即使用户坚持也不写入详细执行任务。
  - 多个目标按已读的 planning-core「2.3 多目标处理」写进同一份计划。职业与求职按已读的 job-search-interview「1. 阶段路由」：只把现在最该推进的那一阶段（定位、材料、投递、面试、Offer 或入职）写成详细任务，其余阶段写成后续里程碑，不要一次铺完全流程。
  - 需要针对性面试题包时，读取 [interview-question-design.md](references/interview-question-design.md)。按该文件使用临时JSON组织题目并从本Skill目录运行 `python3 scripts/validate_interview_question_pack.py <临时题包.json>`；通过校验后，将题目写入当前用户产物，默认放入XLSX的`面试题`或`问题清单`工作表；校验反复不通过时，交付已通过的题并说明少了哪类，不反复重排题包。临时JSON只用于机器校验，写入用户产物后清理；除非用户明确要求结构化JSON，否则不得把它列为配套文件或交付给用户。不需要题包时不加载此文件。
7. **判断是否创建定时任务**
  - **不创建且不推荐**：用户没要求创建定时任务、提醒、到点通知或推送，也没有「错过会造成明显损失、到点能产生新内容、需要提前准备」的高价值节点。本轮不创建、不读取 [schedule-prompts.md](references/schedule-prompts.md)，直接完成交付。
  - 用户明确要求创建定时任务、提醒、到点通知或推送，或存在上述高价值节点时，读取 `schedule-prompts.md` 了解定时任务生成规范。最多建议 3 条，同一计划最多 1 条重复；不要把每天的学习、训练或投递转成定时任务。细则按 schedule-prompts「2. 数量与频率预算」。
    - **直接创建**：用户明确要求创建，且能从请求或计划中确定任务名称、时间、重复方式和任务内容，或能得到唯一、低歧义的合理推荐值。本轮直接创建，不要求用户逐项再次确认。
    - **不创建，只在 Answer 结尾推荐**：用户没有要求创建，但存在高价值节点；或用户明确要求创建，但关键参数存在多个差异明显的选择，无法可靠推断。本轮不创建，在 Answer 结尾列出拟创建的 1—3 条（任务名称、时间、重复方式、任务内容），问用户要不要；下一轮确认后再创建。本步不调用 `ask_user_question`。



## 工具规则

何时调用、调用几次由执行流程各步决定；本节只列可用能力和通用约定。

- `ask_user_question`：按第 3 步（补齐最小信息）和第 5 步（诊断目标合理性）的配额调用；第 4 步（读取材料并核验事实）如需补问，占用第 3 步（补齐最小信息）的剩余配额；第 7 步（判断是否创建定时任务）不调用。
- `web_search` / `web_fetch`：查公开事实；用户贴了链接用 `web_fetch`。
- 读用户材料：只用现有 `read`、`pdf`、`docx`、`xlsx` 和图片理解。不要另写解析脚本，不要为读附件安装库。这里的 `xlsx` 是读用户已有表格，不是去 `load_skill` 读取 `xlsx` Skill。
- `docx` / `pptx` / `pdf` / `write`：按 output-contracts 渲染；`write` 可用于生成自包含 HTML 和计划 JSON。写计划表只调用本 Skill 的 `scripts/render_xlsx.py`，不要 `load_skill` 读取 `xlsx` Skill，不要自写 openpyxl。指定 PPT 时，工作区成品必须复制成中文交付文件名后再回复。
- `task_schedule`：创建定时任务前先通过 load skill 读取 `task_schedule` Skill；节点、数量、频率和固定指令按 schedule-prompts。
- `picture_search` / `video_search`：只在健身动作说明等确有帮助时补充可信参考。
- 同一条命令超时或没有返回时，不重复运行，改用不依赖该工具的方式或跳过。

外部来源、许可证和未引入脚本的审计记录保存在 [source-attribution.md](references/source-attribution.md)，仅在维护 Skill 时读取，执行用户计划时不要加载。

## 运行约束

- 只生成当前会话的一次性计划和文件。
- 不读取未来执行状态，不维护个人档案、计划进度、打卡记录或多目标看板。
- 不承诺跨会话记忆、自动复盘或自动修改原产物。
- 定时任务只能使用创建时写入的固定指令和必要摘要，不得读取原计划文件、自动获取用户执行状态或虚构完成进度。
- 不编造用户经历、学习成绩、身体状态、公司事实或官方规则。
- 医疗、心理、劳动法律等高影响内容只做信息整理、一般性计划和风险提示，不替代专业意见。



## 完成条件

文件一旦打得开且不是空表，立即按各格式的交付检查收手。XLSX 的结构项看渲染回包那 5 行，用途和内容在脑子里过一遍：有 FAIL 或用途没做成，只改 JSON 再跑一次 `render_xlsx.py`，然后停。第二次之后不要再为报告改列名、拆脚本或重写 JSON。不要读或改 `render_xlsx.py`，不要另写核查脚本，不要扫字体。PPT 仍是检查一次、修复一次。空格默认西文字体不算没过。JSON 一次 `write` 写完。需要默认 HTML 阅读版时，xlsx 打得开且不是空表后立刻用一次 `write` 写出 HTML，不要先写 `build_html.py`。指定了 PPT 时，工作区成品复制成中文交付文件名再回复，不要用 HTML 顶。之后不再为样式、文案、排版、丰富度、字段重命名、压缩打包或用户没要求的格式继续修改。

读附件只用现有读文件能力，失败最多再试 1 次后用已读内容继续，不写解析脚本。某个文件生成失败、写到一半超时或步数将满时，交付已成功的产物，如实说明缺了哪一份；xlsx 已写出而指定的阅读版未写时，先补阅读版再回复（指定 PPT 就交 PPT，不要改交 HTML）。没有文件时交付聊天计划卡。不得声称失败的文件已经生成。

面试题包按第 6 步跑本 Skill 的题包校验即可。
