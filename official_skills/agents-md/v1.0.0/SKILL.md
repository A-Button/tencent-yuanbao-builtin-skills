# AGENTS.md 文档生成器

## 概述

本 Skill 用于分析功能模块代码并生成/维护专业的 AGENTS.md 文档，为 AI 提供准确的模块功能、使用场景和架构信息。

## 适用场景

当出现以下情况时应使用本 Skill：
- 用户请求为某个目录/模块**生成** AGENTS.md 文档（create 模式）
- 用户请求**更新**已有 AGENTS.md（update 模式）
- 用户不确定目录状态，希望**智能判断**（auto 模式）
- 用户请求**批量更新**所有子项目的 AGENTS.md（update --all）
- 用户使用类似 "生成 AGENTS.md"、"创建模块文档"、"更新模块文档"、"agents-md auto" 等短语
- 用户指定目录路径并要求生成/更新文档

## 模式路由

入口先判断 **mode** 和 **target**，再进入对应流程：

| 模式 | 功能 | 典型调用 | 入口章节 |
|------|------|---------|---------|
| `create` | 全量生成 AGENTS.md（从零创建） | 新模块首次生成 | [流程 A：create](#流程-acreate全量生成) |
| `update` | 增量更新已有 AGENTS.md | 模块代码变更后同步文档 | [流程 B：update](#流程-bupdate增量更新) |
| `auto` | 智能判断：有 AGENTS.md 则更新，无则创建 | 不确定目录状态 | [流程 C：auto](#流程-cauto智能判断) |
| `update --all` | 批量更新所有子项目 | 全局同步所有模块文档 | [流程 D：批量更新](#流程-dupdate---all批量更新) |

**模式识别规则**：
- 明确指定 `create` / `update` / `auto` → 使用指定模式
- 只给了目录路径没指定模式 → 默认 `create`
- 指定 `--all` → 走批量更新
- 未指定目录 → 使用当前打开的目录

## 核心原则

### 准确性原则
- **CRITICAL**: 严格基于代码实际内容进行分析，禁止推测或臆断代码逻辑
- **CRITICAL**: 确保所有功能描述都有对应的代码实现支撑
- **CRITICAL**: 遇到不确定的代码逻辑时，必须向开发者提问确认，而非猜测或跳过

### 简洁性原则
- **IMPORTANT**: 在保证核心功能介绍清楚的前提下，内容尽可能简洁
- **IMPORTANT**: AGENTS.md 是给 AI 看的，聚焦业务逻辑，避免通用开发知识
- 避免冗余描述，重点突出关键信息
- 使用清晰的层次结构组织内容
- **禁止包含的内容**：
  - ❌ 通用的性能优化建议（useMemo、memo、防抖等）
  - ❌ React/前端通用最佳实践
  - ❌ 工程化配置（构建、测试、linter）
  - ❌ 样式编写技巧

### 完整性原则
- 确保覆盖模块的所有主要功能
- 包含必要的使用示例和注意事项
- 提供足够的上下文信息

### 使用场景优先原则
- **CRITICAL**: 必须说明组件/模块在哪里被调用、如何被触发
- **CRITICAL**: 通过 `search_content` 搜索所有调用位置
- 使用场景应包含：调用位置、触发时机、传递数据

### 疑点提问原则
- **IMPORTANT**: 分析过程中遇到以下情况时，必须暂停并向开发者提问：
  - 代码逻辑复杂且无法从上下文推断其意图
  - 存在多种可能的功能解释，无法确定正确含义
  - 发现潜在的设计模式但不确定其应用场景
  - 模块间依赖关系不明确
  - 业务术语或领域概念不清晰
- **提问格式**: 清晰描述疑点位置、当前理解、可能的解释选项
- **继续条件**: 获得开发者明确回复后再继续分析

## 流程 A：create（全量生成）

从零为指定目录生成 AGENTS.md 文档。

**CRITICAL**: 以下步骤必须制定计划逐步执行

### 第一步：准备工作

1. 确定目标目录
    - 从用户输入中提取目标目录路径
    - 如果用户未指定目录，询问用户需要分析的目录
    - 验证目录存在且可访问
2. 在目标目录中生成临时记录文件 `.analysis-temp.md`


**临时记录文件模板**
```markdown
<!-- .analysis-temp.md 初始模板 -->
# 代码分析临时记录

## 分析进度
- 目标目录: [路径]
- 开始时间: [时间戳]
- 已分析: 0/[总数]

## 文件列表

<!-- 文件列表 -->
[ ] [文件路径]

## 分析结果

<!-- 每个文件分析完成后追加到此处 -->
```

### 第二步：目录结构分析

- 使用 `find [DIR_PATH] -type f -print` 输出目录下所有文件列表
- 将文件列表记录在 `.analysis-temp.md` 中

```markdown
[ ] [文件路径]
```

### 第三步：使用场景调研

**CRITICAL**: 在代码分析前，先找到模块的所有调用位置。

#### 调研步骤

1. **搜索调用位置**: `search_content(pattern="组件名|Hook名")`
2. **读取调用代码**: 查看触发时机（点击、Hover、页面加载等）
3. **记录场景**: 调用位置、触发时机、传递参数

### 第四步：代码深度分析

**CRITICAL**: 代码深度分析必须通过 **subAgents** 执行，避免占用主任务的上下文空间。

#### 执行方式

1. **创建 subAgent**: 为代码分析创建独立的 subAgent
2. **传递必要信息**: 传递以下内容给 subAgent：
   - 目录路径和文件列表
   - [代码文件分析指南](./references/code-analysis.md) 的完整内容
3. **subAgent 执行**: 在 subAgent 中完成所有文件的逐一分析
4. **结果回传**: subAgent 完成后，将分析结果（临时记录文件）回传给主任务
5. **疑点收集**: 分析过程中遇到的疑点应记录在临时文件中，待主任务统一向开发者提问

#### subAgent 指令模板

```
按照以下代码文件分析指南，分析目录 [目标路径] 下的代码文件：

[此处插入 references/code-analysis.md 的完整内容]

执行步骤：
1. 创建临时记录文件 .analysis-temp.md
2. 逐个分析代码文件，每个文件分析完成后更新临时记录并清理上下文
3. 分析完成后保留临时记录文件供主任务使用
```

### 第五步：疑点确认

**IMPORTANT**: 在生成文档前，必须处理分析过程中收集的所有疑点。

1. **疑点汇总**: 从 `.analysis-temp.md` 中提取所有标记为疑点的内容
2. **向开发者提问**: 将疑点整理成清晰的问题列表，向开发者确认
3. **等待回复**: 暂停执行，等待开发者回复
4. **更新分析结果**: 根据开发者回复更新临时分析文件

**提问模板**:
```
在分析过程中遇到以下疑点，请帮忙确认：

1. **[文件路径]**: [疑点描述]
   - 当前理解: [你的理解]
   - 可能的解释: A) ... B) ...

2. **[文件路径]**: [疑点描述]
   ...
```

### 第六步：生成 AGENTS.md

基于代码分析结果和使用场景调研生成最终的 AGENTS.md 文档。

详细的生成流程、文档模板和编写指南请参考 [AGENTS.md 生成指南](./references/agents-md-template.md)。

**核心步骤**:
1. 读取 `.analysis-temp.md` 分析结果
2. 整合使用场景调研结果
3. 按模板格式生成各章节
4. **优先编写"使用场景"章节**
5. 进行交叉验证确保准确性

### 第七步：质量审核

1. **长度检查**: 确认文档总长度控制在 500 行以内
2. **使用场景检查**: 确认是否说明了所有主要调用位置和触发时机
3. **文件清理**: 确认 `.analysis-temp.md` 是否已清理

## 流程 B：update（增量更新）

对已有 AGENTS.md 进行增量更新，只修改有变更的部分。

### 前置检查

1. 验证目标目录存在 AGENTS.md，不存在则提示使用 `create` 模式
2. 检查是否存在 `.codebuddy/rules/update-agents-md.mdc`（或 `.ai/rules/update-agents-md.mdc`）

### 有 mdc 规则时

按该规则执行增量更新：读取并执行 `update-agents-md.mdc` 中定义的更新规则（通常包含项目定位、文档格式、更新原则等）。

### 无 mdc 规则时（通用增量逻辑）

1. 读取现有 AGENTS.md
2. 扫描 `src/` 目录，对比变更：
   - **新增模块**：在文档对应章节添加描述
   - **删除模块**：从文档中移除对应章节
   - **修改模块**：仅更新变更部分的描述
   - **无变更模块**：完全保留原有描述
3. **CRITICAL**: 禁止全量重写，只做增量修改

### 增量更新原则

- **增量性**：只更新有变更的部分，保留无变更内容
- **简洁性**：每个模块用 1-2 句话描述核心功能
- **准确性**：基于代码实际内容描述，避免过度推测
- **格式一致**：更新时保持与现有文档相同的格式和结构

## 流程 C：auto（智能判断）

自动判断目标目录状态，分发到 create 或 update：

```
检查目标目录是否已有 AGENTS.md
├── 有 AGENTS.md
│   ├── 有 update-agents-md.mdc → 执行 update（用 mdc 规则）
│   └── 无 update-agents-md.mdc → 执行 update（通用增量逻辑）
└── 无 AGENTS.md → 执行 create
```

输出判断结果，告知用户实际执行的模式。

## 流程 D：update --all（批量更新）

批量更新所有子项目的 AGENTS.md。

### 执行流程

1. 读取 `apps/` 和 `packages/` 目录下的所有子目录，生成目录列表
2. 遍历目录列表，检查每个目录下是否有 `.codebuddy/rules/update-agents-md.mdc`（或 `.ai/rules/update-agents-md.mdc`），无规则的目录从列表中剔除，输出最终目录列表
3. 遍历剩余目录，按顺序执行更新：
   - **IMPORTANT**: 每个目录启动独立的 Task 执行，避免混合上下文
   - 读取目录下的 `update-agents-md.mdc`，使用其中定义的规则更新 AGENTS.md
   - 如果某个目录更新失败，跳过并输出错误信息，继续下一个
4. 全部完成后输出汇总信息（成功 / 失败 / 跳过的目录数）

### 注意事项

- **独立上下文**：每个子项目用独立 Task 执行，避免上下文污染
- **增量更新**：只更新有变更的模块描述，无变更保持原样
- **格式一致**：更新时保持与现有文档相同的格式和结构

## 目录类型智能识别

create 模式下，skill 根据目录特征自动识别类型并针对性生成文档：

| 类型 | 特征 | 生成重点 |
|------|------|---------|
| 项目目录 | 含 `package.json`、`tsconfig.json` | 项目概述、技术栈、依赖关系、目录结构 |
| 组件目录 | 目录名含 `components/` 或大量 `.tsx` | 组件功能、Props 接口、组件层级、关键词标签（功能/场景/技术/业务四维） |
| 公共类目录 | `utils/`、`common/`、`shared/`、`lib/` | 工具函数分类、常量配置、类型定义 |
| API 目录 | `api/`、`services/`、`request/` | 接口分类、数据结构、错误处理 |

3. **代码引用**: 在代码块中保持原始英文名称

## 最佳实践

### 使用场景优先
1. **先找使用场景，再分析代码**：用 `search_content` 搜索调用位置
2. **触发时机要具体**：❌ "在群聊页面使用" → ✅ "右键消息 → 选择'转发'"

### 代码分析技巧
1. 对于文件数量超过 50 的模块，分批分析
2. 优先分析入口文件（index.ts、main.ts）
3. 重点关注对外导出的 API 和组件

### 文档原则
1. **章节顺序**: 模块概述 → 使用场景 → 目录结构 → 核心功能
2. **简洁为王**: 避免冗余，突出关键信息
3. **实用导向**: 优先回答"在哪用"、"怎么触发"

**记住**: AGENTS.md 是为 AI 和开发者提供模块理解的关键文档，应确保内容准确、结构清晰、易于理解。
