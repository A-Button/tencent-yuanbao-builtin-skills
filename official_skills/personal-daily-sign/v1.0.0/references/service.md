# 服务安排与回到原会话

内容依据、频率和送达时刻已经明确就推进，不再问“要不要帮你创建任务”。缺少服务参数时先按 [入口与需求澄清](experience.md) 补齐；“明早一次”走 once，“每天”走 rrule。当前 make-things 的时间型 Todo 需要实际送达时刻；用户已说每天而未说几点时，只补问时刻，不自行设定。若当天已有足够内容，可先交付今天这一张，并在同轮只追问送达时刻；单张图片的回执不等于 Thing、Todo 或 Trigger 已建立，也不再问用户要不要每天收到。当天内容也未到齐时等用户提供，不用空值先造一张。

## 创建与展示

按技能名加载 make-things，以当前能力完成 Thing、Todo 与 Trigger 的关联，并在依赖完整后启用规则。先定位**本次原 Session 绑定**的服务；`get_thing` 按关键词返回的同名 Thing 可能来自用户的其他会话，只能在可信上下文或工具返回能确认当前会话归属时复用。用户说“改成、以后换成”时，委托对象是已有服务：先沿旧会话或实际支持的跨会话接口修改它。若当前会话无法改到旧服务，说明旧安排仍在，并让用户选择在原会话修改还是明确另建当前会话服务；不能以新建替代修改。用户明确要在新会话开始一项持续服务时才创建新的 Thing。会话归属决定 Trigger 投递目标与此刻关联，不能只凭标题相同修改旧 Thing。

默认开通请求先按真实 Thing/Todo 与会话归属查重。已有可管理的日签服务就沿用；查到其他会话的日签而当前不能管理时，保留旧安排并说明尚未绑定到本会话，不另建一个同名每日服务。

创建时以实际接口完成 Thing、Todo、Trigger 的同一服务绑定。接口若支持创建 Thing 时一并写入 Todo、创建 Trigger 时直接绑定并启用，可使用这条短链；否则按 make-things 的分步能力写入。无论哪条链，记录真实 thing_id、todo_id、trigger_id 与下次触发时间，并在可读接口中核对 Todo 与规则的关联；创建回执早于绑定时 `rule_ids` 为空，不等于最终关联状态。

`get_thing` 返回的 Todo 状态、时间和进展用于日签选材。`trigger/list_triggers` 用于核对当前可管理服务的规则开关与投递安排，例如创建、改时间或排查未送达；它不提供用户近期生活进展。跨会话规则可能无法读取，查询失败不表示规则已停用，日常选材也无需逐个查询其他事项的 Trigger。

| 内容 | 写法 |
|---|---|
| Thing title / goal | 我的日签 / 只记用户明确委托的主体、持续内容范围、接收安排和已确认口味，用可读的短句表达。当天候选事项每天重新读取；历史查询推测的人物、地点、身份与行程不写入 goal。旧 goal 中来源不明的个人描述只作待核线索；专业计算所需的详细资料留在相应依据记录 |
| 每日 Todo title / description | 每日签 / 每天 {用户确认时刻}，为你准备一张日签。使用真实值 |
| 单次 Todo title / description | 今日签 / {用户确认日期与时刻}，为你准备一张日签。使用真实值 |
| schedule_info | kind=TIME；time 中含实际 schema 的 cycle、time_of_day；单次还含 date |
| 每日 Trigger | rrule、FREQ=DAILY、用户时区未来的 dtstart、真实 timezone；无条件日签不加 judge |
| 单次 Trigger | once，使用未来 run_at；不以 DAILY 模拟单次 |
| instruction | `先加载 personal-daily-sign，核对本次绑定的日签服务及今天是否已交付。用已确认偏好定口味；服务包含生活预览时，调用 get_thing 读取相关 Thing/Todo 的最新状态，以仍在进行的事项理解近期阶段，以今天到期或有真实变化的 Todo 选择当天线索。user insight 中的历史搜索、问路和商品比较只作兴趣候选，不认定身份、行程或当前状态；旧日签 goal 中未确认的描述同样处理。此刻已有内容若可读，用来避重，不作为必需数据。选一两个线索写给人的签文，不复述资料和事项清单。当天信息不足时沿已确认口味创作，不编造进展；在原会话交付一张图与签文，再发布此刻卡片。` |

cycle 的具体枚举、时间编码与状态值读取真实工具 schema，不从展示文案猜。相对时间和“今天几点”先按 make-things 方法取钟，起点必须在未来；避免沙箱缺失 zoneinfo 导致 UTC 偏移。write_todos 的 expected_version 使用真实返回的值，类型遵循当前 schema。

Trigger 将上述执行指令投递到创建 Thread/Thing 时绑定的原 Session，运行时提供关联引用。初次建立服务的用户请求保留在原会话，不作为每日新消息重发；原 Session 用于定位委托与保留可回聊的历史，每天仍要读取当次可用的状态。此刻关联同一真实服务时沿这一会话绑定；若 `show_widget` 明确拒绝归属，先核对是否误用了跨会话 Thing，不能把去掉 Thing/Todo ID 的成功发布当成已关联服务。已有仅投递 `创建日签` 的规则仍按本技能的定时入口处理；绑定或发现失败时记录待恢复。

用户调整已有服务的取材与表达规则时，沿原会话和实际 make-things 能力同步原 Trigger 的 instruction；仅替换 Skill 包不等于已保存的规则文案随之改变。旧规则仍能唤起本技能时，定时执行沿当前技能流程判断内容；规则无法读取或更新时如实保留该状态。

用户在安排确定前先发来当日时长、心情等内容时，核对原会话里已表达的每日意愿与尚缺条件；完成当天的签后继续补齐安排。服务建立后，用户再发每日数据时按当地日期定位同一 Thing 与当日记录，必要时完成等待数据的那张签，不为每条消息新建 Thing 或重复生成。累计与连续天数只从可重读的真实记录计算；未保存成功时不承诺以后会自动累加。

## 偏好与历史

会话保存用户回答与专业依据；可读 goal 保存恢复安排所需的偏好摘要。云端在 `/data/user/personal-daily-sign/` 创建用户级存储保存完整内部状态：以真实服务 ID 隔离，包含 preferences、引用、当地日期、完成图、必要时另做的横版封面、签文、每张所用焦点与依据、相关 Thing/Todo 上次可见状态和时间、修订号、发布请求和回执。本地由宿主提供实际用户存储路径，Skill 包路径随加载位置确定。

审美记录注明依据是用户明确选择、历史认可、insight 线索还是本次创作选择。Agent 自行使用的画风保留为创作记录，后续可按内容调整；旧 goal 中来源不明的风格词也只作参考。用户对画面给出新反馈时，在已有服务中更新审美依据并保留旧记录，下一次按新依据创作；原有接收安排继续沿用。上述来源信息放内部简报，沿现有工具字段保存。

状态读写使用宿主文件能力或已有业务存储，无须新增 Thing 工具。每次重读后仅合并本次变化，保持完整原始值；旧 `[personal-daily-sign-state]`、旧渠道回执无损迁移。内部简报与长状态不塞进 Todo.description。存储不可用时保留会话中的真实结果并说明持久化待完成，不虚构已恢复或已写入。

## 定时回调与查看

1. 按真实引用重读服务、Todo 与已保存的当地日期跳过安排；暂停/关闭或本次投递日期已被跳过时静默结束。无法读取状态时暂缓自动生成与发布。
2. 按用户当地日期查主签；重复回调复用已有图片。首次创作先取已确认的内容与审美偏好。服务包含生活预览时，按当前 make-things 能力调用 `get_thing`，读取委托范围内相关 Thing 及其 Todo 的状态、更新时间与临近节点。Thing 仍为 ACTIVE 只说明服务存在：以 Todo 的实际状态判断哪件事仍在推进，自动监控的检查节奏不等于用户今天要完成的事。比较上次可见记录后选取近期阶段与今天真正到期或变化的线索；此刻已有卡片若可读，用于判断今天已经说过什么，否则使用日签自己的交付记录。天气、节日或专业结果按 [每张日签的内容创作](content-directions.md) 判断是否适用，不要求全部具备。本次 SP 注入的 user insight 只为明确偏好与候选兴趣补充信息，历史查询和旧 goal 的推断不升格为当前事实。查询不可用时沿已确认偏好与近期日签创作，不声称看见新进展；明确约定的专业依据缺失时保留待继续状态，沿真实结果或已同意的备选方案继续。
3. 生成后在原会话直接展示完成的图片与签文，记录真实 URL 和该修订的交付结果；同一修订已经交付时复用记录，已发布当日主签则不重复发布。
4. 新内容准备好后按 [此刻卡片](now.md) 发布一张卡片，保存请求与 now_id。未知发布结果先核对，图片不重做。

查看旧签按用户主动输入的日期与修订定位，不刷新成今天的新签。此刻的“查看完整签文”和整卡点击静默打开原会话，用户在那里阅读原回答；旧卡带 send_prompt 的回流按实际内容兼容处理，新卡按此刻协议省略该字段。一次性任务按实际完成结果收束；每日重复 Todo 保持持续运行。

## 修改

| 用户意图 | 动作 |
|---|---|
| 换画风、短一点 | 更新相应偏好；指向本张时新增修订，否则下一次生效 |
| 补齐依据，如“每天出，喜木火”；纠正当张错误 | 保存新依据与来源，修订当张并在会话交付，按此刻协议处理原卡同步；已明确的每日意愿和时间沿用 |
| 改时间 | 保留偏好和 rule_ids，更新 schedule_info 与原 Trigger 的未来时刻 |
| 暂停、关闭 | 停用自动规则并暂停对应日签 Todo；保留历史 |
| 重启 | 复用原服务与偏好，确认接收安排，从未来起点启用所需规则 |
| 今天跳过 | 按用户当地日期保存一次跳过安排，覆盖当天后续自动生成与发布；每日规则与以后日期继续沿原安排。已经交付的历史保留，用户另行主动索取时按单次请求处理 |
| 以后我来时再给 | 停用自动规则并保留偏好、历史；之后由用户主动请求单张，重启每日服务需要新的持续意愿 |
| 忘记某个偏好 / 以后不提某主题 | 更新实际可写的偏好记录及恢复副本；按下节处理撤回或排除范围，不改接收时间 |
| 临时再看一次文字，原安排照旧 | 只做本次解读，原 Thing/Trigger 不变 |

每次写 Todo 都保留所有未改的可写字段，特别是完整 rule_ids、schedule_info、cover_url、action。版本冲突重读后合并。规则停用创建、全量写入和部分失败恢复遵循 make-things；只报告真正保存、启用或发布的部分。

当日状态分别保存最新内容修订与此刻已发布修订：`content_revision`、`published_revision`、真实 `now_id`、`sync_status`。会话交付另记已交付修订及实际可见结果；状态未知时先核对。这些是内部存储字段，沿真实接口组装请求。更新 Todo.cover_url 只确认任务封面已保存；此刻同步独立确认，旧图与旧回执保留。

## 撤回偏好与排除主题

“忘记这个偏好”表示该偏好退出后续选题与画风判断；“以后不提这个话题”表示保存用户明确的内容排除范围。使用现有用户状态记录撤回/排除的对象、范围与时间，并清理实际可写的偏好字段及恢复副本。回调先应用最新撤回与排除，再使用 insight、旧 goal 或历史签；旧记录中的已撤回值仅保留为历史，不重新提升为当前偏好。

这属于日签业务内的偏好使用控制。聊天历史或宿主长期记忆若无可写能力，说明实际处理范围；用户要求彻底删除资料时沿宿主真实删除能力处理。历史图片与签文保持原值，用户明确要求删除它们时再处理。成功读取不到最新控制状态的后台回调暂缓创作，避免使用已撤回的偏好。

## 停止与重启

“暂停、关闭、取消日签”默认停止后续自动日签，保留已生成的图片、签文、偏好和原服务绑定；用户明确要求删除历史时另按实际删除能力处理。按真实绑定定位目标服务，调用当前 `make-things` 的停用规则与更新 Todo 能力；共享 Thing 中的其他安排不受影响。操作后以真实回执说明哪些已停、哪些仍待完成。重启复用原服务与仍适用的偏好，确认新的接收安排后从未来时刻恢复规则。
