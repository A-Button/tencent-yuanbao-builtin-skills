# 简历方法：诊断与改写

覆盖简历诊断与按岗位改写/投递材料两类任务（均属场景 1 · 简历美化）。目标是给出有事实依据、可解释、可直接使用的结论与材料，不编造经历、职级、成果或数字。

## 用户级持久化与隐私

- 诊断/改写需要读取简历内容：直接读取用户给的本地简历文件或用户粘贴的内容用于分析。
- 本轮提供文件时，先提取可读的规范化 Markdown，再调用 `scripts/state_store.py freeze-resume`，把原件和规范化副本复制到 `/data/user/job-hunting/materials/resumes/<resume_id>/`。不得把会话级 `/data/inputs/...` 路径当作长期路径。
- 本轮没有提供简历时，优先读取 `/data/user/job-hunting/state.json` 中 `profile.resume_path` 指向的当前版本；文件不存在才请用户重新提供。不得因为换了对话就声称没有简历，也不得擅自选用非当前版本。
- `state.json` 只存持久路径、版本索引和结构化诊断，不落全文；回复只给分析结论与必要证据，不回显联系方式、证件号等无关个人信息。
- 简历与改写稿只存用户持久目录 `materials/`，不写入技能安装目录，不复制到 Thing/Todo/Trigger 或卡片 DataModel，也不外发。

## 一、简历诊断

产出三类结论 + 一个综合评分，全部基于简历自身事实：

- **亮点**：如经历完整、职级清晰、与意向岗位匹配的可验证证据。
- **待改进**：如项目缺量化结果（只写「做了什么」缺 GMV/转化率等）、技能与目标岗位关键词不够贴合、经历顺序不利于阅读。
- **修改建议**：针对每条待改进给具体、可执行的下一步；不确定处列为待补事实，不猜。
- **综合评分**：对简历完备度的相对判断，说明构成；不冒充过筛率或录用概率。

诊断只描述简历，不虚构外部数据；无法确定的内容明确标出，交由用户补充。诊断结果写入用户账本的 `profile.diagnosis`，并带上对应的 `resume_id`（见 [状态规则](state.md)）。

## 二、按岗位改写

按请求选择范围：局部润色、补充经历、针对 JD 改版、从零整理或排版导出；不要把一句话修改扩成全套重写。

1. **事实基线**：读用户指定版本与相关岗位 JD，建立可追溯清单（经历、角色、起止、职责、协作边界、交付物、结果、来源）。冲突只追问影响本次输出的事实。
2. **JD 到经历取舍**：把职责拆成业务问题/预期产出/方法/工具/资历，建立「JD 要求—经历证据—处理」对应表。有证据的用岗位术语准确表达；信息不完整的提问，不补成能力声明；无证据或用户否认的不写入。
3. **正文改写**：每条经历回答「解决了什么、你亲自做了哪部分、用了什么方法、结果与依据」。按真实职责选动词（协助≠主导）；指标保留时间范围、分母、单位与个人/团队归属；无数字用已确认产出，不估漂亮数字；未上线的不写成已发布。
4. **投递材料**：只做用户需要的——岗位简历、求职信、HR/内推联系草稿、投递表单答案、作品说明；共用同一事实基线，公司名/岗位/时间/指标互相核对。产物是草稿或文件，不自动发送或投递。
5. **版式与检查**：保留可用视觉风格；页数服务内容。交付前查事实一致、阅读顺序、可提取性、渲染视觉、投递完整性；无法完成某项检查就标缺项，不标「已验收可投递」。
6. **保存与联动**：生成稿先写到临时文件，再用 `freeze-resume` 冻结为新的持久版本；通用版本标记 `kind=base`，针对岗位的版本标记 `kind=tailored` 并记录 `based_on` 与 `target_job`。把冻结返回的 id、path、source_path、created_at 和改动摘要追加到 `profile.resume_versions`。针对岗位的版本默认不替换当前基础简历；只有用户明确要求时才切换 `active_resume_id` 和 `resume_path`。只有确认的新事实才更新 profile；改写完成后刷新简历美化卡；保存简历不等于已投递。

改写示例（仅演示边界）：原始事实「协助测试新注册流程，整理问题清单交给研发」→「执行新注册流程测试，归纳问题并形成清单供研发修复」。除非用户补充依据，不能写成「主导增长实验，提升注册转化率」。
