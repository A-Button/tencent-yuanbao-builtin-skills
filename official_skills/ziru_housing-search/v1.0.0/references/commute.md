# 通勤找房

## 先确定目的地

使用 `resolve_locations(purpose=destination)` 查询公司、写字楼、园区等地点，并同时提交用户明确的 `city_name` 与 `city_code`。地图已配置时来源是百度地图；未配置时工具可能返回 BFF 地点候选，但这些候选只用于确认目的地，尚未计算路线。只有 `resolution=unique_exact_identity` 时可直接采用指定候选；相关、同名多候选或园区/楼座身份不完整时交给用户选择。用户只确认“杭州”并不等于确认了阿里西溪园区或滨江园区。

使用同一候选返回的 `name` 与 `coordinate` 组成结构化目的地，不靠模型记忆填写坐标。居住范围的 `location` 不能替代通勤目的地。禁止按常识做“阿里巴巴 → 西溪园区 → 五常/西溪商圈”之类的推导，也不能拿相邻大商圈冒充公司附近。

用户给出“到 X 步行/公交/驾车 N 分钟”“X 通勤 N 分钟”等明确通勤条件时，`X` 是目的地。只有用户另外明确说了“想住 Y、只看 Y、范围限定 Y”时才同时提交结构化 `location=Y`；“X 附近”不是一个额外居住范围，不能同时把同名商圈作为居住范围。没有独立居住范围时必须走下方单目的地搜索，把目的地坐标、方式和分钟交给 BFF 原生通勤召回。

分别记录每个目的地的交通方式与时长上限。用户明确说通勤时长但未给方式，可说明“先按公共交通”并显式使用 transit；已有方式则继承。“附近”“近一点”“太远了”不是具体分钟数，先对照上一批真实路线；没有上一批事实或明确上限时，追问可接受的通勤分钟数、距离或具体居住范围，不凭空写 30 分钟或 3 公里。地图不可用时不能报告到公司的公里数或分钟数。

若 `resolve_locations(purpose=area)` 同时返回与用户原话完全同名、`searchable=true` 的自如范围，可把它作为“同名自如商圈”的降级候选，但必须先说明这是按商圈范围搜、不是按公司坐标半径搜。优先使用 `match_kind=exact` 的原生范围；`related` 的五常、西溪等范围必须由用户明确选择，不能自动并集搜索。

用户明确给出距离半径时，调用 `search_houses` 的 `nearby`：

```json
{"nearby":{"destination":{"name":"阿里巴巴西溪园区","coordinate":"120.0327,30.2853"},"max_distance_meters":3000}}
```

`nearby` 不能和居住范围 `location`、`commute` 同时提交。工具会把目的地坐标及公里半径提交给 BFF；`nearby_application.backend_filter_applied=true` 表示筛选已提交，但当前没有逐套独立复算直线距离，因此按“3 公里范围检索结果”表达，不报未经返回的精确公里数。单说“附近”时不得自行补出这个字段。

必须区分三类条件：`nearby.max_distance_meters` 是距一个已确认具体地点的半径；`commute.max_minutes` 是指定交通方式的真实路线时间；“距任意地铁 N 米”是地铁可达性筛选，当前不支持，不能偷偷改成前两者。若用户明确指定某个地铁站，可先把该站作为具体地点解析，再按用户明确给出的半径使用 `nearby`。

## 单目的地搜索

调用 `search_houses`，完整条件中加入：

```json
{"commute":{"destination":{"name":"阿里巴巴西溪园区","coordinate":"120.0327,30.2853"},"transport":"transit","max_minutes":45}}
```

保持城市、预算、租赁方式、居室及其它已支持条件。工具会把单目的地通勤交给 BFF 召回，并逐房源调用地图验证；`commute_route.within_limit` 才是当前路线是否达标的证据。

同时指定居住片区时再传同一候选组成的结构化 `location`。此时工具对该片区一页房源计算通勤，建议 `page_size=20` 形成候选池，再只展示 3–5 套便于比较。以 `commute_application.qualified_listing_ids` 和每套 `commute_route.within_limit=true` 为达标证据；超限房源只能作为明确标差异的推荐，路线未知的房源不能包装成达标。本页不达标不代表整个片区无解。

## 多目的地与嫌远

已有房源时，调用 `calculate_routes`：`origins` 使用每套房源事实中的真实名称与 `coordinate`，`destinations` 使用每个已确认目的地的真实名称、`coordinate`、方式和上限。完整检查每一对路线。只有全部目标都有成功路线且满足各自上限，才能称为“当前测算都达标”。某条未知则该套总体仍待核验。

若缺少房源坐标，以当前完整条件重新调用 `search_houses`；若目的地身份或坐标无效，重新调用 `resolve_locations`。使用新结果中的结构化名称与坐标最多重试一次，不复制工具返回的任何签名引用。

用户要两人折中、还没选住区时转 [规划](planning.md)，比较最长通勤、双方差距、预算和库存。几何中点不能证明通勤均衡。

嫌远时优先依据已测路线调整选择；用户明确新时长才修改上限。取消通勤时整个 commute 字段省略，普通检索不能残留旧分钟和方式。

## 目的地解析失败

`resolve_locations(purpose=destination)` 返回 `not_found`、错误或没有可核验 `coordinate` 时，本轮通勤搜索停止在“目的地待解析”。不得使用模型记忆或常识填写坐标，不得改用同名/相邻商圈搜索后计算房源直线距离，也不得把直线距离换算成步行时间。可以换用用户提供的更具体园区名、楼座或地址再次解析；仍失败时直接说明暂时无法完成真实通勤筛选。

## 路线表达

说明交通方式、约多少分钟及来源为本次百度地图测算。路线会随出发时间、交通和换乘变化，不承诺每天相同。工具 unavailable 时只说无法核验，不估分钟/公里，也不把楼盘到地铁的步行距离说成到公司的通勤时间。
