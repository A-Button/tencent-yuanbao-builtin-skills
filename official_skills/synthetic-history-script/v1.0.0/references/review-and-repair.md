# 生成后审核与返修

完整生成后必须执行。目标是发现可以定位、修正的问题，不是给自己的创作背书。以当前用户简报为标准，不把股票/旅行样本的20K长度、题数、评分封顶或文本分布设成所有任务的默认。

## 1. 先看成品，不只看结构

读实际历史、留出问题和评分规则。首次需覆盖完整成品；后续局部返修可精读改动及上下文，同时重跑全量结构与引用校验。大文件分片读取，不把工具截断输出误称全文已读。审核输入应绑定具体版本；不由生成代码中的摘要代替最终原文。

| 方向 | 应查什么 | 常见问题与处理方向 |
| --- | --- | --- |
| 格式与接入 | 消息schema、ID/index、日期、TEXT展开、任务映射和文件入口是否一致 | 不因同名TASK-MAP就假设字段一致；明确schema或适配入口，不静默改冻结源 |
| 人物与状态 | 谁说的、谁的偏好、候选/确认/完成/暂停/取消、最新有效版本 | 假设不能成为真实交易/操作；引用旧文不自动更新现状；纠正要覆盖正确对象 |
| 仿真语气 | 用户短问/补充/材料粘贴是否自然；助手长度与任务匹配 | 减少规则课程、固定段式与反复免责声明；长回复用于实际分析/方案，不为凑token扩写 |
| 作者痕迹 | 对话中是否出现写剧本、评测、gold、该记住什么等元指令 | 作者台账/评分设计放正文之外；自然的课堂算例不必删除，但保持假设域 |
| 任务连续性 | 局部交付是否完整，变化是否引发合理后续依赖 | 不只有“已记录”；不会把讨论意愿写成未授权操作；不凭空扩展目标Skill能力 |
| 难度设计 | 跨Session的更新、约束组合和证据分布；长段有没有有效用途 | 长不等于难。查最后一段是否汇总全部答案、旧成稿能否直接复制过关；不靠隐藏规则为难模型 |
| 长度与分布 | 每段约定下限、长段占比、角色长度、重复与段式 | 用户明确要求单长Session时保留该约束，用有任务意义的材料替换重复，不机械拆段或灌水 |
| 题目隔离 | 留出问题仅user；各题历史截止；干扰是否保留；后续状态是否倒流 | 完整人审全集不作Build输入；不得预写新任务答案，不能串用另一题结果 |
| Rubrics | 每项有来源，要求与题干相符；能否区分承诺/成稿；是否可验证 | 证据存在不证明答案做到；防止复制旧稿即可过关；条件项未触发如何计分、权重/分母/封顶须明确 |
| 范围与安全 | 是否把模拟Skill回执说成真执行，是否包含无必要的真实隐私/凭证 | 明确合成声明；没有实际业务调用时不宣称真的查询/发送/交易；不为写作擅自联网或运行评测 |

可报告字符分布、重复段式、证据集中度等诊断数据，但没有普适合格阈值。负向约束未被违反不一定说明成功召回；某条评分证据在多个地方出现也不必然是缺陷。只有实际测量才报告token；说明编码、统计范围，不能声称所有模型一样。

## 2. 难度和评分的反例检查

在作者侧检查下面的捷径，不把反例/预期答案写进原始历史：

- 只看最后一个Session，是否已经拿到了完成任务所需的全部信息？
- 复制历史中的现成稿件，是否无需适配新需求就能拿到满分？
- 只复述偏好、列待办或承诺下一步，是否仍会因复合项太宽而高分？
- 未知实时资源是否被评分规则强迫猜测，或合理条件方案是否被误判为未交付？
- 可选/“若提到”条目未触发时，是未违反、N/A还是遗漏？分母和跨题比较是否明确？

发现捷径后先判断是否符合该题本来目标。只有用户要求综合续接/迁移时才补强，不把每道简短诊断题都强制变成高难综合题。难度只作设计判断；没有实际实验就不报告提升分数/召回收益。

## 3. 问题分级与返修闭环

记录每个问题的版本、Session/index或文件/评分项、可核查摘录、影响、修订和复查结果。

- **阻断交付**：缺正文/明确长度未达标、结构无法解析、来源引用失效、留出或未来泄漏、关键状态矛盾、作者隐藏规则导致无解、题目与Rubrics实质冲突。
- **需要返修**：明显作者口吻、严重模板重复、核心任务只有占位、仿真显著失真、与任务目的相悖的明显捷径。
- **可披露局限**：个别风格判断、尚未实测难度、受能力限制未独立验证的非阻断项。不能把阻断问题降成“局限”来宣称通过。

在已授权创作范围内，由生成Agent修复问题，不把“请用户帮我改”当默认交付。返修后重读改动和受影响上下文，并重新检查：原始JSON→历史/问题投影→TASK-MAP→证据引用→评分政策→完整明文→统计/manifest/Hash。不要为了过检查降低用户约定的长度或换掉考点，也不要随意新增难度目标。

默认最多3轮自审返修；用户已给其他次数/预算时按其要求。连续不能解决同一阻断、材料缺失、需要新业务能力或改变用户已确认范围时，保留当前版本与问题清单，标记`needs_user_decision`，说明具体需要的选择，不无限循环或伪称最终完成。新一轮用户授权后可继续修。

已交付、冻结或准入版本不原地覆盖；修订创建新版本/候选迭代并保留来源关系。内部迭代不必复制整个工作目录，但必须保留前后证据，不能把失败记录抹去。

## 4. 最终给用户看什么

- `conversation-review.md`：从最终JSON生成/校对的逐Session、日期、角色、index全量明文，包含各个独立留出问题但不包含其解答；不以摘要或省略号代替正文。
- `REVIEW.md`或明确指向的`REVISION-REVIEW.md`：审核方向、实际发现和位置、返修前后、校验结果、剩余局限、是否可交用户复审。
- 原始消息、独立历史与题目、任务入口、Rubrics和版本/Hash；说明哪个文件给Build，哪个给Answer，哪个只给Evaluator。

自审没有阻断后，状态为`pending_user_review`。请用户审阅最终明文；准入必须由用户明确确认，另走admission.md。自审通过不是独立审核、真实业务测试或已验证的评测难度。
