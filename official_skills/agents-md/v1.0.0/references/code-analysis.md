# 代码文件分析指南

## 概述

本文档详细描述如何对代码文件进行深度分析，是生成 AGENTS.md 文档的核心步骤。

## 要求

- **CRITICAL**: 每个 js、ts、jsx、tsx 文件都必须读取分析

## 分析流程

### 1. 单文件分析流程

读取 `.analysis-temp.md` 的文件列表，循环对每个代码文件执行以下分析步骤：

#### 1.0 读取临时记录
- 读取 `.analysis-temp.md` 获取已有分析结果
- 将临时记录内容作为当前文件分析的上下文参考

#### 1.1 读取文件
- 完整读取当前文件内容
- 记录文件路径、大小、类型

#### 1.2 功能识别
- 分析文件主要功能和职责
- 识别文件在模块中的角色（入口文件、工具类、组件等）

#### 1.3 代码结构分析
- 识别类、函数、方法的结构和关系
- 分析导出内容（export）
- 识别主要的数据结构和类型定义

#### 1.4 依赖分析
- 分析该文件的导入依赖（import）
- 识别被其他文件依赖的情况
- 区分内部依赖和外部依赖

#### 1.5 设计模式识别
- 识别使用的设计模式（单例、工厂、观察者等）
- 分析架构特点和代码组织方式

#### 1.6 专有名词提取
- 提取文件中的专有术语
- 参考 [专有名词映射表](./GLOSSARY.md) 进行转换

#### 1.7 更新临时记录并清理上下文
- 将当前文件的分析结果追加到 `.analysis-temp.md`
- 更新分析进度计数和文件分析状态
- **CRITICAL**: 清理当前文件分析产生的上下文，释放内存
- 仅保留临时记录文件内容作为后续分析的参考

### 2. 分析记录格式

每个文件的分析结果应按以下格式记录：

```markdown
#### 文件：[文件路径]
- **主要功能**: [功能描述]
- **核心组件**: [类/函数列表]
- **依赖关系**: [导入的模块和被依赖情况]
- **设计特点**: [架构模式和设计亮点]
```

### 3. 文件优先级

分析时应遵循以下优先级顺序：

1. **入口文件**: `index.ts`、`main.ts`、`App.tsx` 等
2. **核心业务文件**: 实现主要功能的文件
3. **工具/辅助文件**: hooks、utils、helpers 等
4. **类型定义文件**: `types.ts`、`*.d.ts` 等
5. **配置文件**: 各类配置相关文件

### 4. 分析深度控制

| 文件类型 | 分析深度 | 说明 |
|---------|---------|------|
| 入口文件 | 详细 | 完整分析导出、路由、初始化逻辑 |
| 业务组件 | 详细 | 分析 props、状态、主要逻辑 |
| 工具函数 | 中等 | 关注主要功能，忽略实现细节 |
| 类型定义 | 简要 | 列出主要类型，不展开字段 |
| 文档文件 | 辅助 | 结合文档内容辅助理解代码逻辑 |
| 配置文件 | 简要 | 仅记录关键配置项 |
| 测试文件 | 跳过 | 通常不纳入分析 |
| 样式文件 | 跳过 | `.css`、`.less`、`.scss` 等不纳入分析 |
| 图片文件 | 跳过 | `.png`、`.jpg`、`.svg` 等不纳入分析 |

### 5. 文档辅助分析

当目录中存在文档文件（如 `README.md`、`CHANGELOG.md` 等）时：

1. **优先阅读文档**: 了解模块的设计意图和使用方式
2. **结合代码验证**: 用文档信息辅助理解代码实现
3. **补充分析记录**: 在分析记录中引用文档中的关键说明

```typescript
// 分析要点：
```


## 常见模式识别

### 设计模式

| 模式 | 识别特征 | 记录方式 |
|-----|---------|---------|
| 单例模式 | 私有构造函数、静态实例 | 标注"使用单例模式" |
| 工厂模式 | 创建对象的工厂函数 | 标注"使用工厂模式创建 XX" |
| 观察者模式 | 订阅/发布机制 | 标注"基于观察者模式的事件系统" |
| 策略模式 | 可替换的算法/行为 | 标注"使用策略模式处理 XX" |

### 架构模式

| 模式 | 识别特征 | 记录方式 |
|-----|---------|---------|
| MVC | Model/View/Controller 分离 | 标注架构类型 |
| MVVM | ViewModel 层 | 标注架构类型 |
| 容器/展示组件 | 逻辑与 UI 分离 | 标注组件类型 |
| 状态管理 | Jotai atoms | 标注状态管理方式 |

## 错误处理

### 无法理解的代码

```markdown
#### 文件：[文件路径]
- **主要功能**: 需要进一步分析
- **备注**: [说明无法理解的原因]
```

### 文件读取失败

```markdown
#### 文件：[文件路径]
- **状态**: 读取失败
- **原因**: [错误信息]
```

### 代码量过大

对于超过 500 行的文件：
1. 优先分析导出内容
2. 关注公共 API
3. 简化内部实现描述
4. 标注"文件较大，仅分析核心功能"

## 输出示例

```markdown
#### 文件：src/components/ChatInput/index.tsx
- **主要功能**: 聊天输入框组件，处理用户消息输入和发送
- **核心组件**: 
  - `ChatInput`: 主组件
  - `useChatInput`: 输入状态管理 hook
- **依赖关系**: 
  - 导入: `@/hooks/useChat`, `@/atoms/messageAtom`
  - 被依赖: `ChatPanel`, `MainLayout`
- **设计特点**: 使用容器/展示组件模式，逻辑与 UI 分离

#### 文件：src/hooks/useChat.ts
- **主要功能**: 聊天功能核心 hook，管理消息发送和接收
- **核心组件**:
  - `useChat`: 主 hook，返回 { sendMessage, messages, isLoading }
- **依赖关系**:
  - 导入: `jotai`, `@/api/chat`
  - 被依赖: `ChatInput`, `MessageList`
- **设计特点**: 基于 Jotai 原子化状态管理
```

## 最佳实践

1. **保持客观**: 只描述代码实际做了什么，不推测意图
2. **关注公共 API**: 优先分析对外暴露的接口
3. **简洁描述**: 避免复制代码，用自然语言概括
4. **标注不确定**: 遇到不确定的逻辑，明确标注
5. **记录依赖**: 依赖关系对理解模块架构至关重要
