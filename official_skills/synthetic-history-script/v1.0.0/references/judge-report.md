# 配套报告与Judge rubrics

评分材料必须在历史之外；最终Agent答案冻结前，不能让记忆构建、检索、精排、压缩critic或回答模型读取。这里是样本设计用的候选评价，不自动替换用户已有的正式Benchmark/Judge协议。

## 报告结构

1. **来源与范围**：大纲依据、输入Skill定义版本、合成声明；说明未真实调用业务工具。
2. **实际Session统计**：主题、日期、消息数量、长度、Skill标记位置；对照约定下限逐段检查。
3. **最后的新任务**：原文、改变的条件、历史/留出边界；不能提前给历史加入解决方案。
4. **两列Rubrics主表**：信息类型 / 针对最后问题的预期正确处理。
5. **证据附表**：rubric ID、Session ID、index、角色、简短摘录；需要组合的事实列多条，不只指向最后一段总结。
6. **更新关系**：哪些已被纠正、否决、局部覆盖或仅属于他人。
7. **一致性与局限**：实际做过的检查、未做的真实执行/独立标注/模型评测、时效信息缺口。

有分支/干扰时另列事件—问题—rubric映射，并分别报告主线、分支和干扰的数量/长度。关联分支按其对新任务的实际影响评分；纯干扰不设专门题目或评分项，不能因Agent没有复述它而扣分。类型与多题时间边界遵循 [branches-and-distractors.md](branches-and-distractors.md)。

有多个留出问题时，每题各有上述两列主表、允许历史范围、证据和分值。逐条验证证据属于该题允许的历史，尤其不让后续状态桥接进入较早问题。不得从其他题的预期答案推导本题历史事实。

## 主表如何写

下面是信息类别的选项，不是每个场景都必须有的固定评分点。根据实际历史选择，每一行都要能落到可观察的输出或行为。

|信息类型|针对最后问题的预期正确处理|
|---|---|
|基础条件与硬约束|保留仍有效的日期、参与者、截止条件和任务范围；新需求明确替换的条件不再沿用|
|深层目标与优先级|新方案满足用户原本目的，而不是只替换名称或表面形式|
|稳定偏好与人物归属|正确区分谁的偏好，按适用对象落实；不把他人的咨询当用户要求|
|局部例外与历史纠正|单次例外不永久化；显式修正覆盖旧错误；候选不等于决定|
|原方案的依赖关系|识别核心变更影响的安排，重建一份整体相容的方案，不逐项机械拼接|
|不可直接迁移的体验或功能|核实可行替代、解释冲突或提出必要澄清，不凭空保证兼容|
|资源、费用与执行状态|区分已付/未付、预算/成本、已提交/已完成、预计退款/到账；不存在的订单不处理|
|时效与能力边界|需要新查的信息标明并核实；不拿旧快照当现在；不虚构Skill没有的功能|
|后续安排同步|必要时调整与旧方案绑定的提醒或待办；没有执行依据就列为待办，不宣称已完成|
|澄清与授权|不重复问历史已明确的信息；对真正新增的缺口追问；计划变更不等于交易授权|

不要用“记住了所有偏好”作一条无法核查的大评分点。细化到具体事实或一组相同机制的事实，写清怎样才算落实，但避免同一个错误在多个近义条目反复扣分。

**证据约束：**只有最终历史中出现、可合理推导的信息才可要求。作者大纲写了但消息没写，不是Agent遗漏。推断要说明依据和不确定性，不把作者意图当事实。没有当前时刻、实际库存、工具输出的部分，正确做法可能是核实或给条件方案，不是猜中作者答案。

## 候选评分法

涉及“必须本轮交付”、严格门槛、相似历史误用或搜索成本时，先按 [strict-rubrics-and-efficiency.md](strict-rubrics-and-efficiency.md) 明确交付合同与独立效率协议。既有高分样本不能被原地换题或改分，需新数据/协议版本。

除非用户已有协议，建议每项0/1/2：

- 0：未处理或处理错误，或者虽复述事实但最终方案明显违反该条件。
- 1：部分覆盖，但没落实到方案/待办，或适用范围不清、存在局部遗漏。
- 2：正确处理并落实；确实缺少信息时，明确列出必要核实或澄清，而非编造。

单独记录关键错误，例如违反硬截止、混淆参与者、虚构付款退款、把已经否决的危险/不可行方案恢复。报告分项和关键错误，不只给一个总分；未获得用户批准不擅自设定正式通过阈值。

允许多个正确新方案，不按唯一参考路线或措辞评分。是否真实查到新事实、是否真的调用工具，要以实际RunTrace判断，不能用合成历史里的Skill标记证明。引用正确不等于回答正确，召回了也不等于使用了。

```json
  "question_session_id": "thread-synthetic-heldout",
  "question_index": 1,
  "rubrics": [
    {
      "rubric_id": "R01",
      "information_type": "已确认的固定安排",
      "expected_handling": "填写本样本具体的、可观察的正确处理要求。",
      "max_score": 2,
      "evidence": [
        {"session_id": "thread-synthetic-history", "index": 5, "role": "user", "excerpt": "最终消息中的精确摘录"}
      ]
    }
  ],
  "critical_error_flags": [],
  "evaluation_status": "not_run"
}
```

示例中的占位内容必须替换；不能把示例ID引用到实际报告。台账、rubrics和参考回答均不进入history-only文件。

## 诊断归因，不提前声称效果

生成样本后只能确认创作与校验结果。后续如果真的运行评测，分别检查：原文是否明确 → 压缩是否保留 → 检索是否召回 → 回答是否正确使用。没有这些产物时不能归因“Memory Search能力差”或声称剧本提升了召回率。

为了让检索有必要，评测端应只提供留出问题、工具入口与精确记忆快照；长历史本身不会强制工具调用。是否支持多轮搜索、预算多大、是否允许读取原始证据，由评测协议决定，不能在写作Skill中偷偷改动。
