# 提交找房需求

这是“暂时没有合适房源，或用户主动希望管家继续协助，由自如后续联系”的写操作，不是每次空结果的自动动作。

## 使用条件

1. 必须先确认一个自如可搜索的居住区域，并执行该区域的 `search_houses`。调用 `preview_housing_request` 时，把最近一次区域搜索的完整有效条件整理为结构化 `search_criteria`；不要使用、复制或改写 `search_ref`。若用户只有城市、通勤终点或“附近”锚点，先让用户确认具体商圈、小区或行政区，再完成区域搜索。
   - `search_criteria` 至少包含 `city_code`、`rental_mode` 和已确认的 `location`；预算、居室、朝向、面积、独卫、阳台、地点半径和通勤条件只在最近一次搜索实际使用时填写。
   - 位置必须使用用户已确认的 `{name, type}`；地点半径使用 `{destination_name, max_distance_meters}`；通勤使用 `{destination_name, transport, max_minutes}`。不得把通勤终点冒充居住区域，不得把旧轮次或用户已经取消的条件带入。
   - MCP 会在该区域内按价格升序检查前几套真实普通房源，找到第一位可识别的负责管家作为需求接收人。房源只用于内部确定 `keeperId`，不是用户看中的房源，不展示、不推荐，也不加入备注。管家当前休息不阻止需求提交。
2. 只有用户明确表示愿意留下需求、希望自如联系，或主动提出让管家继续帮找时才开始。普通空结果先解释原因，并提供调整条件、换片区或“管家帮找”等选项。
   - 用户选择“管家帮找”表示愿意核对待提交内容，但不等于已经同意提交。
3. 调用 `preview_housing_request`，把当前真实进展和用户补充要求写进 `note`；联系时间只有用户明确说过才填写。备注不能空泛，也不能编造用户未表达的不满意原因：
   - 用户说过具体原因时，记录该原因，例如“前两页房源离地铁较远，希望优先推荐步行 10 分钟内的房源”。
   - 用户未说明具体原因时，只记录已发生的事实，例如“已查看当前候选，希望管家继续推荐符合当前条件的房源”；只有确实浏览多页或明确没选中时，才写具体数量或“暂未选中”。
4. 面向用户只展示有值的核心条件、已确认区域、必要备注和账号脱敏手机号，不展示“未指定”字段，不强制使用表格。用自然话术询问：“以上需求没问题的话，我就提交给负责国贸区域的自如管家继续帮你找，并通过账号手机号 135****8040 联系你，可以吗？如需更换本次联系号码，也可以告诉我。”区域和号码按实际结果替换。账号没有可用手机号时，说明用途后询问用户是否提供本次联系号码。
   - 不要说“我先读取流程”“已生成待确认”“留资”“request_ref”“search_ref”或工具名称，也不要主动解释“不是即时客服转接”。只有用户误以为正在实时转接时，才说明会由自如工作人员后续联系。
   - `submission_available=false` 时只说“现在暂时无法提交给管家”，不得继续承诺。
5. 用户明确确认后，调用 `submit_housing_request`，把预览结果中的结构化 `confirmed_request` 原样传入。确认使用账号手机号时传 `phone_action=use_account_phone`，不要传 `user_phone`；用户明确给出新号码时传 `phone_action=replace` 与 `user_phone`。替换号码会写入管家可见的需求备注，账号身份仍以 OAuth 用户为准。MCP 服务端按 OAuth `uid` 在当前进程内限制最多成功使用 2 个不同替换号码；提交失败不占次数。出现 `PHONE_REPLACEMENT_LIMIT_EXCEEDED` 时，不要继续索要新号码，请用户改用账号手机号或此前成功使用过的号码。不要选择或复制旧版 `request_ref`。
6. 只有 `status=submitted` 才能说“已提交”。工具失败、超时或响应不明确时，只能说明没有确认提交成功，并允许重试。
   - 区域无法唯一确认、区域内没有可用于确定负责管家的真实房源，或前几套房源均无法解析管家时，说明本次尚未提交，请用户确认更具体的区域、换一个区域或稍后重试；不得跨区域随机找管家。

## 推荐确认话术

> 好的，我来请负责国贸区域的自如管家继续帮你找。提交前确认一下：北京国贸、整租一居、6500 元/月以内；将通过账号手机号 135****8040 联系你。以上信息没问题的话，我就按这个需求提交。

条件按当前用户实际情况替换；条件较多时最多保留最关键的 3–5 项，其他要求合并成一句补充说明。

## 隐私与状态

- 不主动索要姓名、身份证等无关信息。
- 不在回复或日志里展示完整手机号；工具只返回脱敏号码。
- 新流程只传预览返回的结构化 `confirmed_request`，其中包含已展示给用户确认的需求、备注与联系时间；旧版签名引用只用于兼容旧客户端，模型不要读取或复制。
- 不向用户展示内部用于确定管家的房源、`inv_no` 或 `keeperId`；日志可记录这些字段用于审计。
- 模型不应无故重复提交；工具失败时最多按用户要求重试，不能假称已经成功。
